# 거래 후 잔고·대시보드 잔액 조회 검증

2026-11-15 · `feature/account-history-filter` · 기준 `b6fa382` · [설계](../designs/transaction-balances.md).

- 실제 거래·계정·통화별 누적 잔고를 스키마 v9에 저장한다. 같은 날짜는 거래 ID 오름차순이다. 과거 삽입·날짜 변경·계정 변경·unpost/repost·삭제 시 영향을 받는 이후 잔고를 동일 쓰기 트랜잭션에서 보정한다. 반복 생성·할부·개시잔액·이관·분류 이동도 기존 posted 경계를 사용한다.
- 선택 계정 조회에 `거래 후 잔고`를 제공한다. 날짜·태그·페이지를 적용하기 전 장부 누적값이며 현재 계층의 그룹·보관 후손·과거 그룹 직접 기록을 포함한다. 부채·수익·자본의 자연 부호로 표시하고 변동액 색상과 잔고를 분리한다. 전체 계정 조회의 기존 계약은 유지한다.
- 새 `balance_after.amount`는 10진 문자열이고 UI는 BigInt로 표시한다. 개별 저장 잔고는 signed int64이며 REAL 승격을 CHECK로 차단한다. 범위를 넘는 쓰기는 `balance_history_integer` 오류와 함께 원장·캐시를 롤백한다. 그룹 합계는 Python 정수로 정확하게 계산한다.
- 메타데이터만 수정할 때는 기존 금융 분개를 다시 쓰지 않는다. 유효성·동시 수정 버전·요청 영수증·태그 원자성은 유지한다.

## 검증

- 신규 백엔드 8개: 독립 Python fold와 저장값 대조, 동일 날짜·분할·소급 삽입·날짜/계정 변경·무작위 60회 수정·시나리오 이동·통화·보관·그룹 내부 이동·롤백·같은 읽기 스냅샷·v8 마이그레이션 백필/실패/재실행을 확인한다. 읽기는 쓰지 않는다.
- signed int64를 넘는 추가와 삭제 모두 원자적으로 실패한다. 메모만 수정하는 경계 사례는 금융 잔고를 그대로 보존한다. 그룹 10^19 합계도 정확한 문자열로 반환한다.
- `/balances`의 실제 잔고는 계정 수와 무관하게 1회 batch SELECT(계정 메타데이터 조회 별도), 전체 거래 hydration은 posting/tag를 포함해 3회 SELECT다. 선택 계정 거래내역은 페이지 전체 잔고를 1회 추가 batch SELECT하므로 비어 있지 않은 helper 조회는 5회다. 기존 미선택은 4회다.
- E2E 집중 9개: 이전 필터·URL·응답 순서·수정 복귀, 색상·문구 숨김, 실제 101건의 2페이지 거래 직후 잔고와 계정 변경 후 재계산, 자연 부호·필터 초안·전체 계정 해제, KRW/USD 큰 정수의 minor unit 표시와 모바일 axe를 검증한다.
- SQLite 중간 SUM overflow 통계 회귀는 기존 400 오류를 유지하도록 v8 legacy fixture에서 검사한다. 새 v9는 그 누적값을 저장 전에 거부한다. 할부 v7 업그레이드 검증은 현재 스키마 버전을 따르며 기존 거래·배분 보존 assertion은 유지한다.
- 같은 모델의 별도 문맥으로 저장/마이그레이션·성능/보안, UI/API·유지보수, 테스트, 적대적 검토를 수행했다. 정수 승격·그룹 집계·메타데이터 수정 경계 문제를 수정하고 재검토했다. 외부 모델 및 중첩 Codex 호출은 사용하지 않았다.

## 성능 측정·제한

동일 로컬 환경의 합성 10,000건·계정 200개에서 7회 중앙값을 비교했다. 실제 잔고 집계 부분만 기존 **200 SELECT / 2323.611ms**에서 **1 SELECT / 0.402ms**로 줄었다. 전체 거래 객체 생성은 **145.078ms → 129.817ms**, 합성 데이터 쓰기는 **0.918초 → 1.570초**였다. 거래·분개·태그 건별 조회를 제거했지만 객체 생성·응답 크기·프런트 렌더·차트 계산은 여전히 비용이 든다. 이 수치를 대시보드 전체 HTTP/화면 시간이나 실제 사용자 DB의 속도로 주장하지 않는다.

저장은 조회를 빠르게 하는 대신 같은 계정의 오래된 거래를 바꾸면 이후 행을 보정한다. 현재 잔고를 과거 행에 반복 표시하지 않는다. 스키마 업그레이드는 기존 백업/원자적 마이그레이션 runner를 사용하며, 큰 기존 누적값이 int64를 넘으면 실패 후 기존 DB를 보존한다. 로컬 구현·미출시이며 PR #18 의존성, ship/main 병합은 별도 요청 단계다.

## v10 소급 기장과 전망 조회 벤치마크

PR #20의 첫 CI에서 기준 브랜치는 전망 서비스와 API의 p95가 각각 129.7ms와 142.4ms였다. v9 후보는 20분 제한 안에 결과를 출력하지 못했다. 같은 계정에 과거 거래를 게시하면 이후 잔고 행마다 해당 계정의 분개 전체를 다시 읽어 이번 거래의 변동액을 계산했다.

로컬 합성 장부에 실제 거래 500건과 예정 거래 500건, 거래당 분개 2개를 준비했다. 세 버전 모두 거래 ID 순서로 게시했고 실제 거래일은 기존 벤치마크의 `id % 365` 순서로 순환했다. 아래 시간은 분개 삽입을 마친 뒤 게시하는 구간 한 번을 측정한 값이다.

| 버전 | 게시 시간 | SQLite 총 변경 행 수 |
| --- | ---: | ---: |
| main, v8 | 0.012초 | 3,000 |
| 수정 전, v9 | 18.750초 | 84,650 |
| 수정 후, v10 | 0.129초 | 84,650 |

v10은 계정·통화별 변동액을 이번 거래의 분개에서 한 번 집계하고 날짜·거래 ID 인덱스로 이후 잔고를 찾아 보정한다. 기존 v9 장부는 쓰기 트리거만 교체한다. 회귀 테스트는 365일 순환 순서로 기장하고, 첫날 거래를 취소한 뒤 금액과 날짜를 고쳐 다시 게시한다. 각 단계에서 저장한 모든 잔고를 원장으로부터 독립 계산한 값과 대조한다. SQLite VM 명령 수 상한을 적용한 같은 테스트가 v9에서는 게시 도중 실패하고 v10에서는 통과했다.

전망 읽기 벤치마크는 양쪽 버전에서 같은 ID와 날짜의 실제 거래 50,000건과 예정 거래 500건을 날짜·ID 순서로 게시한다. 장부 준비 시간을 별도 기록하고, 이후 서비스와 HTTP API를 각각 5회 예열하고 30회 측정한다. 기존 SQL 문장 수와 같은 러너의 p95 비교 기준을 적용한다.

같은 머신에서 전체 읽기 벤치를 두 번 비교했다. 서비스 p95의 수정본/기준 배율은 1.031과 0.978, API p95 배율은 0.964와 0.889였다. 두 비교 모두 서비스와 API가 각각 SQL 10개를 실행했다. 첫 비교의 장부 준비 시간은 v8 4.02초, v10 11.29초였다.
