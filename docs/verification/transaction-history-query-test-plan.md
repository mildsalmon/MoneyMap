## Affected Pages/Routes

- `/transactions`: 최근 한 달 기본값, 빠른 기간·직접 기간·태그 조회, 100건 페이지, 로딩/오류/빈 결과.
- `/transactions/:id/edit`: 수정 저장·취소·Back 이후 적용 조건과 같은 페이지의 위치 복원.
- 제안 `GET /api/transaction-history`: 날짜·태그 SQL 필터, 전체 건수, 페이지 보정, 같은 요청 안의 일관된 읽기.
- 기존 `/api/transactions`, `/api/transactions/:id`, `/api/tags`, `/api/balances`: 기존 동작 보존 및 새 History와의 연결 회귀.

## 프레임워크와 격리

- 백엔드: pytest, 기존 FastAPI TestClient·임시 SQLite fixture 재사용. 다중 연결 검증은 임시 파일 DB와 WAL·Event 동기화 패턴을 재사용한다.
- 프런트엔드: 기존 Playwright runner로 순수 상태 함수와 브라우저 흐름을 모두 검증한다. 별도 테스트 라이브러리는 추가하지 않는다.
- 실제 원장·실행 중인 개발 서버에 쓰지 않는다. E2E는 미사용 전용 포트와 기존 격리 설정을 사용하고 외부 API override가 실제 원장을 가리키지 않는지 먼저 확인한다.
- 날짜 계산은 주입한 오늘 값으로 단위 검증하고 기본 진입 E2E는 브라우저 시계·시간대를 고정한다. 고정된 과거 거래 수정 테스트는 명시한 시작일·종료일로 진입한다.
- 합성 거래는 고유 식별자/태그로 분리한다. 동일 날짜 100건 초과, 정상 복식 분개, 해당 페이지 밖 데이터, 다른 시나리오와 posted=0 거래를 포함한다.

## 실행 경로와 사용자 흐름

아래 함수명은 구현할 책임을 표시한 것으로 아직 존재하는 코드가 아니다. 각 G 항목은 여러 입력 조합을 포함하는 테스트 그룹이다.

History 진입

     |-- 유효 날짜/태그/페이지 -> 적용 조건
     `-- 누락/잘못된 날짜/페이지 -> 오류, 요청 안 함
  -> 날짜/태그 초안 입력                                [G03 신규]
     |-- 조회 전 -> 이전 결과 안내, 페이지 차단
     |-- 조회/Enter -> 1페이지, 결과 숨김
     `-- 빠른 선택 -> 즉시 적용, 1페이지
  -> 전용 GET
     |-- API 형식·날짜 검증 -> 잘못된 요청 거부           [G04 신규]

     |-- 정상/0건 -> 건수·행·버튼 일치                   [G09 신규]
     `-- 느림/실패/재시도/역순응답/이탈 -> 오래된 응답 무시 [G10 신규]
  -> 수정 저장 / 취소 / Back                           [G11 확장, CRITICAL, E2E]
     |-- 같은 조건+페이지 -> 결과 준비 후 위치/포커스 1회 복원
     |-- 새 조건/페이지 -> 복귀 의도 폐기, 목록 시작
     |-- 날짜·태그 밖 / 다른 페이지 -> 설명, 현재 페이지 유지
     `-- 마지막 페이지 없어짐 -> 보정, 시작점과 알림
  -> 삭제                                             [G12 신규, E2E]
     |-- 확인 취소 -> DELETE 0회
     |-- 요청 중 연속 클릭 -> DELETE 1회
     |-- 성공 -> 갱신·페이지 보정
     `-- 거절/응답 유실 -> 안내, DELETE 자동 재시도 없음
  -> 종류·잔액 보존                                    [G13 확장, CRITICAL, E2E]
  -> 모바일/키보드/재진입                              [G14 확장, E2E]

신규 기능 완성 기준 14개 그룹 모두 추가/수정 필요. 기존 관련 테스트가 있다는 것이 새 기간별 경로의 통과를 의미하지 않는다. 이 숫자는 측정된 코드 커버리지가 아니다.

## CRITICAL: 기존 테스트를 약화하지 않고 전환

- `transaction-edit.spec.ts:17`의 `**/api/transactions?*` 목업은 새 History 요청을 잡지 못한다. 새 목록 API 목업을 추가하고 날짜·태그·page를 실제처럼 적용한다. 전용 endpoint를 사용하는 테스트가 기존 무제한 API를 실수로 호출하면 실패시킨다.
- `transaction-edit.spec.ts:30`의 고정 `2026-01-02` 거래는 현재 최근 한 달에서 보이지 않을 수 있다. 거래 날짜를 포함하는 명시적 기간으로 테스트를 열어 날짜에 따라 성공 여부가 변하지 않게 한다.
- 기존 `toHaveURL` 정규식은 tag만 있는 URL 또는 `/transactions` 끝을 가정한다. 문자열 순서가 아닌 정규화된 날짜·태그·페이지 값을 검증하면서 기존 저장·ID 보존·잔액 갱신 확인은 유지한다.
- 기존 스크롤 테스트는 70건·무제한 배열 기반이다. 실제 API를 사용하는 2페이지 복귀를 추가하고 `.main.scrollTop > 0`을 먼저 확인한 뒤 복귀 값을 검증한다. `window.scrollY === 0`으로 바꾸지 않는다.
- `transaction-edit-state.spec.ts:79`의 UI 상태 검증은 기간·페이지·미적용 조회 초안 필드를 허용하되, 거래 금액·메모 등 금융 초안은 복귀 정보에 저장하지 않는 기준을 유지한다.

## 실행과 인수 확인

- 구현 중 각 책임의 집중 테스트를 작성한 뒤 백엔드 전체 pytest, 프런트엔드 전체 E2E, 프런트엔드 build를 실행한다.
- 성능은 SQL 횟수/계획·전송 거래 수·DOM 행 수와 시간 측정을 구분한다. 기계마다 달라지는 지연을 단일 임의 시간 문턱으로 판정하지 않는다. 비어 있지 않은 전용 History 페이지는 최대 4 SELECT(건수·거래·분개·태그)로 검증한다. 연결 설정/트랜잭션 제어와 별도 계정/태그 목록 API는 구분하고, 희소/밀집/없는 태그 및 긴 legacy 분개·메모의 비용도 확인한다.
- 실제 API와 임시 DB를 잇는 핵심 시나리오: 기간 조회 → 2페이지 → 수정 → 복귀 → 마지막 행 삭제 → 페이지 보정. 목업은 실패·지연·응답 유실 재현에 사용하고 이 실제 연결 검증을 대신하지 않는다.
- 사용자는 구현 후 최근 한 달을 훑고 기억나는 과거 거래를 찾아 수정했다 돌아오는 흐름을 확인한다.
