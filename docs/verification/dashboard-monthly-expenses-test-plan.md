본문은 구현 전 승인한 검증 계획을 보존한다. T1~T4를 브라우저 테스트 5개로 구현했고 전체 회귀와 수동 QA를 완료했다. 실행 수치와 한계는 위 결과 문서를 기준으로 한다.

## 대상과 격리

대시보드 / 의 하단 ‘이번 달 지출’ 표. 실제 가계부가 아닌 합성 데이터와 포트별 임시 DB를 사용한다.
기존 frontend/e2e/test.ts 및 Playwright 설정을 재사용한다. 브라우저 시각은 월 중간으로 고정하고 표 내부로 탐색 범위를 제한하여 상단의 동명 지출 합계와 혼동하지 않는다.

## 실행 흐름과 검증 매핑

```
대시보드 진입
  ├─ 계정/거래/규칙 조회 중 → 로딩, 빈 목록 안내 없음 [기존 일부 + T3]
  ├─ 조회 실패 → 오류 → 다시 불러오기 → 전체 목록 [기존 일부 + T3]
  └─ 조회 성공
      ├─ 이번 달 아님 / 비용 아님 → 제외 [T1]
      └─ 이번 달 비용 → 계정별 합산 → 금액 내림차순
          ├─ 12개 이상 → 마지막 행까지 표시 [T1]
          ├─ 여러 거래/분할/부분환불 → 정확한 합계 [T1]
          ├─ 전액환불 0원 / 초과환불 음수 → 유지 [T1]
          ├─ 보관 계정 → 유지; 거래 없는 계정 → 제외 [T1]
          ├─ 동액 → 기존 입력 순서 유지 [T1]
          └─ 0개 → 기존 빈 목록 안내 [T2]
화면 갱신
  ├─ 실제 신규 거래 저장 → 대시보드 복귀 → 반영 [기존 whatif + 제목 수정]
  └─ 조회 중 이탈 → 취소 → 재진입 [기존 query-cancellation]
표시
  ├─ 데스크톱 → 기존 2열, 모든 항목 [T4]
  └─ 모바일 → 기존 1열, 긴 이름/금액 겹침 없음 [T4]
```

위 표시는 계측된 코드 커버리지가 아니라 정적 검토에 따른 계획이다.
기존 테스트는 저장 후 반영, 조회 오류·취소, 잔액 및 기본 반응형을 검증한다.
전체 비용 행의 값·순서·환불·빈 월·긴 목록은 신규 검증이 필요하며 승인 설계의 검증 기준에 이미 포함되어 있다.

## 신규 테스트: frontend/e2e/dashboard-expenses.spec.ts

- T1: 뒤섞인 12개 이상의 비용 계정 합계와 기대 정렬을 고정 데이터로 대조한다. 같은 계정의 복수 거래·분할 분개·부분환불을 포함한다. 전액환불 0원, 초과환불 음수, 보관 비용 계정, 동액 행을 포함한다. 전월·익월·수입·자산·부채와 거래 없는 비용 계정은 제외한다. 모든 행의 이름·금액·순서와 상단 월 지출 합계를 확인한다. 첫 5개만 확인하는 테스트로 축소하지 않는다.
- T2: 활성 자산 계정과 온보딩 완료 상태를 준비하고 이번 달 비용만 없는 상황에서 빈 안내를 확인한다. 양수 지출과 환불이 상쇄된 계정은 T1에서 빈 상태가 아닌 0원 행인지 확인한다.
- T3: 거래 조회를 보류한 동안 빈 안내가 나오지 않는지 확인한다. 503 실패 시 오류와 재시도 버튼을 확인하고, 정상 응답으로 바꾼 뒤 전체 목록으로 복구되는지 검증한다. 계정 조회 실패·취소는 기존 테스트를 재사용한다.
- T4: 1440px 및 390px 너비에서 12개 이상 행의 끝까지 페이지 스크롤로 접근한다. 긴 한글 계정명과 큰 금액이 겹치지 않는지 확인한다. 더보기·접기 버튼을 요구하지 않는다. 레이아웃 문제가 실제 재현되는 경우에만 최소 CSS 수정을 검토한다.

## 기존 테스트 수정·재사용

- frontend/e2e/whatif.spec.ts:122: 기존 ‘이번 달 지출 상위’ 표 탐색을 새 제목으로 변경한다. 계정 생성→거래 저장→대시보드 복귀의 통합 검증은 유지한다.
- frontend/e2e/dashboard-balances.spec.ts: 보관 계정 잔액 비노출·전체 순자산·조회 복구 회귀를 그대로 실행한다. 이 정책을 비용 목록에 잘못 적용하지 않도록 T1에서 별도 검증한다.
- frontend/e2e/query-cancellation.spec.ts: 조회 취소·재진입·실패 복구를 유지한다.
- frontend/e2e/whatif.spec.ts: 기존 전망 및 데스크톱/모바일 기본 배치 테스트를 유지한다.

## 실패 모드

- slice 제한 잔존 또는 새 고정 제한: 마지막 행 누락, T1/T4에서 탐지.
- 양수만 필터링 또는 보관 필터 재사용: 환불·보관 비용 누락, T1에서 탐지.
- 제목 변경으로 기존 선택자 실패: whatif 테스트 수정 후 실행으로 탐지.
- 네트워크 실패를 빈 월로 오인: 기존 오류 처리 유지, T3에서 탐지.
- 긴 목록·계정명으로 표 겹침: T4에서 탐지.
- 월 경계의 날짜 흔들림: 브라우저 시각 고정 및 전월/익월 데이터로 탐지.

## 실행 순서

새 테스트를 기존 코드에 먼저 실행하여 5개 제한 때문에 실패하는지 확인한 뒤 구현한다.
신규 대상 테스트, 백엔드 전체 pytest, 프론트 전체 E2E, build 순서로 검증한다.
E2E는 사용하지 않는 별도 MONEYMAP_E2E_BACKEND_PORT / MONEYMAP_E2E_FRONTEND_PORT를 지정한다.
기본 개발 서버 및 실제 DB를 대상으로 테스트하지 않는다. 이 문서는 실행 결과를 주장하지 않는다.
