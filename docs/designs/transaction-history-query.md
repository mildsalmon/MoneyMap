## 문제와 목표

- 사용자는 “주로 최근 지출을 훑어보”며 먼 과거일수록 조회 빈도가 낮다. 최근 내역은 바로 열고, 과거 내역은 원하는 기간을 지정해 찾도록 한다.
- 현재 `History.tsx`는 실제 원장 전체를 요청한 뒤 브라우저에서 역순 정렬·태그 필터·전체 행 렌더링을 한다. 거래 누적에 따라 전송량과 렌더링량이 증가하는 구조를 바꾼다. 실제 지연 시간은 이번 설계에서 측정하지 않았다.
- 기존 TODO의 P2 ‘거래내역 초기 조회 제한과 더보기’를 이 설계로 구체화한다. 새로운 거래 입력 기능이나 통계 기능이 아니다.

## 승인된 결정

- **기간별 조회:** 사용자가 더보기 대신 제안한 방식. 오래된 내역까지 여러 번 목록을 늘릴 필요가 없다.
- **빠른 선택과 직접 지정 병행:** `최근 한 달`, `이번 달`, `지난달`, 시작일·종료일, `조회` 버튼을 제공한다. 기본 진입은 최근 한 달이다.
- **최근 한 달은 달력 기준:** 오늘이 2026-09-13이면 2026-08-14부터 2026-09-13까지, 양 끝 날짜를 포함한다. 고정 30일이 아니다.
- **100건 단위 페이지 이동:** 선택한 기간을 유지하며 `이전`·`다음`으로 목록을 교체한다. 더보기·무한 스크롤·누적 목록은 제공하지 않는다. 전체 건수와 현재 페이지를 표시한다.
- **태그와 수정 복귀 유지:** 선택한 기간 안에서 태그로 조회하고, 수정 후 돌아오면 기간·태그·페이지·보던 위치를 유지한다.
- **중복 문구 제거:** 결과 위에 날짜 범위와 태그를 다시 표시하지 않는다. 사용자는 “이 문구는 중복인거 같아서 빼도 될듯”이라고 요청했고 수정된 배치를 승인했다.
- **미적용 상태만 안내:** 입력 조건이 조회 결과와 달라졌을 때만 `조회 버튼을 눌러 적용하세요`를 표시한다. 기존 결과는 이전 조회 결과임을 알리고 페이지 이동을 막는다.

## 화면과 상호작용

- 기존 원장 테이블, 메모 보기, 거래별 수정·삭제 버튼을 유지한다. 모바일은 조건 영역을 줄바꿈하고 거래 표만 가로 스크롤한다. 기본 디자인 시스템을 사용하며 새 시각 테마나 의존성은 추가하지 않는다.
- **디자인 검토 승인 (2026-09-15):** 열 순서는 데스크톱·모바일 공통으로 `날짜 → 내역 → 금액 → 흐름 → 수정·삭제`로 변경한다. 사용자는 모바일 사용 빈도가 낮으므로 간단한 변경만 원했다. 모바일 전용 표·고정 열·별도 폭 최적화는 추가하지 않고 기존 가로 스크롤을 유지한다. 좁은 화면에서 앞의 세 열이 항상 모두 보인다고 보장하지 않는다. 금액 우측 정렬·전체 금액 표기는 유지한다.
- 상단에 빠른 선택, 그 아래 시작일·종료일·태그·조회 버튼을 둔다. 결과 위에는 `전체 N건 · 최신순`, 아래에는 `1–100 / N건`, `이전`, `현재 / 전체 페이지`, `다음`을 둔다.
- 화면 시안은 별도 정적 HTML이다. 예시 거래만 사용했고 앱과 연결되지 않았다. 시안에서 생략한 96행은 실제 구현에서 페이지 크기를 줄인다는 뜻이 아니다.
- 직접 수정한 시작일·종료일·태그는 초안으로 유지하고 조회 버튼 또는 폼의 Enter 제출로 한 번에 적용한다. 성공 여부와 별개로 새 조회를 시작하면 1페이지로 이동한다.
- 빠른 선택은 선택한 날짜 범위와 현재 태그 입력값으로 즉시 조회하며 1페이지로 이동한다. 실제 날짜 입력이 프리셋과 일치할 때만 해당 버튼을 선택 상태로 표시한다.
- 페이지 이동은 적용된 조건만 사용한다. 이전 결과에 새 조건의 건수·페이지를 섞어 보여주지 않는다. 한 페이지 이하이면 이전·다음은 비활성화하고, 0건이면 `0건`만 표시하여 `1 / 0`을 만들지 않는다.
- 요청을 시작하면 이전 결과의 행·건수·페이지 컨트롤을 숨기고 로딩 상태와 제출한 조건을 표시한다. 실패 상태에서도 이전 결과는 다시 표시하지 않고 오류·재시도 버튼을 표시한다. 중복 제출·페이지 이동은 막으며 실패 시 해당 요청의 조건·페이지로 다시 조회할 수 있다. 조건을 새로 바꾸면 그 조건으로 조회하며 이전 응답이 새 결과를 덮어쓰지 않는다. 조회 버튼을 누르기 전의 미적용 초안 상태에서만 이전 결과를 명시적 안내와 함께 유지한다.
- 빈 결과는 `선택한 기간과 태그에 해당하는 거래가 없습니다.`로 안내한다. 자동으로 기간을 넓히거나 태그를 해제하지 않는다.

## 날짜 규칙 — 구현 제안

- 브라우저의 로컬 달력 날짜로 오늘을 계산하고 `YYYY-MM-DD`로 전송한다. UTC 문자열 변환으로 날짜가 하루 밀리지 않도록 한다. 원장에 저장된 거래 날짜를 재해석하거나 변경하지 않는다.
- 최근 한 달의 종료일은 오늘이다. 시작일은 ‘오늘에서 달력 한 달을 뺀 날짜’의 다음 날이다. 이전 달에 같은 일자가 없으면 그 달 말일로 보정한 뒤 하루를 더한다.
- 월말 예: 2026-03-31 → 2026-03-01~2026-03-31, 2024-03-31 → 2024-03-01~2024-03-31. 연도 경계 예: 2026-01-13 → 2025-12-14~2026-01-13.
- 이번 달은 해당 달 1일~말일, 지난달은 이전 달 1일~말일이다. 기본 최근 한 달과 달리 이번 달에는 이미 저장된 미래 날짜 거래가 포함될 수 있다. 예측 거래를 새로 생성하지 않는다.
- 시작일=종료일은 하루 조회로 허용한다. 날짜 누락·존재하지 않는 날짜·시작일>종료일은 폼과 API에서 거부한다. 직접 지정한 긴 기간이나 미래 날짜는 임의 제한하지 않는다.
- 조회 도중 자정이 지나도 적용 날짜와 페이지를 자동 변경하지 않는다. 새 기본 진입 또는 빠른 선택을 누를 때 오늘을 다시 계산한다.

## 데이터 조회 — 구현 제안

- 실제 원장의 **모든 기존 거래 종류**를 대상으로 한다. 지출만 남기는 필터는 추가하지 않는다. 수입·이체·환불·개시잔액·CSV 이관·반복 규칙 생성 거래의 표시 의미를 보존한다.
- 기존 `/api/transactions` 배열 응답과 이를 이용하는 다른 화면을 변경하지 않고, History 전용 읽기 API를 추가하는 방향을 권장한다. 예: `GET /api/transaction-history?start=...&end=...&tag=...&page=1`.
- 페이지 크기는 서버와 화면에서 100건으로 고정한다. API는 날짜 범위와 페이지 양의 정수를 검증한다. 실제 원장 `scenario_id=1 AND posted=1`만 조회하며, 별도 시나리오를 선택하는 기능은 범위 밖이다.
- 응답은 `items`, `total`, `page`, `page_size=100`, `total_pages`로 구성한다. `page`는 실제 반환한 페이지다. `total_pages=max(1, ceil(total/100))`로 정하고 0건 화면에서는 페이지 표기를 숨긴다. 과도한 페이지는 마지막 유효 페이지로 보정하고 결과·URL을 일치시킨다.
- 최신순은 `date DESC, id DESC`로 고정한다. 태그 조건은 페이지를 나누기 **전에** SQL에서 적용한다. `EXISTS` 또는 동등한 방식으로 태그 조인 때문에 한 거래가 중복 집계되지 않게 한다. 기존 정확한 태그 일치 의미를 유지한다.
- **성능 검토 승인 (2026-09-13):** 태그가 있을 때는 태그 이름에 맞는 거래 ID 집합을 먼저 구하는 비상관 `IN` 서브쿼리를 우선 사용한다. 기존 태그 연결 인덱스를 재사용하며 이름은 바인딩된 값으로 정확히 비교한다. 합성 데이터에서 상관 태그 이름 비교보다 빨랐고 결과가 같았지만, 중간 ID 집합의 메모리 비용과 희소/밀집/없는 태그는 구현 시 재검증한다. 새 인덱스·DB 마이그레이션은 추가하지 않는다.
- 로컬 단일 사용자 앱과 현재 페이지 표시를 고려해 `COUNT`와 `LIMIT/OFFSET`을 사용하는 접근을 우선 검토한다. 건수 조회와 해당 페이지 조회는 같은 짧은 읽기 트랜잭션에서 처리한다. 깊은 페이지의 SQL 처리량까지 일정하다고 주장하지 않는다.
- 전체 거래를 Python 객체로 구성한 뒤 자르거나 브라우저에서 자르지 않는다. 현재 페이지의 분개·태그만 일괄 로딩해 행마다 추가 쿼리를 실행하는 구조를 피한다. 전송 및 렌더링 거래 수는 최대 100건이다.
- 비어 있지 않은 History 페이지의 읽기 SQL 예산은 최대 4회(건수, 거래, 분개 일괄, 태그 일괄)로 검증한다. 연결 설정·트랜잭션 제어와 별도 계정/태그 목록 API는 이 예산에서 구분한다. 빈 결과는 필요한 조회를 생략할 수 있다. 100건 제한은 거래 수의 제한이며 긴 메모나 legacy 분개까지 응답 바이트가 일정하다는 뜻은 아니다.
- 태그 선택지는 기존 `/api/tags` 목록을 재사용한다. 현재 페이지에 나타난 태그만 수집하면 다른 페이지의 거래를 찾지 못하므로 그렇게 구현하지 않는다. 태그 0건 결과여도 선택값은 유지한다.
- 날짜 범위 인덱스, 분개 거래 ID 인덱스, 태그 연결 인덱스를 먼저 재사용한다. 실행 계획과 합성 데이터로 검증 후 부족한 경우에만 별도 기술 검토에서 인덱스 변경 여부를 결정한다. 이번 설계만으로 DB 마이그레이션을 승인한 것은 아니다.
- 연결·라우터·읽기 어댑터·취소 가능한 `useQuery` 등의 기존 패턴을 재사용한다. 전 저장소 리팩터링이나 범용 목록 프레임워크는 만들지 않는다.

## 조회 상태와 수정·삭제 후 복귀 — 구현 제안

- 적용된 `start`, `end`, `tag`, `page`는 URL에 저장한다. 기본 진입은 구체적인 날짜로 URL을 정규화하여 새로고침·뒤로가기·수정 후 복귀가 같은 기간을 가리키게 한다. 미적용 폼 초안은 URL에 저장하지 않는다.
- 날짜 매개변수가 둘 다 없으면 기본 최근 한 달을 적용하고 기존 태그 링크는 유지한다. 날짜 한쪽만 있거나 유효하지 않은 URL은 오류를 알리고 자동 조회하지 않는다. 페이지가 생략되면 1, 잘못된 페이지 값은 오류를 표시한다. 잘못된 조건에서 원장 전체 조회로 후퇴하지 않는다.
- 새 조회·페이지 이동 시 현재 히스토리 항목의 조회 URL을 교체한다. 브라우저 Back을 페이지 이동 이력으로 가득 채우지 않는다. 수정 화면으로 이동할 때는 기존처럼 별도 탐색 항목을 만든다.
- `HistoryReturn`에 적용 날짜·태그·페이지를 추가하고 검증한다. 조회 전 미적용 초안이 있다면 수정 진입 때 이를 보존하고 복귀 후 다시 미적용 상태로 표시한다. API와 페이지 복귀에는 적용된 조건만 사용한다.
- 저장 후 결과를 다시 읽고 기존 페이지·위치를 우선 복원한다. 수정된 날짜나 태그가 조건에서 벗어나면 `수정한 거래가 현재 조회 조건에 해당하지 않아 목록에 표시되지 않습니다.`를 안내한다. 조건에 맞지만 정렬 변경으로 다른 페이지로 이동했다면 현재 페이지를 유지하고 그 사실을 안내한다.
- 수정 거래가 현재 페이지에 있으면 해당 수정 버튼으로 포커스를 복원한다. 없다면 결과 제목으로 포커스를 이동한다. 실제 수직 스크롤 컨테이너인 `.main`과 표의 가로 위치를 복원하고 화면 크기에 맞게 제한한다. `window.scrollY`만으로 검증하지 않는다.
- **기술 검토 승인 (2026-09-13):** 복귀 위치는 정규화한 적용 `start/end/tag/page`가 현재 조회와 정확히 일치하고 그 조회의 결과가 준비된 경우에만 한 번 적용한다. 날짜·태그·페이지를 바꾸거나 서버가 페이지를 보정하면 이전 복귀 의도를 폐기하고 목록 처음으로 이동한다. `location.key`만으로 일치 여부를 판단하지 않는다. 거래 수정으로 데이터 갱신 세대가 바뀌는 것은 동일 조건 복귀를 막지 않는다.
- 삭제 또는 외부 변경으로 마지막 페이지가 없어지면 마지막 유효 페이지로 보정한다. 보정 시 목록 시작으로 이동하고 알린다. 사용자 페이지 이동·새 조건 조회도 목록 시작으로 이동한다. 빈 결과도 정상 상태로 처리한다.
- **삭제 오류 처리 승인 (2026-09-13):** 목록에서 삭제 요청은 한 번에 하나만 진행해 중복 클릭을 막는다. 성공 응답을 확인한 뒤 갱신·페이지 보정을 수행한다. 네트워크 단절 등 응답 유실 시에는 성공이나 실패로 단정하지 않고 `삭제 결과를 확인할 수 없습니다. 목록을 다시 조회해 주세요.`를 표시한다. DELETE를 자동 재시도하지 않고 읽기 전용 목록 다시 조회를 제공한다. 조회 결과에 행이 없다는 사실만으로 삭제 성공을 단정하지 않는다. 서버가 명시적으로 거절한 오류도 사용자에게 표시하며, 조회 실패와 삭제 결과 미확인을 구분한다.
- 서로 다른 페이지 요청 사이의 외부 변경을 고정하는 스냅샷 기능은 만들지 않는다. 매 조회는 최신 원장 상태를 읽는다. 같은 날짜의 안정 정렬, 페이지 보정과 요청 취소로 기본 일관성을 지키며 삭제·날짜 수정으로 행 위치가 바뀔 수 있음을 명시한다.

## 검증 기준

1. 기본 최근 한 달, 이번 달, 지난달, 직접 지정, 하루 조회, 월말·윤년·연도 경계·로컬 자정 전후를 검증한다. 날짜 양 끝의 거래는 포함하고 바로 밖의 거래는 제외한다.
2. 0·1·100·101·201건과 같은 날짜에 100건을 넘는 합성 거래로 건수·페이지·정렬·경계 중복/누락을 검증한다. 변경 없는 원장을 모든 페이지로 읽으면 조건에 맞는 거래 ID가 정확히 한 번씩 나타나야 한다.
3. 태그가 다른 페이지에만 있는 경우, 존재하지 않는 태그, 태그 없음, 한국어·특수문자 태그도 서버 필터와 전체 건수가 일치해야 한다.
4. 1만 건 이상 합성 데이터에서 페이지 거래 최대 100건, 관련 데이터 일괄 로딩, 쿼리 횟수 상한, 인덱스 사용과 얕은/깊은 페이지 응답 비용을 확인한다. `COUNT`/offset 비용과 화면 렌더링 비용을 구분해 기록한다.
5. 느린 응답·실패·재시도·연속 조건 변경에서 오래된 결과가 새 결과를 덮어쓰지 않으며, 표시된 건수·페이지가 해당 결과와 일치해야 한다. 미적용 상태에서는 페이지 이동이 막혀야 한다.
6. 2페이지 이상에서 수정 저장·취소·브라우저 Back·새로고침을 검증한다. 날짜/태그 변경으로 목록에서 빠짐, 다른 페이지로 이동함, 마지막 행 삭제, 전체 0건 전환, 미적용 초안 복원도 포함한다.
7. CSV 이관·환불·수입·이체·개시잔액·반복 생성 거래가 기존과 같은 의미로 표시·수정되며, 잔액·통계·시나리오·기존 전체 목록 API 결과는 변하지 않아야 한다.
8. 데스크톱/모바일에서 폼 라벨·키보드 조회·포커스 복귀·페이지 버튼 터치 영역·표 가로 스크롤·빈 결과·실패 안내를 확인한다.
9. 구현 시 격리된 합성 DB로 `cd backend && uv run pytest`, `cd frontend && npm run e2e`, 프런트엔드 빌드를 실행한다. 이번 설계 단계에서는 앱 테스트를 실행하거나 실제 DB를 수정하지 않았다.

## 대안과 범위

- 최근 100건 + 더보기: 사용자에게 최근 지출은 기간 단위가 더 자연스러워 제외.
- 최근 한 달 + 이전 한 달 이어 붙이기: 사용자가 기간 직접 조회를 선호해 제외.
- 날짜 입력만 제공: 사용자가 빠른 선택과 날짜 입력을 함께 제공하는 안을 승인해 제외.
- 모든 기간 결과를 한 화면에 표시: 긴 기간에서 초기 문제를 재현하므로 100건 페이지 이동으로 대체.
- 커서 기반 조회는 깊은 페이지 성능에는 유리하지만 총 페이지와 역방향 복귀 관리가 복잡해진다. 실제 비용 검증이 필요성을 보일 때 재평가한다.
- 거래입력 최근 입력 더보기·태그 UI 재설계·새 통계·전문 검색·전체 내보내기·다중 통화·계정 시간 이력은 이번 범위에 포함하지 않는다.
- office-hours 단계에서는 외부 웹 조사와 선택적 별도 모델 의견을 실행하지 않았다. 이후 기술 검토에서 SQLite·Python·React Router 공식 자료를 확인했다. 별도 모델 검토의 생략과 합성 SQL 진단 결과는 아래 기술 검토 기록에 구분했다.


## 구현 순서와 병렬 가능성

| 단계 | 모듈 | 선행 조건 |
|---|---|---|
| 계약 고정 | 읽기 API 응답 및 화면 조회 상태 | 승인 설계 |
| Lane A: 읽기 API·SQL 테스트 | backend/moneymap, backend/tests | 계약 고정 |
| Lane B: 조회 UI·상태·복귀·삭제 | frontend/src, frontend/e2e | 계약 고정 |
| 실제 API 통합 및 전체 검증 | backend/tests, frontend/e2e | A+B 완료 |

A와 B는 계약 고정 후 독립적으로 진행할 수 있다. B 내부의 조회·복귀·삭제는 History와 상태 파일을 공유하므로 순차 진행한다. 최종 통합 테스트는 두 lane 이후다. 이 문서는 병렬 가능성만 분석하며 추가 worktree 생성·구현 에이전트 실행을 승인하거나 실행한 것은 아니다.
