## 문제와 사용 경험

같은 아이템의 거래를 반복 입력할 때 유형 탭과 계정 선택 상자를 매번 거치는 수고를 줄인다. 소유자 본인이 사용하는 로컬 복식부기 가계부이며, 사용자가 제공한 후잉 화면이 상호작용 참고다. 공개 웹 검색은 사용자의 선택으로 생략했다.

사용 흐름: `점심` 입력 → 지난번 저장한 `식비 / 신한카드`가 선택됨 → 금액 입력 → 저장. 다른 계정을 클릭해 저장하면 다음 `점심`부터 바뀐 조합을 사용한다. 날짜와 금액은 아이템 기억 때문에 바뀌지 않는다.

현재 `TxnInput.tsx`는 거래를 전부 조회한 뒤 마지막 8건만 기억 대상으로 사용한다. 동일 내역, 지출 탭, 빈 금액이라는 조건에서만 계정과 금액을 함께 채운다. 저장소 조회 순서는 `date, id`여서 뒤늦게 입력한 과거 거래를 마지막 입력으로 다루지 못한다. 기존 계정 트리, 기장 가능 여부 판정, 복식 미리보기와 저장 API는 재사용한다.

## 사용자 확정 결정

- D1: 지출·수입·이체·카드값 납부 탭을 없애고, 왼쪽 차변·오른쪽 대변을 한 화면에서 클릭한다. 계정 선택 위치를 일관되게 유지하려는 선택이다.
- D2: 같은 아이템에는 마지막으로 저장한 계정 조합 **하나만** 기억한다. 다른 과거 조합 후보나 빈도순 추천은 표시하지 않는다.
- D3: 추가 검색 없이 제공된 화면과 코드에서 설계한다.
- D4: **B, 서버에서 아이템별 마지막 조합을 조회**한다. 입력 화면의 전체 거래 다운로드를 없애고 규칙을 Python에서 검증한다.
- D5: 화면 배치와 이하 상세 규칙을 승인했다. 출처 불명 기존 기록의 최초 확인, 계정만 자동 채움, 수동 선택 보호, 삭제 후 남은 기록 재조회 정책을 포함한다.
- Design D1: 7개 디자인 항목 전체를 검토한다.
- Design D2: 비교 보드에서 **C안(5/5)**을 선택하고 `아이템 항목 밑에 메모 넣을 수 있게 해줘.`라고 요청했다. 이어진 “다음단계 진행해줘”에 따라 이 선택을 반영한다. 기존 메모 제외 범위는 이번 요청으로 대체한다. A/B의 0은 평가하지 않은 값이며 부정 평가로 해석하지 않는다.

- Design D3: 사용자 A. 메모는 저장한 거래에 남기고, 성공 후 동일 초안의 메모·금액은 비운다. 저장 실패와 저장 중 새로 작성한 메모는 보존한다. 과거 메모는 아이템 자동 선택이나 최근 입력 클릭으로 불러오지 않는다.

이하 상세 동작은 D5 및 후속 Eng/Design 결정에서 승인한 구현 기준이다.

## 검토한 방식

- A, 기존 전체 거래 API 결과를 브라우저에서 계산: 변경 범위는 작지만 거래 수에 따라 조회와 전송 비용이 커져 선택하지 않았다.
- **B, 서버 조회 (선택):** 실제 장부의 마지막 거래에서 조합을 도출한다. 조회 API·포트·인덱스·테스트가 추가되지만, 별도 학습 테이블과 장부 사이의 동기화가 필요 없다.
- 다중 조합 후보 UI: 사용자가 “마지막 조합만”을 선택해 제외했다.

## 화면과 입력

- 상단은 날짜 → 아이템 → 금액이며, **아이템 바로 아래에 메모**를 둔다. 기존 `description` 필드는 아이템으로 유지하고 메모는 거래의 별도 선택 입력 필드로 저장한다. 아이템과 메모를 합쳐 저장하지 않으며 가맹점/태그 엔티티는 추가하지 않는다. 두 필드 모두 선택 입력이다.
- 메모는 줄바꿈 가능한 textarea이고 항상 보이는 `메모 (선택 입력)` 레이블을 제공한다. 데스크톱은 아이템 열에 맞추고 모바일은 아이템 바로 아래 전체 너비로 배치한다. Enter는 메모에서 줄바꿈하며 저장을 실행하지 않는다. 현재 시안은 두 줄 높이로 시작한다.
- 본문은 차변과 대변의 두 선택 영역이다. 각 영역에 선택 계정 요약, 계정 검색, 동일한 계정 트리가 있다. 분류는 자산·부채·수익·비용·자본이며 하위 그룹과 영속 계정 순서를 유지한다.
- 그룹 제목은 접고 펼칠 수 있고 직접 기장할 수 없다. 활성 말단 계정만 선택한다. 보관 계정과 개시잔액 시스템 계정은 일반 입력 선택에서 제외한다. 같은 이름의 계정은 그룹 경로로 구분한다.
- 차변/대변을 자산 증감의 `+/-`로만 설명하지 않는다. 차변은 자산·비용 증가 / 부채·수익·자본 감소, 대변은 그 반대라는 도움말을 제공한다. 마이너스통장도 원래의 안정된 자산 계정 위치를 유지한다.
- 선택은 색과 체크 표시를 함께 사용한다. 자동 선택된 계정은 `지난 입력에서 불러옴`을 표시한다. 사용자가 변경하면 해당 쪽은 수동 선택 상태가 된다. 후보 계정 조합 목록은 없다.
- 복식 미리보기는 선택 영역 아래의 얇은 검산 영역으로 옮긴다. 저장과 동일한 postings를 사용해 계정·차변·대변 금액 및 순자산 변화를 보여준다. 불일치, 빈 계정, 0 이하 금액, 양쪽 같은 계정이면 일반 입력을 저장할 수 없다.
- 날짜·계정·아이템을 유지하고 금액을 비우는 기존 연속 입력 동작을 보존한다. Design D3에 따라 메모도 비운다. 저장 중 새로 편집한 초안에는 이 초기화를 적용하지 않는다. 저장 후 금액으로 포커스를 돌린다. 새 아이템을 입력하면 이전 아이템에서 유지된 계정은 새로 판단한다.
- 화면 하단 최근 입력 5건은 유지하되 서버에서 제한 조회한다. 클릭하면 그 거래의 아이템으로 **마지막 조합 조회**를 수행한다. 클릭한 옛 거래의 다른 조합을 덮어씌우지 않는다. 날짜와 금액은 이 동작으로 복사하지 않는다.
- `분할 입력`은 유형 탭 대신 보조 열기 동작으로 남긴다. 기존 다중 postings, 행 추가/삭제, 검산을 보존한다. 각 행의 계정 선택도 같은 클릭 선택기를 사용한다. 분할 모드에서는 아이템으로 행과 금액을 자동 변경하지 않는다.
- 분할 저장은 **계정과 금액이 모두 빈 행만** 여분의 빈 행으로 무시한다. 계정만 선택했거나 금액만 입력한 행, 0 이하·해석 불가 금액이 있는 행은 해당 행에 오류를 표시하고 저장을 막는다. 차변/대변 기본값만 있는 행은 빈 행이다. 유효한 행을 먼저 골라 나머지를 조용히 버리지 않는다. 모든 작성된 행의 검증을 통과한 동일한 postings를 미리보기와 저장에 사용한다. Eng D2에서 사용자 A로 승인했다.
- 모드를 바꿔도 날짜·아이템·메모는 한 입력 초안이 소유한다. 기본 → 분할은 차변·대변 두 행에 현재 선택과 공통 금액을 옮기며 빈 값도 그대로 보존한다. 분할 → 기본은 완전히 빈 초안이거나 차변/대변 각 한 행의 금액이 같고(둘 다 빈 금액도 허용) 서로 충돌하는 계정이 없는 경우 되돌아갈 수 있다. 이때 빈 계정도 그대로 옮긴다. 추가 행, 서로 다른 금액 등 기본 입력으로 표현할 수 없는 경우에는 내용을 버리지 않고 분할 모드를 유지하면서 정리해야 할 행을 알려준다. 이 전환은 별도 저장/기억 갱신이 아니다.
- 기존 카드 잔액 채우기는 차변에 부채 계정, 대변에 자산 계정이 선택됐을 때 `오늘 부채 잔액으로 채우기`라는 명시적 버튼으로 제공한다. 실제 부채가 남아 있을 때만 양수 금액을 채운다. 아이템 자동 선택만으로 금액이 바뀌지 않는다. 부분 납부는 계속 직접 입력한다.
- 720px 이하에서는 차변 → 대변을 세로로 배치한다. **선택한 두 계정 요약은 계정 선택 영역에 도달하면 상단에 고정하고, 금액·저장은 하단에 둔다(C안).** 최초 표시에서 선택된 그룹을 펼치고 나머지는 접어 길이를 줄인다. 이름 줄바꿈, 선택 요약, 저장 버튼의 접근성을 유지한다. 데스크톱도 계정 목록을 별도 내부 스크롤 상자에 가두지 않고 그룹 접기와 검색을 사용한다. 모바일 키보드·확대·긴 이름에서 고정 영역이 내용을 가리지 않도록 아래 Design Pass 6의 조건과 검증 기준을 적용한다.
- `DESIGN.md`의 미색 종이·먹·장부초록, Pretendard, 괘선, 4px 간격 체계를 따른다. 흑백 와이어프레임은 배치 확인용이며 새로운 디자인 시스템이 아니다.

## 마지막 조합의 의미

| 상황 | 동작 |
|---|---|
| 같은 아이템을 다른 계정으로 저장 성공 | 그 거래가 다음 자동 선택의 근거가 된다. |
| 실패한 저장, 입력 중 클릭, 입력 취소 | 저장된 거래가 없으므로 기억을 바꾸지 않는다. |
| 지난달 날짜로 오늘 저장 | 거래일과 무관하게 오늘 입력한 거래가 우선한다. |
| 마지막 거래를 실행취소/삭제 | 삭제된 거래는 조회 대상에서 사라진다. 남아 있는 이전 마지막 거래가 다음 조회 근거가 되며, 없으면 비어 있다. 별도의 숨은 기억은 남기지 않는다. |
| 아이템이 비어 있거나 처음 입력한 이름 | 자동 선택하지 않는다. 새 아이템을 입력할 때 이전 아이템에서 물려받은 자동/유지 계정은 비운다. |
| 마지막 거래의 계정이 보관/그룹/시스템 계정으로 바뀜 | 조합 전체를 자동 적용하지 않고 직접 선택을 안내한다. 더 오래된 유효 조합으로 몰래 되돌아가지 않는다. |
| 마지막 거래가 분할 거래 | 한 쌍으로 축소하지 않는다. 기본 입력에서는 자동 선택하지 않고 분할 입력 안내를 보여준다. |
| 같은 아이템에 여러 과거 조합 | 저장 순서상 마지막 하나만 조회한다. 횟수와 금액은 순위에 쓰지 않는다. |
| 반복 규칙 생성, 개시잔액, 가상 시나리오 거래 | 일반 입력의 기억을 갱신하지 않는다. 실제 장부에서 직접 저장한 거래를 대상으로 한다. |
| 계정 이름 변경/이동 | account_id로 연결하며, 현재 이름·경로로 표시한다. |

### 입력 중 덮어쓰기와 응답 순서

- 아이템 비교 키는 Unicode NFC 정규화와 양 끝 공백 제거로 만든다. 내부 공백·대소문자·구두점·초성·유사어는 합치지 않는다. `점심`과 `점심 회식`은 서로 다른 아이템이다. 기존 표시 문자열은 그대로 보존한다.
- 한글 조합 입력 중에는 조회와 Enter 저장을 실행하지 않는다. 조합 완료 뒤 200ms 안정된 정확한 아이템 키로 조회한다. 빈 아이템은 네트워크 조회를 하지 않는다.
- 각 쪽의 값 출처를 `비어 있음 / 자동 / 직접 선택 / 이전 저장에서 유지`로 구분한다. 자동 응답은 비어 있거나 자동으로 정해진 쪽만 채운다. 사용자가 **현재 입력 건에서** 직접 고른 쪽은 아이템 이름을 바꿔도 보존한다.
- 아이템이 다른 키로 바뀌면 자동·이전 저장 유지 값은 즉시 지우고 조회한다. 현재 입력에서 직접 선택한 값은 유지한다. 자동 응답이 다른 한쪽만 채우는 경우 표시 문구도 그 한쪽에만 적용한다. 같은 계정이 양쪽에 남으면 저장을 막고 직접 변경하게 한다.
- 저장 성공 후 동일한 초안을 정리할 때는 유지된 계정의 수동 잠금을 해제한다. 다음 새 아이템이 이전 건의 직접 선택 때문에 자동 배치를 못 하는 상태가 되지 않도록 한다.
- 조회 요청은 아이템 키·모드·입력 건 식별자를 갖고, 계정 양쪽은 각각 편집 번호를 갖는다. 아이템/모드 변경, 입력 건 저장 후 정리, 취소로 식별자가 달라진 응답은 전체를 무시한다. 계정 한쪽만 직접 변경하면 **전체 조회를 취소하지 않는다**. 응답의 키와 입력 건이 같다면 직접 변경한 쪽은 보존하고 아직 비어 있거나 자동 상태인 반대쪽에는 적용한다. 조회 완료/실패는 최신 활성 요청의 대기 상태만 끝낸다.
- 조회 중에는 아직 검증되지 않은 이전 자동값으로 저장할 수 없다. 양쪽을 직접 선택하면 조회 완료를 기다리지 않고 저장할 수 있다. 조회 실패 시 `이전 계정을 불러오지 못했습니다. 직접 선택해 주세요.`를 인라인으로 보여주며 날짜·아이템·금액·수동 선택을 보존한다.
- Enter는 기본 입력의 아이템·금액 필드에서만 저장한다. 계정 선택기의 Enter/Space는 선택, 그룹 제목에서는 접기/펼치기다. 저장 중에는 중복 제출을 막는다.
- 저장 요청은 제출한 payload와 초안 개정 번호를 캡처한다. 진행 중 필드 편집은 허용하되 추가 저장은 완료까지 막는다. 성공하면 원장·최근 목록은 항상 갱신한다. 금액·메모 비우기, 선택 출처 변경, 포커스 이동은 현재 초안 개정이 제출 당시와 같을 때만 실행한다. 다른 내용을 입력했다면 새 초안을 그대로 두고 저장된 아이템을 토스트로 식별한다. 실패도 제출 건의 실패임을 표시하며 새 초안을 지우거나 포커스를 빼앗지 않는다.
- 부채 잔액 조회 역시 요청 당시 계정 쌍·금액 편집 세대를 확인하고 적용한다. 조회 중 사용자가 금액을 바꾸면 그 값을 보존한다.

## B의 데이터 경계와 기존 기록

새로운 아이템별 기억 테이블을 만들지 않는다. 확정 거래의 계정·posting·저장 순서가 근거다. 서버가 정확한 아이템 키로 **마지막 후보 거래 한 건을 먼저 선택한 뒤** 한 쌍 여부와 계정 유효성을 검사한다. 유효성 조건을 먼저 걸러 오래된 거래를 대신 반환하면 안 된다.

현재 정상 저장 경로는 SQLite가 부여하는 정수 transaction id를 쓰고 수정은 삭제 후 재입력이다. 따라서 남아 있는 거래의 `id DESC`를 저장 순서로 사용한다. 벽시계나 거래일을 쓰지 않는다. 향후 기존 행을 제자리 수정하는 기능을 추가하면 별도 저장 순번 정책을 함께 개정한다.

거래에는 서버가 관리하는 `item_key`와 `entry_origin` 메타데이터를 추가한다. 값은 `user / rule / system / legacy_unknown`이다. 일반 거래 저장은 user, materialize는 rule, 전용 개시잔액 경로는 system이며 시나리오는 scenario_id로 별도 제외한다. API 요청자가 이 출처를 임의 지정하거나 일반 거래에 시스템 계정을 사용할 수 없다. 거래 저장과 메타데이터 저장은 같은 트랜잭션이다. 반복 규칙을 지워도 entry_origin은 남는다. 기존 원장의 정확한 개시잔액 구조는 마이그레이션과 조회에서 계속 system으로 분류한다.

**기존 데이터의 관측된 한계:** `adapters/sqlite/rules.py`가 규칙 삭제 때 source_rule_id를 NULL로 바꾼다. NULL만 보고 기존 거래를 모두 user라고 역추정할 수 없다.

- 마이그레이션은 기존 description에서 item_key를 계산한다. source_rule_id가 있는 거래는 rule, 기존의 정확한 개시잔액 판정에 맞는 거래는 system, 나머지는 legacy_unknown으로 둔다. 원장 postings·날짜·금액·계정 ID는 바꾸지 않는다.
- 정확한 키의 마지막 후보는 actual의 user 또는 legacy_unknown 거래다. 알려진 rule/system 거래는 제외한다. 최신 후보가 legacy_unknown이고 유효한 한 쌍이면 **그 한 쌍만** `이전 기록 확인 후 불러오기`로 표시한다. 자동 적용하지 않는다. 클릭으로 불러오고 새 거래를 정상 저장하면 다음부터는 user 거래가 근거가 되어 자동 선택한다. 후보 여러 개를 표시하는 기능은 추가하지 않는다.
- 확인하기 전에는 기존 기록의 출처가 확실하지 않다는 짧은 설명을 보여준다. 버튼을 누른 것만으로 기존 거래를 user로 재분류하거나 기억을 저장하지 않는다.
- 판정 불가능한 기존 기록을 추정으로 덮지 않는 선택이므로, 업그레이드 직후 일부 아이템은 최초 한 번의 확인이 필요하다. 이 정책은 D5에서 승인했다.
- 적용은 현재 시나리오 기반 작업의 번호 있는 마이그레이션·검증된 백업 패턴을 따른다. 백업/마이그레이션 실패 시 앱 기동을 중단하며, 반복 실행과 기존 DB 복원을 검증한다.

## 조회 계약과 재사용

`GET /api/transaction-input/last-pair?item=...`를 제안한다. 서버가 동일한 정규화 함수를 저장·조회·마이그레이션에 사용한다. 실제 장부 id는 서버에서 고정한다.

- 응답: 정규화된 item_key와 `matched / none / unavailable / legacy_confirmation_required` 중 한 상태. 해당되는 경우 source_transaction_id, debit_account_id, credit_account_id, unavailable_reason을 반환한다. 금액·거래 날짜는 채움 값으로 반환하지 않는다.
- `unavailable` 이유는 분할 거래, 현재 사용 불가 계정, 같은 계정 쌍 등이다. 선택되지 않은 과거 거래 목록은 반환하지 않는다.
- 마지막 거래와 현재 계정의 기장 가능성 판정은 하나의 SQLite 읽기 스냅샷에서 수행한다. 저장 시에는 쓰기 트랜잭션 안에서 다시 확인한다. **현재 `validate_postable_accounts`는 보관 계정을 거부하지 않으므로 이 검사 추가가 구현 범위에 포함된다.** 일반 거래는 존재하는 활성 말단 계정을 사용하고 일반 시스템 계정 기장을 거부한다. 전용 개시잔액 경로와 기존 일반 API의 정확한 개시잔액 구조는 명시적 예외로 유지하며 system 출처로 분류한다. 시스템 계정을 일반 거래로 선택할 수 있게 해 주는 예외가 아니다. 조회 후 계정이 보관/그룹화되면 저장을 거부하고 입력 내용을 유지한 채 해당 계정을 다시 선택하게 한다.
- 마지막 조합에는 `(scenario_id, item_key, id DESC)`, 최근 입력에는 `(scenario_id, id DESC)` 인덱스를 각각 둔다. **두 인덱스 모두 `WHERE posted=1 AND entry_origin IN ('user','legacy_unknown')`인 부분 인덱스**로 만든다. 조회에도 동일한 조건을 명시한다. Eng D3에서 사용자 A로 승인했다. 계정 유효성·posting 수는 인덱스 조건에 넣지 않고 마지막 후보 한 건을 선택한 뒤 검사한다. 따라서 최신 무효 조합을 건너뛰고 옛 조합을 반환하지 않는다. 계정 그룹 여부는 기존 placeholder 또는 자식 존재 판정이다. 전체 원장을 Python으로 가져와 거르는 경로는 사용하지 않는다.
- 입력 화면의 최근 목록도 별도 제한 조회(`GET /api/transaction-input/recent?limit=5`, 최대 20)를 사용한다. actual의 user/legacy_unknown 거래를 id DESC로 가져오며, 알려진 자동·시스템 거래는 제외한다. UI 클릭은 아이템 조회만 실행한다.
- API는 인바운드 어댑터, 앱 서비스는 결과 조립, 순수 Python 정책은 키와 조합 검증, 조회 포트의 SQLite 어댑터는 SQL을 담당한다. 기존 `accountTree`, `isPostable`, `validate_postable_accounts`, `commaInput`, `todayIso`, 저장/실행취소 API를 재사용한다.
- 입력 조회 API 실패가 일반 거래 저장을 막지는 않는다. 저장 성공/실행취소 이후 진행 중인 조회 결과를 무효화한다. 다시 조회했을 때 현재 원장 기준 결과를 사용한다.

| 영역 | 의미 있는 검증 |
|---|---|
| 직접 선택 | 지출·수입·이체·부채 상환을 탭 없이 입력하고 올바른 부호의 postings와 잔액을 검산한다. 일반 입력에 계정 select 상자가 없다. |

| 저장 순서 | 거래 날짜를 과거로 넣은 최신 저장이 우선한다. 날짜 내림차순으로 잘못 선택하는 경우를 잡는다. |
| 기억의 수명 | 저장 실패·취소는 미반영, 최신 거래 삭제/실행취소는 남은 이전 기록으로 재조회, 아무것도 남지 않으면 none이다. |
| 자동입력 제외 | 규칙 생성·규칙 삭제·개시잔액·시나리오 거래가 새 user 기억을 바꾸지 않는다. legacy_unknown은 단 한 번의 명시적 불러오기 경로를 거친다. |
| 계정 변경 | 보관·그룹화·이름 변경·이동·동명 계정 경로를 처리한다. 최신 조합이 무효여도 옛 유효 조합을 자동으로 대신 쓰지 않는다. |
| 입력 경쟁 | A 아이템의 느린 응답이 B를 덮지 않는다. 한쪽 수동 선택 중 도착한 응답은 다른 쪽만 채운다. 금액 변경·한글 IME·저장 중 재입력에서도 값과 포커스를 보존한다. 오래된 성공/실패 응답으로 새 초안을 초기화하지 않는다. |
| 예외·호환 | 빈 아이템, 긴 이름, 공백/NFC, 분할 거래, 같은 계정 쌍, 네트워크 실패, 부채 잔액 불러오기, 실행취소, 빈/부분/완성 기본·분할 초안의 왕복과 불가 전환 시 보존을 검증한다. |
| 분할 행 보존 | 균형 잡힌 두 행 뒤에 금액만 있거나 계정만 있는 행을 추가하면 POST 없이 해당 행 오류를 표시한다. 완전히 빈 추가 행은 허용하고, 불완전 행을 완성하거나 지우면 저장할 수 있다. `0`을 입력한 행을 빈 행으로 취급하지 않는다. |
| 조회 비용 | 큰 합성 원장에서 서버가 전체 거래 목록을 만들지 않음을 SQL/결과 크기로 검증한다. 후보 조회는 최대 4 SQL문, 최근 5건은 최대 3 SQL문으로 고정한다. 계정 수마다 별도 SQL을 실행하지 않는다. |
| 접근성 | 계정은 의미 있는 단일 선택 컨트롤로 구현한다. 레이블·선택 상태·키보드 이동·접힌 그룹·검색 결과 없음·초점 표시·모바일 44px 클릭 영역을 검증한다. |

구현 시 기존 E2E의 selectOption 기반 거래 입력 검증을 새 클릭 흐름으로 교체하고, pytest와 Playwright의 각 시나리오는 독립된 데이터를 준비한다. 동작/디자인 변경 후 `cd backend && uv run pytest`, `cd frontend && npm run e2e`, 프론트 빌드를 실행한다. 현재 산출물은 설계 문서와 와이어프레임이며 제품 테스트를 실행했다는 의미가 아니다.

Eng review의 상세 [검증 계획과 실행 경로 도식](transaction-input-test-plan.md)에 Python 17개·프론트 17개 요구사항 묶음, 기존 테스트 근거, 실패 시 사용자 복구 동작을 연결했다. 이는 계획한 검증 범위이며 구현된 테스트 개수나 측정한 커버리지가 아니다. 신규 프레임워크 없이 pytest와 Playwright를 사용한다.

## 적용 순서와 배포

1. 출처/item_key 마이그레이션과 저장 경로 보존, 마지막 한 건 조회 및 오류 상태를 Python 테스트로 고정한다.
2. 공통 계정 클릭 선택기와 기본 입력, 분할 입력 접근, 부채 잔액 수동 채우기를 조립한다.
3. 아이템 조회 상태·수동 선택 보호·최근 입력을 연결하고 실제 원장 대신 격리한 DB로 입력 흐름을 검증한다.
4. 모바일/키보드·회귀 테스트 후 기존 로컬 실행 및 릴리스 경로로 제공한다. 별도 앱·서비스·외부 모델은 필요 없다.

현재 작업 트리에는 진행 중인 시나리오 기반 리팩터링이 있다. 이 설계 작업은 해당 코드에 손대지 않으며, 구현은 그 기반과 호환되는 별도 변경 단위로 진행한다. 과거의 단일 `api.py`/`api.ts` 경로를 전제로 구현하지 않는다.

## Engineering data flow

```text
USER SAVE / OPENING / RULE MATERIALIZATION / SCENARIO WRITE
  trusted caller selects origin; shared policy computes item_key
       |
       v
  existing write boundary / BEGIN IMMEDIATE
    -> current account checks appropriate to this entry point
    -> _insert_txn(metadata + postings -> posted=1)
    -> caller commit, or all rollback

ITEM LOOKUP
  composition ends -> debounce -> GET(item)
    -> existing request read transaction
    -> eligible partial index -> highest surviving id, LIMIT 1
    -> that candidate's postings + current account eligibility
    -> none | unavailable | legacy confirmation | matched
    -> guard request key / mode / draft identity
    -> apply only sides still eligible; preserve manual edits

DRAFT STATE
  fields + mode + side origins + draft identity + edit revisions
    item changed -> clear auto/retained sides, keep manual sides
    manual side edit -> lock that side, leave other side eligible
    save submitted -> snapshot payload/revision, block duplicate save
      error -> preserve draft, identify failed submission
      success -> refresh ledger/recent, invalidate prior lookups
        revision unchanged -> clear amount, retain values, focus
        newer revision     -> preserve new values and focus
```

`transactionInputState.ts`에는 이 초안 전이의 핵심 도식을 주석으로 남긴다. `_insert_txn`/materialization의 기존 원자성 주석에는 메타데이터도 같은 경계에 포함됨을 반영하고, 조회 어댑터에는 **후보 선택 → 유효성 검증** 순서를 명시한다. 새로운 저장 서비스 계층이나 외부 캐시는 필요 없다.

일반 거래의 생성 순서는 surviving id로 판단한다. 기존 계정의 직접 기장을 하위 계정으로 재분류하는 `reclassify_direct`는 postings를 바꾸지만 새 입력 사건은 아니므로 id와 origin을 유지한다. 이후 조회는 그 거래의 현재 postings를 읽는다. 새로운 사용자 거래 수정 기능은 이 경계와 함께 저장 순번 정책을 다시 검토한다.

## 성능 검토 근거와 구현 기준

로컬 Python 표준 SQLite의 메모리 DB에 오래된 기억 대상 5건과 같은 아이템의 더 최신 rule 거래 200,000건을 만들었다. 동일한 `WHERE scenario_id=1 AND posted=1 AND entry_origin IN ('user','legacy_unknown')`, `ORDER BY id DESC`, `LIMIT 1/5`로 비교했다. 마지막 조합에는 정확한 item_key 조건도 적용했다. 실제 장부나 제품 API는 사용하지 않았다.

| SQL 실험 | 기존 전체 인덱스 | 승인한 부분 인덱스 |
|---|---:|---:|
| 마지막 조합, SQLite VM 실행 단계 | 1,600,037 | 46 |
| 최근 5건, SQLite VM 실행 단계 | 1,600,098 | 56 |
| 최근 정렬 임시 B-tree | 발생 | 없음 |
| 반환 transaction IDs | 마지막 `[5]`, 최근 `[5,4,3,2,1]` | 동일 |

VM 단계는 데이터 탐색 비용을 비교한 관측치이며, 제품 API 지연·사용자 장부 크기·절대 성능 보장을 뜻하지 않는다. 실제 구현에서는 B17로 계측을 다시 수행한다. 인덱스는 다음 두 구조로 고정한다.

```sql
CREATE INDEX idx_txn_input_item
ON transactions(scenario_id, item_key, id DESC)
WHERE posted=1 AND entry_origin IN ('user','legacy_unknown');

CREATE INDEX idx_txn_input_recent
ON transactions(scenario_id, id DESC)
WHERE posted=1 AND entry_origin IN ('user','legacy_unknown');
```

조회는 후보 한 건을 먼저 제한한다. 분할 여부 확인에 모든 postings를 응답으로 전송하지 않고, 두 행 초과를 판별할 수 있는 제한 읽기 또는 집계를 사용한다. 최근 입력은 먼저 최대 20개 transaction ID를 정한 뒤 요약을 일괄 조회한다. 무제한 분할 행을 최근 카드 응답에 그대로 담지 않는다. 계정마다 추가 SQL을 실행하지 않으며, 처음 승인한 후보 최대 4 SQL문/최근 5건 최대 3 SQL문 예산을 검증한다. 자동 생성 거래가 대부분인 합성 데이터에서도 승인 인덱스 사용과 최근 조회의 정렬 제거를 확인한다. 새 결과 캐시·기억 테이블·원장 전체 로드는 도입하지 않는다.

## Worktree parallelization strategy

이 표는 향후 구현 분담 계획이다. 이 검토에서 worktree를 만들거나 구현 에이전트를 실행하지 않았다. 기반 시나리오 작업이 정리된 별도 변경 단위에서 시작한다.

| 단계 | 모듈 | 의존성 |
|---|---|---|
| 0. API 상태·초안 이벤트·검증 기준 공유 | 설계/검증 문서 | 이 검토의 승인 결정 |
| A. 메타데이터·마이그레이션 → 조회 API | `backend/moneymap/`, `backend/tests/` | 0 |
| B. 계정 선택기 → 초안 전이·분할 검증 | `frontend/src/views/`, `frontend/src/api/`, `frontend/e2e/` | 0, API 응답 예시 |
| C. 실제 서버 연결 → 전체 회귀·모바일 QA | frontend와 통합 검증 | A와 B 완료 |

A와 B는 두 독립 lane으로 병렬 가능하며 각 lane 내부는 같은 모듈을 건드리므로 순차 작업한다. C는 둘을 합친 뒤 수행하는 세 번째 lane이다. 프론트 파일을 여러 lane에서 동시에 수정하지 않는다. 이 계획의 lane 수는 3, 병렬 시작은 2, 후속 순차 통합은 1이다.

### Pass 1 — 정보 구조 (8/10 → 9/10)

가장 먼저 볼 세 가지는 이번 거래의 입력값, 선택한 두 계정, 저장 동작이다. 메모는 아이템 아래의 보조 입력이다. 내비게이션은 기존 앱 셸을 재사용한다.

```text
데스크톱
  기존 사이드바 | 날짜       아이템       금액
               |            메모
               | 아이템 조회 상태
               | 차변 계정 선택 | 대변 계정 선택
               | 검산 → 분할 입력 / 저장 → 최근 입력

모바일
  기존 3열 내비게이션 → 날짜·금액 → 아이템 → 메모
  아이템 조회 상태
  선택한 차변·대변 요약 (계정 영역부터 상단 고정)
  차변 계정 선택 → 대변 계정 선택 → 검산·분할 입력·최근 입력
  금액·저장 (하단 고정)
```

메모를 넣는 위치와 선택 여부는 사용자 요청으로 확정했다. **D3에서 저장 성공 후 동일 초안의 메모를 비우는 동작을 승인했다.** 기존 초안 개정 번호 검사에 메모도 포함하여 저장 중 새로 작성한 내용을 보호한다. 분할 입력은 각 행의 계정 버튼으로 **편집 중인 행의 선택기 하나만** 해당 행 바로 아래에 펼친다. 다른 행을 누르면 선택기를 옮기고, 선택/닫기 뒤 해당 행 계정 버튼으로 초점을 돌린다. 선택하지 않고 닫아도 기존 계정·금액·메모를 보존한다. 모든 행에 전체 트리를 반복하거나 행마다 탭을 만들지 않는다. 이는 고정된 클릭 선택과 과도한 탭을 피하려는 기존 방향의 상세화다.

### 메모 추가에 따른 엔지니어링 보완 범위

현재 `domain/transaction.py::Transaction`, `routers/transactions.py::TransactionIn`, SQLite transactions 테이블, 프론트 `createTransaction`에는 메모 필드가 없다. 입력칸만 추가하면 저장되지 않으므로 다음을 구현 범위에 추가한다.

- 거래의 `memo: str = ""` 필드, 일반 저장 요청·응답, 도메인·SQLite 저장/읽기, 프론트 타입을 연결한다. SQLite에는 `memo TEXT NOT NULL DEFAULT ''`를 추가한다. 기존 거래와 메모를 보내지 않는 기존 호출은 빈 메모로 호환한다. 별도 메모 엔티티/테이블은 만들지 않는다.
- 기본·분할 초안이 같은 거래 메모를 공유한다. 입력 전환과 실패 시 작성 내용을 보존하고, 늦은 저장 응답의 초안 보호 대상에 메모 편집도 포함한다.
- 저장된 메모를 거래 내역에서 다시 읽을 수 있어야 한다. 사용자 입력은 일반 텍스트로 표시하고 줄바꿈을 보존한다. 메모로 새로운 계정 후보나 기억 키를 만들지 않는다.
- 마이그레이션·기존 DB 호환, 저장 후 재조회·새로고침, 여러 줄 메모, 기본/분할 전환, 실패·느린 응답 중 새 메모 보호를 검증 계획에 추가한다. D3에 따른 저장 후 초기화와 새 메모 보존을 함께 검증한다.

기존 Eng review는 메모가 없던 범위를 검토했다. 그 결론을 메모 추가 범위의 검증 완료로 확대하지 않는다. 메모는 같은 거래 insert에 포함하며 기존 commit 경계를 유지한다. 기존 description에서 메모를 추정하지 않고 기존 행은 빈 값으로 둔다. 마지막 조합 응답에는 메모를 채움 값으로 싣지 않는다. 최근 입력 요약에서도 전체 메모를 전송하지 않으며, 저장한 메모는 기존 거래 내역에서 접을 수 있는 `메모 보기`로 읽는다. 이 보완은 설계 수준으로 구체화했으며, 메모 추가를 포함한 별도 Eng review가 실행되었다고 주장하지 않는다.

선택기는 각 쪽/편집 행마다 의미 있는 단일 선택 그룹이다. Tab으로 검색과 그룹 제목, 라디오 그룹에 접근한다. 라디오에서 화살표로 보이는 활성 계정 사이를 이동·선택하고 Space로 선택한다. Enter도 명시적으로 선택 처리하여 form 제출로 전파하지 않는다. 그룹 제목은 native details/summary를 재사용하며 Enter/Space로 접고 펼친다. 접힌/필터로 숨긴 계정에는 초점이 가지 않는다. 선택 항목이 검색에서 숨겨졌을 때는 첫 보이는 항목이 그룹의 키보드 진입점이 되되, 진입점 변경만으로 선택을 바꾸지 않는다. 결과가 없으면 `검색어 지우기`로 돌아간다.

검색 레이블은 화면에도 남긴다. 그룹과 라디오에는 차변/대변·계정 전체 경로를 제공한다. 자동 선택 상태는 한 곳의 `role=status`/polite 안내로 전달하며, 조회 완료가 포커스를 이동시키지 않는다. 위아래에 반복하는 요약으로 같은 내용을 중복 낭독하지 않는다. 저장 오류는 `aria-invalid`와 연결된 오류 문구로 제공하고, 현재 초안의 직접 제출 검증 실패에만 첫 오류로 이동한다. 늦은 응답은 초점을 옮기지 않는다.

모바일 계정·그룹·검색어 지우기·행 열기/삭제·저장은 최소 44×44px이다. 포커스는 기존 accent의 2px 외곽선으로 표시한다. hover/focus 100ms, 상태 전환 150–250ms 이내이며 입장 애니메이션은 없다. `prefers-reduced-motion`에서는 불필요한 전환·부드러운 스크롤을 끈다. 기본→분할→기본에서는 동일 초안을 유지하고, 전환 뒤 해당 모드의 제목/첫 편집 컨트롤로 초점을 보낸다.
