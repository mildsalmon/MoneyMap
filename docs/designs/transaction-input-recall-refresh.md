## 문제와 근거

사용자는 아이템 입력에 따른 차변·대변 자동 채움이 페이지 로딩 후 한 번만 동작한다고 보고했다.
아이템 조회는 다시 실행되지만 `applyPair()`가 이미 값이 있는 모든 계정을 보호한다.
상태 함수 재현에서 A 조합을 자동 선택한 뒤 B 입력, 저장 후 C 입력 모두 A 계정이 유지됐다.
기존 브라우저 테스트 2개도 이 보존 정책을 검증한다. 조회 누락이 아니라 선택 출처를 구분하지 않는 적용 정책 문제다.

## 확정한 결정

- D1 A: 빈 계정·자동 선택(auto)·이전 거래에서 유지된 계정(retained)은 새 아이템의 사용 가능한 추천으로 갱신한다. 현재 거래에서 직접 선택한 계정(manual)은 차변·대변별로 보호한다.
- D2 A: 추천 없음, 사용 불가능한 조합, 조회 실패에는 계정을 지우지 않는다. 기존 선택을 유지했다는 안내를 표시한다.
- Eng D1 A (2026-09-20): 추천 조회는 5초 후 대기를 종료한다. 기존 입력을 보존하고, 유효한 계정이면 저장을 허용한다. 기존 안내 영역의 “계정 추천 다시 조회” 버튼으로 추천만 재조회하며 거래 저장은 재시도하지 않는다.
- Eng D2 A (2026-09-20): 저장 허용 여부를 공통 순수 함수에서 판단한다. 버튼 활성화와 실제 저장 처리에서 같은 함수를 사용하고, 저장 직전 최신 초안과 조회 상태로 다시 검증한다. 두 경로의 조건 불일치를 테스트한다.
- Eng D3 A (2026-09-20): 저장 실행취소가 성공해도 작성 중인 계정 값과 선택 출처는 유지한다. 실행취소로 시작된 조회와 그 이전의 늦은 응답은 현재 선택을 덮지 않는다. 이후 아이템 변경·최근 아이템 선택·명시적 추천 재조회에서는 기존 자동/수동 보호 규칙으로 적용한다.
- Eng D4 A (2026-09-20): 화면 이동·재진입 후에도 실행취소 보존 정책을 지킨다. `App`에서 실행취소에 따른 갱신 원인/세대를 현재 입력 화면에 전달한다. 이전 화면의 지역 상태에 의존하지 않는다. 실행취소 요청 중 이동했다가 응답을 받는 경우도 테스트한다.
- 기존 거래 수정 설계의 “선택 출처와 무관하게 덮지 않는다”를 신규 입력의 유효 추천 적용에 한해서 대체한다. “자동 초기화하지 않는다”와 수정 화면의 자동 추천 금지는 유지한다.
- 목표는 재입력 클릭을 줄이되 직접 선택을 잃지 않는 것이다. 자동 분류 학습, 새 DB, 계정 재분류, UI 재배치는 범위 밖이다.

## 비교한 접근

- A 선택 출처별 적용: 선택됨. 기존 source/revision/epoch와 마지막 조합 API를 재사용하는 작은 변경으로 수동 보호와 반복 입력을 함께 충족한다.
- B 모든 계정 덮어쓰기: 직접 선택까지 바뀌므로 제외했다.
- C 별도 적용 버튼: 매번 클릭해야 하므로 제외했다.
- 자동화 실패 시 선택 초기화: 사용자가 D2에서 기존 값 유지로 결정했다.

## 동작 계약

| 상황 | 차변·대변별 처리 |
|---|---|
| 사용 가능한 추천 + empty/auto/retained | 현재 아이템 응답임을 검증한 후 해당 쪽 갱신 |
| 현재 거래에서 직접 선택 | 같은 값을 다시 눌렀어도 manual로 보호 |
| 조회 도중 직접 선택 | 계정별 revision이 달라진 쪽은 늦은 응답 무시 |
| 추천 없음·분할/보관 등 사용 불가·조회 실패 | 기존 값과 선택 출처 유지, 이유 안내 |
| 아이템을 빈 값으로 변경 | 조회 취소, 계정 보존, 기존 빈 아이템 입력 허용 |
| 동일 초안 저장 성공 | 기존 필드 비우기 유지, 계정은 retained로 전환하여 다음 입력에서 갱신 가능 |
| 저장 중 더 최신 초안 작성 | 최신 초안·manual 보호를 유지하고 이전 저장의 초기화를 적용하지 않음 |
| 저장 실행취소 성공 | 현재 계정과 출처 유지, 실행취소에 따른 추천 재적용 없음 |
| 분할 입력·거래 수정 | 기존 동작 유지, 자동 덮어쓰기 없음 |

- 아이템 정규화, 요청 취소, 아이템 키·epoch 검증을 유지한다. A→B→A에서도 첫 A 응답을 마지막 A에 적용하지 않는다.
- 최근 입력에서 아이템을 다시 고르는 동작에도 같은 계정별 보호 정책을 적용한다.
- 출처 확인이 필요한 과거 이관 기록은 기존 명시적 확인 버튼을 유지한다. 확인 전에는 자동 적용하지 않고, 확인 시에도 현재 manual 선택을 덮지 않는다.
- 자동 추천은 계정만 바꾼다. 날짜·금액·메모·태그는 바꾸지 않는다.
- 유지한 한쪽 계정과 새 추천의 다른 쪽이 같아지는 경우 임의로 수동 선택을 바꾸지 않는다. 기존 검산으로 저장을 막고 사용자가 수정하도록 안내한다.

## 저장과 조회의 경합

Office-hours D3에서 저장 대기 보호를 승인했고, Eng D1에서 5초 제한과 실패 복구 동작을 확정했다.
아이템 변경 직후(debounce 대기 포함)부터 현재 아이템의 추천을 기다리는 동안 갱신 대상(auto/retained/empty)이 남아 있으면 저장을 잠시 막는다.
그렇지 않으면 이전 아이템의 계정으로 저장된 직후 화면만 새 추천으로 바뀔 수 있다.
양쪽 모두 직접 선택하면 추천 대기를 이유로 저장을 막지 않는다.
추천 없음 또는 조회 실패로 끝나면 보존한 계정이 유효한 경우 저장할 수 있다.
무응답 조회가 저장을 영구 차단하지 않도록 실제 추천 요청 시작부터 5초로 제한한다. 기존 200ms debounce 대기도 저장 제한에는 포함한다.
시간 초과·조회 실패 시 입력과 계정 선택 출처를 보존하고 대기를 종료한다. 보존한 계정이 유효하면 저장할 수 있다.
기존 안내 영역에 “계정 추천 다시 조회” 버튼을 표시한다. 재조회는 현재 아이템의 새 요청으로 실행하고, 같은 저장 대기·5초 제한·수동 선택 보호 규칙을 적용한다.
실행취소 성공 후에도 같은 버튼으로 사용자가 추천을 다시 요청할 수 있다. 실행취소 때문에 조회를 생략한 상태는 대기 중이 아니라 선택 유지로 표시한다. 단순히 응답 적용만 막고 저장을 영구 대기로 남기지 않는다.
화면을 넘어 유지되는 알림의 실행취소는 `App`의 갱신 정보에 실행취소 원인/세대를 기록한다. 현재 마운트된 입력 화면이 이 정보를 소비해 이전 추천 요청을 무효화하고, 현재 계정 값/source를 보존한 종료 상태로 전환한다. 실행취소를 시작한 과거 화면의 `alive`나 epoch만으로 보호하지 않는다. 기존 `refresh()` 호출자는 그대로 동작하도록 호환성을 유지한다. 사용자가 이후 아이템을 변경하거나 명시적으로 재조회하면 새 요청 소유권으로 정상 적용한다. 실행취소 표시를 영구 전역 차단 플래그로 남기지 않는다.
시간 제한 이후 도착한 응답은 요청 세대/취소 신호로 무효화한다. 아이템 변경·화면 이탈에 따른 정상 취소와 시간 초과를 구분하고, 시간 초과는 반드시 종료 상태와 안내를 남긴다. 거래 저장 요청의 자동 재시도는 추가하지 않는다.

저장 가능 판단은 기존 검산 결과, 저장 중 여부, IME 조합 중 여부, 현재 아이템의 조회 대기 여부, 계정별 선택 출처를 입력으로 받는 공통 순수 함수로 모은다. 화면의 저장 버튼 두 개와 실제 저장 처리에서 같은 규칙을 사용한다. 실제 저장에서는 `current.current`의 최신 초안 기준으로 조회 소유권과 검산을 다시 계산한다. 렌더 시점의 `lookupPending`만 재사용하지 않는다. 이 함수는 신규 입력 전용이며 수정 화면에 추천 대기 조건을 추가하지 않는다.

기존 폼·계정 트리·선택 요약을 유지한다. 새 화면, 모달, 레이아웃은 만들지 않는다.
기존 안내 영역에서 “양쪽 자동 적용 / 한쪽 적용·직접 선택 보호 / 기존 선택 유지 / 조회 실패”를 구분한다.
자동으로 기존 값을 교체했는데도 “유지합니다”라고 표시하지 않도록 실제 적용 결과와 안내를 함께 갱신한다.
조회 중에도 입력 및 직접 계정 선택은 가능하다. 저장 제한 이유는 안내 영역에 표시한다.
시각 스타일은 DESIGN.md를 따른다. 이 단계에서는 별도 시각 시안과 외부 시장 조사를 실행하지 않았다.

2026-09-20: 사용자가 HTML 시안 확인 후 개발을 요청하여 추천안 A(상태 안내 + 저장 버튼 근처 대기 이유)를 기준으로 구현한다. 이미지 생성은 API 키 부재로 실행되지 않았고 HTML 비교로 대체했다. 디자인 스킬의 나머지 공식 검토 단계는 완료로 기록하지 않는다.
기존 안내 영역·보조 버튼·선택 요약을 유지하며, 재조회 버튼은 오류·시간 초과·실행취소 보존 상태에 표시한다. 조회 중에는 중복 재조회 버튼을 표시하지 않는다. 저장 대기 이유는 기존 저장 힌트에 표시하고 검산 오류를 우선한다. 조회가 끝나면 기본 저장 안내로 복귀한다. 재조회 버튼 최소 높이는 44px이며 기존 flex-wrap으로 작은 화면에서도 줄바꿈한다.

## 구현·검증 계획

1. 기존 source/epoch/revision으로 적용 자격과 응답 무효화를 표현한다. 생성·수정이 공유하는 함수의 영향 범위를 확인한다.
2. 상태 테스트: 연속 A/B/C, 한쪽·양쪽 manual, 저장 후 retained, 추천 없음·오류, 오래된 응답, 동일 계정 충돌, 이관 확인, 분할 전환.
3. 브라우저 테스트: 실제 라디오 선택과 안내, 입력→저장→다음 입력, 조회 실패, IME, 늦은 저장 완료. debounce/느린 조회 중 저장 차단과 직접 선택을 통한 제한 해제, 요청 시작 후 5초 시간 제한·재조회·시간 초과 후 늦은 응답 무효화도 검증한다. 재조회가 거래 저장 요청을 보내지 않는지 확인한다.
4. 기존 수정 화면에서 자동 추천을 호출하지 않는 검증과 ID·분개 보존 검증을 유지한다.
5. 격리 DB/서버에서 전체 pytest, 전체 E2E, frontend build, 코드 리뷰와 실제 브라우저 QA를 실행한다. 실제 원장에 테스트 거래를 쓰지 않는다.
6. 문서와 TODO를 갱신하고 별도 변경 단위로 커밋·PR을 준비한다. 리뷰 결과와 실행 증거를 확인하고 별도 승인 범위에 따라 머지한다.

## 기술 검토: 재사용과 범위

- 범위 검토: 기존 상태 함수와 입력 화면, 관련 테스트를 중심으로 진행한다. 새 서비스·DB·API는 필요 없다.
- `transactionInputState.ts`: 선택 출처, 계정별 revision, 아이템별 epoch, 검산을 재사용한다. 자동 적용 자격과 신규 입력 저장 판단만 수정·추가한다.
- `TxnInput.tsx`: 기존 200ms debounce, AbortController, 생존 여부 검사, API, 안내 영역을 재사용한다. 조회 완료·실패·시간 초과·실행취소 보존 상태를 명확히 구분한다.
- `TransactionForm.tsx`: 기존 저장 이벤트와 버튼 인터페이스를 재사용한다. 수정 화면은 추천을 호출하지 않는다.
- `App.tsx`: 기존 전역 갱신 정보에 실행취소 원인/세대를 추가해 현재 입력 화면으로 전달한다. 계정/최근 내역 등 다른 데이터 갱신을 막지 않으며, 새로운 전역 상태 라이브러리는 도입하지 않는다.
- 성능: 신규 자동 재시도나 폴링·캐시 계층을 추가하지 않는다. 기존 조회량의 상한은 입력 debounce로 유지하고 명시적 재조회만 추가한다. 성공·실패·취소·화면 이탈에서 타이머를 정리한다. DB 쿼리 변경 없음.
- 공식 근거: React의 effect cleanup은 요청 취소 또는 오래된 결과 무시를 권고한다. https://react.dev/learn/synchronizing-with-effects#fetching-data

## 테스트 흐름과 실패 대응

아래는 구현 전 테스트 요구사항이며 실행 통과를 뜻하지 않는다. [기존]은 관련 테스트를 읽어 확인했고, [추가/수정]은 이번 구현에서 작성한다.

```text
아이템 변경 / 최근 아이템 / 명시적 재조회
  -> 현재 조회 소유권 발급 -> 200ms 대기 -> API (5초 제한)
     |-> 유효 추천 -> auto/retained/empty 갱신 [추가/수정]
     |               manual/revision 변경 쪽 보호 [기존+확장]
     |-> 없음/사용 불가/오류 -> 값+출처 보존 [기존+확장]
     |-> 시간 초과 -> 대기 종료, 입력 보존, 재조회 [추가]
     `-> 이전 요청/아이템/모드/화면 응답 -> 무시 [기존+확장]
저장 시도 (버튼/Enter/저장 후 대시보드)
  -> 최신 초안 + 공통 판단
     |-> 대기 & 자동 갱신 대상 존재 -> 요청 0회 [추가]
     |-> 양쪽 manual / 조회 종료 -> 검산 통과 시 저장 [추가/기존]
     `-> IME/중복 제출/검산 실패 -> 요청 0회 [기존+확장]
저장 완료 -> 같은 초안: retained / 새 초안: 입력 보존 [기존+확장]
실행취소 -> 계정+출처 유지 -> 명시적 재조회에서만 적용 [기존+확장]
거래 수정 -> 추천 호출 0회, 거래/분개 ID 보존 [기존]
```
