## Problem Statement

Implementation and verification: [account-ordering verification](../verification/account-ordering.md).

MoneyMap은 계정마다 형제 범위의 영속적인 `position`을 저장하고 모든 계정 트리를 그 값으로 정렬한다. 그러나 사용자가 이 순서를 직접 바꿀 수단은 없다. 과거 거래 이관으로 계정과목이 늘어난 현재 상태에서는 자주 쓰는 계정을 원하는 위치에 둘 수 없고, 계정 관리·거래 입력·시나리오 편집기에서 같은 탐색 비용이 반복된다.

이번 기능은 기존 계정의 회계 의미나 계층을 바꾸지 않고, 같은 부모 아래 형제 계정의 표시 순서만 사용자가 직접 정하게 한다.

## What Makes This Cool

- 계정 관리에서 한 번 정리한 순서가 거래 입력과 시나리오 규칙까지 즉시 이어진다.
- 사용자가 만든 계정 트리가 앱 전체의 일관된 탐색 지도 역할을 한다.
- 데스크톱에서는 손잡이를 바로 끌고, 드래그하기 어려운 환경에서는 위·아래 버튼으로 같은 결과를 만든다.
- 순서 변경은 즉시 저장되지만 한 번의 `실행 취소`로 되돌릴 수 있다.

## Constraints

- 로컬 단일 사용자 FastAPI + SQLite + React 앱이며, 프론트와 백엔드는 같은 릴리스로 배포한다.
- `accounts.position`과 `(type, COALESCE(parent_id, -1), position)` 고유 인덱스가 이미 존재한다.
- 계정 `version`을 이용한 낙관적 잠금이 이미 계정 설정 저장에 적용돼 있다. 낙관적 잠금은 사용자가 본 버전이 최신인지 저장 직전에 확인해 다른 화면의 변경을 덮어쓰지 않는 방식이다.
- `accountTree()`가 계정 관리·거래 입력·시나리오 편집기의 공통 정렬 함수다.
- 계정 목록은 잔액·개시잔액·설정·보관 작업이 함께 있는 밀도 높은 표다. 전체 행을 드래그 영역으로 만들지 않는다.
- 보관 계정은 활성 목록에서 숨지만 `position`을 유지하며, 복원 후에도 기존 위치를 보존해야 한다.
- `DESIGN.md`의 종이 원장 모더니즘, 32px 데스크톱 행, 44px 모바일 주 조작, 100~250ms 기능성 모션 범위를 따른다.
- 계정 계층 이동, 계정 유형 변경, 화면별 독립 순서, 자동 정렬 규칙, 숫자 단축키는 범위 밖이다.
- 여러 형제 범위의 계정 mutation을 동시에 진행하는 기능은 범위 밖이다. 이번 버전은 하나의 계정 mutation만 허용하고, 범위별 병렬 처리는 실제 필요가 확인되면 후속 TODO에서 다룬다.

## Premises

1. 재정렬은 `position`만 변경한다. `account_id`, `parent_id`, 거래, 반복 규칙, 개시잔액과 잔액은 변경하지 않는다.
2. 동일한 `type`과 `parent_id`를 가진 활성·비시스템 형제 계정끼리만 순서를 바꾼다.
3. 하나의 저장 순서를 모든 계정 트리 소비 화면이 공유한다.
4. 데스크톱 포인터 환경은 전용 손잡이 드래그를, 모바일과 키보드는 위·아래 버튼을 제공한다.
5. 드롭 또는 버튼 이동 직후 저장하고 최신 성공 변경 하나에 실행 취소를 제공한다.
6. 저장 실패나 버전 충돌이 발생하면 서버의 최신 순서를 다시 읽어 화면을 복구한다.
7. 보관·시스템 계정의 위치는 재정렬 중 수정하지 않는다.

## Cross-Model Perspective

독립 Codex 검토는 이 기능의 핵심을 “한 번 정한 순서가 앱 전체의 조작 언어가 되는 것”으로 봤다. 구현은 드래그보다 형제 전체 순서 API와 저장소 검증을 먼저 만들고, 접근 가능한 위·아래 버튼을 연결한 뒤 드래그를 추가하라고 권했다.

또한 dnd-kit의 저수준 drag/drop 요소가 손잡이·포인터 활성화·충돌 감지·드래그 오버레이를 제공하지만, MoneyMap이 직접 책임져야 할 부분은 형제 범위 검증, 버전 충돌, 보관 위치 보존, 실행 취소와 앱 전체 순서 전파라고 정리했다. 상위 계정 숫자 단축키 아이디어는 현재 범위를 넓히고 기존 입력 단축키와 충돌할 수 있어 후속 아이디어로 남긴다.

## Approaches Considered

- **단일 계정 이동 API + 브라우저 기본 드래그:** 가장 작지만 형제 전체의 동시 변경을 검증하기 어렵고 브라우저별 드래그 동작을 직접 다뤄야 해 기각했다.
- **형제 전체 순서 API + dnd-kit:** 선택. 기존 `position`·`version` 기반에서 원자성, 복구 가능성, 드래그 품질을 함께 확보한다.
- **형제 전체 순서 API + 직접 만든 Pointer Events 드래그:** 의존성은 없지만 제품 가치와 무관한 포인터·스크롤·충돌 엔진을 직접 유지해야 해 기각했다.

## Recommended Approach

### User flow

계정 행의 계정명 앞에 재정렬 손잡이를 둔다. 데스크톱의 정밀 포인터 환경에서 손잡이를 일정 거리 이상 움직이면 드래그를 시작한다. 전체 행, 계정명, 설정·보관·개시잔액 컨트롤에서 시작한 포인터 동작은 드래그로 해석하지 않는다.

드래그 중에는 같은 형제 범위의 계정 앞·뒤에만 삽입선을 표시한다. 다른 부모, 다른 유형, 자기 후손과 보관 영역은 드롭 대상이 아니다. 잘못된 범위 위에서는 삽입선을 표시하지 않고 놓아도 저장하지 않는다.

드롭하면 로컬 목록을 즉시 새 순서로 보여주고 서버에 저장한다. 성공하면 응답의 최신 계정과 버전으로 로컬 상태를 교체하고 `‘외식’ 순서 변경됨 · 실행 취소` 토스트를 표시한다. 서버가 거부했다고 확정할 수 있는 실패는 변경 전 snapshot을 즉시 복원한 뒤 최신 목록을 읽는다. timeout·연결 끊김처럼 commit 여부를 알 수 없는 실패는 임의로 성공이나 실패로 단정하지 않고 아래의 `reconciling` 절차로 판정한다.

그룹 계정을 옮길 때 화면상의 이동 단위는 그 계정과 모든 후손, 연결된 `(미분류)` 가상 행을 포함한 하나의 블록이다. 저장 결과에서는 그 그룹뿐 아니라 새 슬롯이 달라진 모든 직접 형제의 `position`과 `version`이 바뀔 수 있다. 후손의 `position`, `version`, `parent_id`는 바뀌지 않는다. 열린 계정 설정, 새 분류 초안, 소분류 초안 또는 계정 관련 저장 작업이 있으면 재정렬을 시작하지 않는다. 재정렬 중에는 입력값을 보존하되 계정 변경 컨트롤을 잠시 비활성화한다.

### Canonical reorder scope

하나의 `scope_key`는 `(type, parent_id)`다. `parent_id: null`은 해당 유형의 최상위(root) 범위를 뜻하는 유효한 값이다. 아래 세 용어를 구현·테스트·오류 메시지에서 구분한다.

- `db_scope_rows`: 같은 `scope_key`에 속한 DB의 모든 행. 보관·시스템 계정도 포함한다.
- `eligible_siblings`: `db_scope_rows` 중 `archived=0 AND is_system=0`인 직접 형제. 요청 ID 집합은 이것과 정확히 같아야 한다.
- `preserved_active_slots`: 재정렬 직전 `eligible_siblings`가 차지한 `position` 집합을 오름차순으로 정렬한 값. 원하는 ID 순서에 이 슬롯만 다시 배정한다.

- 요청 ID 누락, 중복, 다른 범위 ID 포함을 허용하지 않는다.
- 보관 계정과 시스템 계정은 요청에 넣지 않으며 서버도 수정하지 않는다.
- 활성 형제가 0개 또는 1개인 범위는 UI에서 조작을 표시하지 않으며 API의 `ordered_accounts`는 최소 2개다.
- 현재의 완전한 ID 집합과 모든 최신 version을 보낸 같은 순서만 성공 no-op이다. 같은 순서라도 version이 stale이면 `409 account_reorder_stale`이며 버전을 올리지 않는다.

### API contract

```http
PUT /api/accounts/reorder
Content-Type: application/json

{
  "type": "expense",
  "parent_id": 73,
  "ordered_accounts": [
    {"id": 74, "version": 5},
    {"id": 125, "version": 3},
    {"id": 112, "version": 4}
  ]
}
```

요청은 부분 이동이 아니라 사용자가 본 활성 형제 전체의 최종 순서다. 전체 순서를 보내면 누락·중복·동시 설정 변경을 서버가 한 번에 검증할 수 있고, 드래그와 이동 버튼이 같은 계약을 사용한다.

아래 응답 예시는 완전한 `Account` 응답 중 재정렬에 관련된 필드만 표시한 축약 예다. 실제 `accounts` 원소는 기존 `/api/accounts`와 같은 완전한 `Account` 표현이다.

```json
{
  "accounts": [
    {"id": 112, "position": 1, "version": 5},
    {"id": 74, "position": 3, "version": 6},
    {"id": 125, "position": 4, "version": 4}
  ],
  "effects": {
    "changed_account_ids": [112, 74, 125]
  }
}
```

응답의 `accounts`는 해당 활성 형제의 완전한 `Account` 표현이며 새 순서로 정렬한다. `changed_account_ids`에는 최종 `position`이 실제로 달라진 계정만 포함한다.

### Domain and repository boundary

새 도메인 모델은 다음 책임만 가진다.

- `AccountOrderItem(id, version)`
- `AccountReorderCommand(type, parent_id, ordered_accounts)`
- `AccountReorderResult(accounts, effects)`
- 순수 검증 함수: 중복 ID, 부모와 계정 eligibility, 형제 집합 일치, 같은 유형·부모, 모든 version 일치

기존 `AccountRepository`에 명시적인 `reorder(command)`를 추가한다. 별도 repository나 일반 account `save()`를 만들지 않는다. FastAPI는 request body를 command로 바꾸고 application service를 거쳐 repository를 호출한다.

```text
Accounts UI
  -> PUT /api/accounts/reorder
  -> app service
  -> AccountRepository.reorder(command)
  -> BEGIN IMMEDIATE
     -> 현재 형제 snapshot 조회
     -> 집합·범위·version 검증
     -> active position 슬롯 보존 재할당
     -> changed account version 증가
  -> COMMIT
  -> canonical ordered accounts
```

### Atomic position reassignment

SQLite 고유 인덱스는 두 계정의 위치를 한 행씩 바로 교환하면 중간 상태의 중복을 거부한다. repository는 하나의 `BEGIN IMMEDIATE` 안에서 다음 두 단계로 처리한다.

1. `BEGIN IMMEDIATE`로 write lock을 잡은 뒤, non-null 부모면 부모 행을 같은 트랜잭션에서 읽어 존재·활성·비시스템·그룹 여부·요청 type 일치를 검증한다. 여기서 그룹은 기존 도메인 규칙처럼 `is_placeholder=1`이거나 자식이 하나 이상인 계정이다. `parent_id: null`은 부모 조회를 생략한다.
2. `db_scope_rows`를 전부 읽고, 요청 계정을 해석한 뒤 정해진 오류 우선순위로 scope·eligibility·집합·version을 검증한다.
3. `preserved_active_slots`와 각 대상의 원래 위치·version을 snapshot한다. no-op이면 쓰기 없이 canonical 응답을 반환한다.
4. `max_position`은 보관·시스템을 포함한 `db_scope_rows` 전체에서 구한다. SQLite signed 64-bit 상한 `9,223,372,036,854,775,807`에 대해 `max_position > MAX - len(eligible_siblings)`이면 `account_position_temp_range_exhausted`로 rollback한다.
5. 모든 `eligible_siblings`를 `max_position + 1 ... + N`의 고유 임시 위치로 옮긴다. 이 SQL은 `position`만 갱신하며 `version`, audit 데이터, 다른 열을 건드리지 않는다. 영향 row 수가 N이 아니면 invariant 오류로 rollback한다.
6. 요청 ID 순서대로 `preserved_active_slots`를 최종 배정한다. 원래 위치와 최종 위치가 다른 계정은 이 최종 단계에서만 `version=version+1`로 정확히 한 번 올리고, 위치가 같은 계정은 version을 유지한다. 최종 위치 할당의 영향 row 수도 N이어야 한다.
7. 최종 집합·고유 위치·요청 순서·보관/시스템 불변을 다시 검산한다. 같은 write transaction 안에서 응답에 쓸 완전한 Account 행과 최종 version 벡터를 읽어 immutable snapshot으로 캡처한 뒤 commit하고, commit 후 재조회하지 않은 그 snapshot을 반환한다.

구체적인 gap/보관 예시는 다음과 같다.

| 상태 | A `id=74` | 보관 `id=90` | B `id=125` | C `id=112` |
|---|---:|---:|---:|---:|
| before | `pos=1, v=5` | `pos=2, v=7` | `pos=3, v=3` | `pos=4, v=4` |
| temporary | `pos=5, v=5` | `pos=2, v=7` | `pos=6, v=3` | `pos=7, v=4` |
| request `C,A,B` 후 | `pos=3, v=6` | `pos=2, v=7` | `pos=4, v=4` | `pos=1, v=5` |

따라서 활성 슬롯 `1,3,4`만 재사용하고 보관 슬롯 `2`와 그 version은 그대로다. position gap을 압축하지 않는다. 임시 단계에서는 version이 오르지 않고, 최종 위치가 바뀐 A·B·C만 각각 한 번 오른다.

트랜잭션 중 오류, version 충돌, 고유 인덱스 실패가 발생하면 임시 위치까지 전부 rollback한다. postings, transactions, recurring_rules, opening balances에는 어떤 쓰기도 하지 않는다.

권위 있는 검증 순서는 다음과 같다.

1. FastAPI/Pydantic shape, AccountType enum, `ordered_accounts` 최소 길이 → `422`
2. 중복 ID → `400 account_reorder_duplicate`
3. non-null 부모의 존재·활성·비시스템·그룹·type → 해당 parent 오류
4. 요청 ID 해석, 존재하지 않는 ID → `404 account_reorder_account_not_found`
5. 요청 ID 중 보관·시스템 → `409 account_reorder_forbidden`
6. 요청 ID의 type 또는 parent 불일치 → `409 account_reorder_scope_mismatch`
7. 요청 ID 집합과 `eligible_siblings` 불일치 → `409 account_reorder_set_mismatch`
8. 모든 version 일치 → 불일치 시 `409 account_reorder_stale`
9. 현재 순서와 비교 → 같으면 no-op, 다르면 재할당

이 순서 때문에 `account_reorder_forbidden`은 set equality보다 먼저 도달 가능하고, 동일한 잘못된 요청은 항상 같은 code를 받는다.

### Optimistic UI, pending state, and undo

#### Account mutation lock

로컬 단일 사용자 v1은 계정 mutation을 한 번에 하나만 진행한다. 재정렬 상태가 `saving | undoing | reconciling | refresh-required`이면 새 분류 저장, 설정 저장, 그룹 전환, 보관·복원, 개시잔액과 다른 재정렬의 실행 컨트롤을 비활성화한다. 반대로 이 작업 중 하나가 pending이거나 계정 설정·새 분류 초안이 열려 있으면 재정렬을 시작하지 않는다.

사용자가 이미 입력한 이름·설정·금액은 자동으로 닫거나 초기화하지 않는다. 잠긴 컨트롤 가까이에 `순서를 저장하는 동안 계정 변경을 잠시 기다려 주세요`를 표시한다. 정상 성공·확정 실패 복구·reconciliation이 끝나면 잠금을 해제한다. 최신 상태 확인이 실패한 `refresh-required`에서는 전체 계정 mutation 잠금을 유지하고 persistent retry만 허용한다.

다른 설정 저장으로 형제 중 하나의 `version`이 바뀌면 `409 account_reorder_stale`로 전체 요청을 거부한다. 저장 실패는 다음처럼 “서버가 거부함”과 “commit 여부를 모름”을 구분한다.

- 요청이 서버에 전달되지 않았음이 확정된 pre-dispatch 취소와 rollback을 보장하는 typed `4xx/5xx` 응답: 변경 전 snapshot을 즉시 복원한 다음 canonical `/api/accounts`를 읽는다. 이 recovery read가 성공하면 canonical을 반영하고 overlay를 제거해 잠금을 푼다. recovery read도 실패하면 변경 전 snapshot을 잠정 표시하는 `refresh-required`로 전환하고 계정 mutation 잠금을 유지한다. 사라지지 않는 `최신 순서를 불러오지 못했습니다 · 다시 불러오기` 배너의 retry가 성공해야 canonical 반영 → overlay 제거 → unlock 순서로 복구한다. 특히 stale/set mismatch에서는 이전 snapshot이 서버보다 오래됐다고 전제한다.
- dispatch 이후의 `AbortError`, timeout, 연결 종료, transport error, malformed `2xx`, body parsing 실패, 계약에 없는 status/code: commit 여부를 알 수 없으므로 모두 `reconciling`으로 보내고 계정 mutation을 잠근 채 canonical 목록을 읽는다.
  - canonical 순서가 원하는 순서와 같으면 “현재 서버가 원하는 순서에 도달해 있음”만 확인한다. 해당 요청이 commit 주체였다고 단정하지 않고 canonical 계정/version을 수용하되 undo는 만들지 않는다.
  - canonical 순서가 이전 순서와 같으면 “현재 서버가 변경 전 순서임”만 알린다. 중간에 commit·재변경됐는지는 단정하지 않고 undo를 만들지 않는다.
  - 둘과 모두 다르면 외부 변경을 canonical로 받아들이고 `다른 변경으로 순서가 달라졌습니다`를 표시하며 undo를 만들지 않는다.
- reconciliation 조회도 실패하면 변경 전 snapshot을 잠정 표시하고 계정 mutation을 잠근다. 사라지지 않는 `순서 확인 필요 · 다시 불러오기` 배너를 표시하고, 재조회가 성공해야 잠금을 푼다.

이 설계는 별도 idempotency ledger나 scope revision을 추가하지 않는다. 그래서 명시적인 성공 `2xx`만 undoable이고, 응답이 불명확했던 작업은 최종 order/version이 예상값과 같더라도 보수적으로 undo를 제공하지 않는다. 나중에 원격 다중 사용자·자동 재시도가 필요해지면 `operation_id` 멱등 처리를 별도 설계한다.

실행 취소 상태는 `idle → saving → undoable → undoing → cleared|failed`로 관리한다.

- 명시적인 정상 `2xx`에 한해 성공 전 ID 순서와 transaction snapshot의 최신 version을 저장하고 같은 reorder API로 되돌린다.
- reorder 시작 시 이전 reorder undo를 닫고 고유한 `operationToken`을 부여한다. 하나의 reorder만 진행할 수 있으며, 완료 callback의 token이 현재 token과 같을 때만 상태와 토스트를 바꾼다. redo는 제공하지 않는다.
- 기존 `App.showToast()`의 만료 조건도 메시지 문자열 비교에서 toast object identity 또는 고유 token 비교로 바꾼다. 같은 계정을 6초 안에 연속 이동해 성공 문구가 같아도 이전 타이머는 최신 undo toast를 닫지 못한다.
- undo 성공은 canonical 응답을 반영하고 `cleared`가 된다. undo 중 버튼을 다시 누를 수 없다.
- undo가 stale이면 강제 덮어쓰지 않고 canonical 목록을 읽어 `다른 변경이 있어 실행 취소하지 못했습니다`를 표시한다.
- undo transport 오류도 일반 저장과 같은 `reconciling` 판정을 거친다.

동시 mutation이 stale 검출을 우회하지 않는 근거는 다음과 같다.

| mutation | 재정렬 snapshot에 미치는 변화 | 서버 판정 |
|---|---|---|
| 같은 scope 계정 생성 | `eligible_siblings` 집합 추가 | set mismatch |
| 보관/복원 | eligible 집합 제거/추가 및 계정 version 변경 | set mismatch |
| 계층 이동 | source/target 집합 변경 및 이동 계정 version 변경 | set/scope mismatch 또는 stale |
| 이름·설정 변경 | 대상 account version 증가 | stale |
| 다른 reorder | 위치가 바뀐 형제 version 증가 | stale |
| 부모 보관·group 해제·type 변경 | 트랜잭션 안 parent eligibility/type 재검증 | parent forbidden/type mismatch |
| 부모 이름 등 scope 비영향 설정 | 형제 집합·슬롯에 영향 없음 | reorder와 양립 가능 |

물리적 account delete API는 현재 지원하지 않는다. 향후 추가할 경우 삭제가 집합 mismatch를 만들고, 삭제 정책은 별도 설계에서 정한다.

### Desktop drag implementation

프론트에 현재 공식 React API인 `@dnd-kit/react`와 센서를 제공하는 `@dnd-kit/dom`을 추가한다. `DragDropProvider`의 기본 센서 구성을 대체해 fine-pointer `PointerSensor`만 등록하고 `KeyboardSensor`는 사용하지 않는다. 키보드 사용자는 아래의 이동 버튼을 사용하므로 Enter/Space가 drag 시작과 패널 열기라는 두 의미로 충돌하지 않는다.

이 표에서는 행을 자동으로 재배치하는 `useSortable`과 기본 optimistic sorting plugin을 사용하지 않는다. 각 block owner의 손잡이에 `useDraggable`을 연결하고, `accountTree()` 결과로 만든 scope별 투영 모델의 유효한 앞·뒤 삽입 경계에 `useDroppable`을 연결한다. 따라서 라이브러리는 포인터·센서·overlay만 담당하고, subtree block 순서와 저장 전 DOM 배치는 MoneyMap이 명시적으로 제어한다.

```ts
type ScopeKey = `${AccountType}:${number | "root"}`;
type ReorderBlock = {
  ownerAccountId: number;
  scopeKey: ScopeKey;
  rowKeys: string[];
  startIndex: number;
  endIndex: number;
};

type ReorderProjection = Map<ScopeKey, ReorderBlock[]>;
```

각 block은 한 직접 형제 owner와 그 아래의 모든 후손 account row, 연결된 `(미분류)` virtual row의 연속 구간이다. 한 row가 여러 ancestor scope의 block에 포함될 수 있으므로 전역 row→owner 단일 map은 만들지 않는다. 대신 drag source에서 `activeScopeKey`를 고정하고, collision 후보와 row→owner 해석은 `ReorderProjection.get(activeScopeKey)` 안에서만 수행한다. 같은 scope의 block row span끼리는 겹치지 않고 화면 순서대로 정렬돼야 한다는 invariant를 projection 생성 시 검증한다.

draggable ID는 active scope의 block owner ID만 사용한다. droppable ID는 `scopeKey`와 owner ID, `before | after` 방향으로 구성해 같은 scope의 명시적인 삽입 경계만 나타낸다. descendant나 virtual row 위의 pointer 위치는 active scope에서 그 row를 포함한 유일한 block owner의 앞·뒤 경계로 정규화한다. source의 `startIndex...endIndex` 내부 경계는 거부한다. target block의 첫 행 top과 마지막 행 bottom으로 전체 rect를 만들고, pointer Y가 그 rect의 수직 중점보다 위면 marker를 `startIndex` 앞에, 아래면 `endIndex` 뒤에 둔다.

- 손잡이만 activator로 연결한다.
- 정밀 포인터에서 작은 이동 임계값을 둬 클릭과 드래그를 구분한다.
- 드래그 오버레이에는 계정 이름과 현재 경로만 표시해 표 전체를 복제하지 않는다.
- 드래그 중 실제 descendant DOM 행 전체에 transform을 적용하지 않는다. overlay와 계산된 insertion marker만 움직이고, drop 직후 optimistic tree 재렌더에서 block 전체가 한 번 이동한다.
- 계정 설정이나 다른 행 작업 버튼을 누르는 동작은 dnd-kit sensor가 시작되지 않도록 차단한다.

드롭 애니메이션, overlay의 전체 경로, subtree 배경 강조는 정확성·접근성 다음의 polish다. 100~150ms와 `prefers-reduced-motion` 원칙은 유지하지만 정식 완료 조건을 막지 않는다.

### Single-pointer, mobile, keyboard, and screen reader behavior

W3C WCAG 2.2의 [Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)는 드래그로 가능한 기능에 드래그하지 않는 단일 포인터 대안을 요구한다. 따라서 데스크톱에서도 손잡이는 `<button>` activator다. 정밀 포인터에서 이동 임계값을 넘으면 drag가 시작되고, 단순 click 또는 키보드 Enter/Space는 손잡이에 붙은 non-modal 순서 패널을 열어 실제 `위로 이동`·`아래로 이동` 버튼을 제공한다. dnd-kit sensor 구성은 공식 [Sensors guide](https://dndkit.com/react/guides/sensors/)를 따른다.

coarse pointer 또는 viewport 720px 이하에서는 drag sensor를 끄고 두 이동 버튼을 행에 직접 표시한다. 이동은 보관·시스템을 건너뛴 이전/다음 `eligible_sibling` block과의 한 칸 swap이며, 위치 안내의 N/M도 eligible 형제만 센다.

- 데스크톱 손잡이의 포인터 영역은 최소 32×32px, 모바일 이동 버튼은 44×44px로 한다. 이는 WCAG 2.2 [Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)의 24×24px 기준을 넘는다.
- 패널이 열리면 첫 enabled 이동 버튼으로 focus를 보낸다. Escape나 바깥 click으로 닫고 손잡이에 focus를 돌린다. Tab, Enter/Space의 기본 의미를 보존한다.
- 첫 형제의 `위로`, 마지막 형제의 `아래로` 버튼은 disabled 상태다.
- 성공 후 포커스를 이동된 계정의 손잡이 또는 방금 누른 방향 버튼으로 돌린다.
- `aria-live` 영역은 `외식, 식비 그룹의 2번째 위치로 이동됨`처럼 계정명·부모·새 위치를 알린다.
- 색만으로 드롭 가능 여부를 표현하지 않고 삽입선, 손잡이 상태와 보조 문구를 함께 사용한다.

### Global propagation

`accountTree()`의 `(position, id)` 정렬은 변경하지 않는다. Accounts 화면은 reorder 성공 응답을 해당 scope의 권위 있는 상태로 동기 반영하고 별도 `loadAccounts()`나 `App.refresh()`를 호출하지 않는다. 위치 변경은 잔액·개시잔액·앱 상태 요약을 바꾸지 않으므로 관련 조회도 반복하지 않는다.

거래 입력의 `TransactionAccountPicker`는 이미 `accountTree()`를 사용한다. 반면 실제 반복 규칙의 `RuleForm`과 시나리오의 `ScenarioRules`는 API 배열을 직접 filter/map하므로 두 화면도 `accountTree(accounts)`의 평탄화 결과에서 postable 계정만 거르도록 바꾼다. 기존 native `<select>` UI와 저장 payload는 유지하고, 정렬 계산만 공통 함수로 통일한다.

현재 React Router 구조에서는 한 번에 하나의 주 화면만 mount된다. Accounts는 reorder 응답으로 즉시 패치되고, 거래 입력·반복 규칙·시나리오 규칙은 다음 navigation/mount에서 최신 `/api/accounts`를 읽는다. 향후 계정 소비 화면을 동시에 mount하거나 keep-alive cache를 도입하면 그때 account 전용 generation/cache invalidation을 추가한다. 이번 버전에서 범용 `App.refresh()`를 위치 변경 알림 버스로 사용하지 않는다.

`useAccountOrdering`은 기존 canonical `accounts`와 최대 하나의 `reorderOperation`을 조합한다. operation은 `token`, `scope_key`, 변경 전 ID 순서, 원하는 ID 순서와 상태를 저장한다. 화면은 해당 operation이 pending인 동안 그 scope에만 원하는 순서를 overlay한다.

1. mutation 시작: 진행 중 account read를 abort하고 고유 token과 optimistic overlay를 둔다. 모든 계정 mutation 컨트롤을 잠근다.
2. full `/api/accounts` read: 기존 `AbortController`와 단조 증가 `accountReadSequence`로 가장 최신 read만 canonical `accounts`에 반영한다. pending overlay는 유지되므로 refresh가 optimistic 순서를 중간에 덮지 않는다.
3. 명시적 reorder 성공: callback token이 현재 token과 같을 때만 transaction 내부 response snapshot을 canonical의 해당 scope에 반영하고 overlay를 제거한 뒤 잠금을 푼다. 오래된 callback은 무시한다.
4. 확정 실패 또는 reconciliation 성공: 최신 read를 canonical에 반영하고 overlay를 제거한 뒤 잠금을 푼다. 조회 실패면 overlay를 변경 전 순서로 바꾸고 `refresh-required`와 persistent retry를 유지한다.

`useAccountOrdering`은 mount마다 고유한 route-visit token을 만들고 cleanup에서 무효화한다. 서버에 dispatch한 reorder/undo write는 화면 이탈만으로 abort하지 않는다. 다만 완료 callback의 visit token이 현재 mount와 다르면 toast, focus, local state 변경과 reconciliation GET을 모두 생략한다. 사용자가 저장 중 다른 화면으로 이동했다가 돌아오면 새 mount의 일반 `/api/accounts` 조회가 서버의 최종 canonical 상태를 표시한다. 이 경우 떠난 화면의 작업에는 undo toast를 제공하지 않는다. 새 방문에서 이전 write와 겹쳐 reorder를 시작하더라도 SQLite write serialization과 요청 version 검증으로 둘 중 하나만 성공하며 부분 저장은 발생하지 않는다.

optimistic snapshot → transaction response 또는 reconciliation 순서를 고정한다. 범위별 병렬 mutation을 지원하지 않으므로 scope epoch map과 다중 overlay merge는 만들지 않는다.

별도의 화면별 정렬 저장소, localStorage 순서, 거래 입력 전용 정렬은 만들지 않는다.

### Frontend code boundaries

현재 `Accounts.tsx`는 이미 계정 조회, 잔액, 개시잔액, 생성, 설정, 보관과 표 렌더링을 함께 담당한다. 재정렬 알고리즘과 비동기 상태까지 같은 파일에 추가하지 않고 다음처럼 나눈다.

- `frontend/src/views/accountOrdering.ts` — `ScopeKey`, `ReorderBlock`, scope별 projection, 위·아래 swap, 삽입 경계 판정, canonical+overlay 합성 같은 순수 함수. React와 네트워크에 의존하지 않는다.
- `frontend/src/views/useAccountOrdering.ts` — 하나의 `reorderOperation`, account mutation lock, 요청 token, abort/reconciliation/retry와 undo 상태를 소유하는 hook. API 호출과 toast 연결은 이 경계에 두며 정상 저장·undo에서 `App.refresh()`는 호출하지 않는다.
- `frontend/src/views/Accounts.tsx` — 기존 계정 표와 초안·설정 상태를 유지하고 hook이 제공하는 표시 계정, lock 상태, drag/button handler를 조립한다. scope 계산이나 실패 상태 전이를 다시 구현하지 않는다.
- `frontend/src/api/accounts.ts`, `frontend/src/api/types.ts` — reorder request/response 계약과 HTTP 함수만 추가한다. 트리 또는 UI 상태 로직을 넣지 않는다.
- `frontend/src/App.tsx` — `showToast()`가 각 toast의 object identity 또는 고유 token을 기준으로 자기 타이머만 만료하도록 고친다. 문자열이 같은 최신 toast를 이전 타이머가 지우지 못하게 한다.
- `frontend/src/views/Rules.tsx`, `frontend/src/views/scenarios/ScenarioRules.tsx` — 기존 native `<select>`는 유지하되 API 배열 직접 순회 대신 `accountTree()` 결과를 사용한다. 두 화면에 별도 정렬 규칙을 만들지 않는다.

그룹 판정과 트리 정렬은 기존 `isGroup()`과 `accountTree()`를 재사용한다. 두 새 모듈에 별도 그룹 규칙이나 정렬 fallback을 복제하지 않는다.

### Error contract

| Status | Code | Meaning | UI recovery |
|---:|---|---|---|
| 422 | FastAPI validation | 잘못된 type, 누락 필드, 2개 미만 목록 등 body shape 오류 | 입력 차단, 개발 오류 로깅 |
| 400 | `account_reorder_duplicate` | 요청에 같은 ID가 두 번 있음 | 이전 순서 복원, 오류 표시 |
| 404 | `account_reorder_parent_not_found` | non-null 부모가 존재하지 않음 | 최신 목록 재조회 |
| 404 | `account_reorder_account_not_found` | 요청 ID가 존재하지 않음 | 최신 목록 재조회 |
| 409 | `account_reorder_parent_forbidden` | 부모가 보관·시스템이거나 group이 아님 | 최신 목록 재조회 |
| 409 | `account_reorder_parent_type_mismatch` | 부모 type과 요청 type 불일치 | 최신 목록 재조회 |
| 409 | `account_reorder_scope_mismatch` | 요청 계정의 type/parent가 요청 scope와 다름 | 최신 목록 재조회 |
| 409 | `account_reorder_set_mismatch` | 활성 형제의 누락·추가 | 최신 목록 재조회 |
| 409 | `account_reorder_stale` | 하나 이상의 계정 version이 바뀜 | 최신 목록 재조회, 재시도 안내 |
| 409 | `account_reorder_forbidden` | 보관·시스템 계정이 요청에 포함됨 | 최신 목록 재조회 |
| 500 | `account_position_temp_range_exhausted` | 안전한 signed 64-bit 임시 위치 범위가 없음 | 전체 rollback, 진단 안내 |
| 500 | `account_position_invariant` | 임시·최종 위치 검산 또는 DB 제약 실패 | 전체 rollback, 일반 저장 실패 표시 |
| 503 | `database_busy` | SQLite write lock 대기 초과 | 이전 순서 복원, 재시도 안내 |

## Success Criteria

- Slice 1에서 최상위 및 하위 범위의 형제를 위·아래 버튼으로 재정렬하고, persistence·접근성·undo·실패 복구를 검증한다.
- Slice 2에서 최상위 계정과 1~3단계 하위 그룹의 형제를 데스크톱 손잡이로 재정렬한다. 이 slice까지 통과해야 전체 기능 완료로 본다.
- 모바일·키보드·단일 포인터 사용자는 위·아래 버튼으로 같은 순서를 만들 수 있다.
- 새 순서는 새로고침과 백엔드 재시작 후 유지되며 계정 관리·거래 입력·시나리오 편집기에 동일하게 표시된다.
- 다른 부모나 유형으로 드롭해도 `parent_id`와 순서가 바뀌지 않는다.
- 그룹 이동 시 후손과 `(미분류)` 표시가 함께 움직이고 후손의 직접 `parent_id`와 `position`은 유지된다.
- 보관 계정의 `position`은 활성 형제 재정렬 전후 동일하며 복원 후 보존된 슬롯에 나타난다.
- 재정렬 전후 모든 계정 ID, postings, recurring rule 참조, opening balance, raw balance, 유형 합계와 전역 trial balance가 동일하다.
- 동시 설정 변경은 typed 409로 전체 재정렬을 막고 어떤 position도 부분 저장하지 않는다.
- 확정 실패는 화면을 서버 순서로 되돌리고, 결과 불명 실패는 reconciliation으로 현재 canonical 순서를 확인하되 해당 요청의 commit 주체를 단정하지 않으며, 조회까지 실패하면 해당 scope를 잠그고 재시도 경로를 유지한다.
- 성공 후 실행 취소는 직전 순서를 복원하고, stale undo는 최신 상태를 강제로 덮어쓰지 않는다.
- 드래그 손잡이와 이동 버튼은 키보드 포커스, 24px 이상 포인터 영역, 스크린리더 위치 알림을 제공한다.

## Verification Plan

### Backend

- Domain/API shape: root `parent_id:null`, 잘못된 enum, 누락 필드, 빈 목록·1개 목록, duplicate를 검증한다.
- Parent/account resolution: 존재하지 않는 부모·계정, 보관·시스템·비그룹 부모, 부모 type 불일치, 보관·시스템 요청 계정, 다른 type/parent 계정을 오류 우선순서대로 검증한다.
- Snapshot: 누락·추가, 모든 version 조합, stale인 같은 순서, 최신 no-op을 검증한다.
- SQLite adapter: 루트·하위 형제, position gap, 보관·시스템 슬롯, 두 단계 고유 위치 교환, 임시 SQL의 version 불변, changed-only version 정확히 1 증가, unchanged version 유지, 단계별 row count와 전체 rollback을 검증한다.
- Integer boundary: 안전한 최대 임시 위치와 signed 64-bit overflow 거부를 검증한다.
- Concurrency: create, archive/restore, reparent, settings, parent eligibility 변경 또는 두 reorder가 겹칠 때 mutation matrix의 set/scope/stale 판정과 원자성을 검증한다.
- API: 완전한 canonical Account 응답, 모든 typed error, 재정렬 전후 계정 ID·회계 참조·잔액·trial balance 불변을 검증한다.

### Frontend and E2E

- Pure state (`frontend/e2e/account-ordering-state.spec.ts`): `accountOrdering.ts`를 직접 import해 빈 범위·단일 형제, root/child scope key, 중첩 그룹과 virtual `(미분류)` row의 block span, 보관·시스템 제외, 위·아래 경계 swap, source span·다른 scope 삽입 거부, canonical+overlay 적용·해제를 모든 분기에서 검증한다. 기존 Playwright runner를 사용하며 새 테스트 프레임워크는 추가하지 않는다.

- Slice 1: 재정렬 중 모든 계정 mutation 컨트롤 잠금, 입력값 보존, 성공 focus/live announcement, single-operation undo 상태 전이를 검증한다.

- Slice 1: typed failure rollback, transport outcome의 세 reconciliation 결과, reconciliation read 재실패와 수동 retry를 검증한다.

## Simple UI direction (2026-09-08)

사용자 요청: “난 디자인은 잘 몰라서 일단 심플하게 접근해줘.” 기존 표와 `DESIGN.md`를 기준으로 필요한 조작만 더한다. 별도 테마 선택이나 화면 개편은 하지 않는다. 2026-09-09 사용자가 드래그앤드롭 HTML 시안을 “좋아”로 승인했다. 아래 방향과 시안을 구현 기준으로 사용한다.

- 정보 우선순위는 계정명·계층 → 잔액 → 계정 작업이다. 데스크톱 손잡이는 계정명 바로 앞의 32×32px 버튼으로 항상 표시하고, 같은 깊이의 행은 손잡이가 없는 경우에도 같은 폭의 빈 자리를 유지한다. 드래그할 수 없는 가상 행에는 버튼을 만들지 않는다.
- 손잡이를 누르면 하나의 작은 비모달 패널에서 `계정명 · 부모명 N/M`, `위로 이동`, `아래로 이동`을 보여준다. 일반 버튼 의미를 사용하고 menu 역할을 붙이지 않는다. 패널은 표의 가로 스크롤에 잘리지 않도록 viewport 안에 배치한다.
- 모바일·coarse pointer에서는 계정명 아래에 44×44px 위·아래 버튼을 둔다. 이름과 버튼을 같은 계정 셀 안에 두고 버튼을 우측 작업 열로 보내지 않는다. 기존 다른 열은 가로 스크롤로 유지한다. 32px는 데스크톱의 최소 행 높이이며 모바일의 두 줄 행에 강제하지 않는다.
- 새 UI는 Pretendard, 기존 색상 변수, 4px 모서리와 괘선을 사용한다. 삽입선은 2px `--accent`, 패널은 `--surface`와 1px `--line-strong`이다. 그림자·추가 카드·입장 애니메이션을 넣지 않는다.
- 긴 계정명과 경로는 패널에서 줄바꿈으로 전부 읽을 수 있게 한다. 모바일 계정명도 줄바꿈을 허용한다. 긴 이름 때문에 버튼 영역이나 금액 정렬이 줄어들지 않게 한다.
- 정상 저장은 이동 계정 가까이에 `순서 저장 중…`을 표시하고, 실패 후 확인이 필요한 경우에는 표 위의 사라지지 않는 배너 하나에 이유와 `다시 불러오기`를 둔다. 동일 안내를 모든 행에 반복하지 않는다. 스크롤 아래에서도 상태를 알 수 있도록 이동 컨트롤에 상태 설명을 연결하고 live 영역으로 알린다.
- 성공 후 기존 실행 취소 토스트를 재사용한다. 이동 후 방향 버튼이 목록 끝에 도달해 disabled가 되면 같은 계정의 다른 enabled 이동 버튼으로 포커스를 보낸다. 데스크톱은 손잡이로 돌아갈 수도 있다. 사라진 계정이면 표 제목을 대체 포커스 위치로 사용한다.
