이 문서는 v0.1.0.0 계정 설정 구현 당시의 설계 기록이다. v0.2.0.0에서는 아래의 process `request_lock`을 요청별 연결·WAL로 대체했고, migration transaction은 순서 있는 runner가 소유한다. 계정 writer의 `BEGIN IMMEDIATE` 원자성은 유지한다. 현재 구조와 검증은 [PR 1 검증 기록](../verification/scenario-foundation.md)을 참고한다.

## Problem Statement

이미 존재하는 계정을 다른 계정과목 그룹 아래로 옮길 수 없다. 사용자가 잘못된 위치를 바로잡으려고 같은 이름으로 새 계정을 만들면 `같은 위치에 이미 '기업은행' 계정이 있습니다`라는 생성 중복 오류를 만난다. 현재 우회 방법은 잘못된 경로를 유지하거나 삭제·재생성을 시도하는 것뿐이며, 후자는 거래·반복 규칙·개시잔액과 연결된 안정된 `account_id`를 잃을 위험이 있다.

이번 기능은 계정을 새로 만들지 않는다. 기존 계정의 `parent_id`와 대상 그룹 안의 표시 순서만 바꾸고, 이름·마이너스통장 설정과 함께 한 번에 저장한다.

## What Makes This Cool

- 사용자는 계정을 삭제하지 않고 `자산 > 저축·적금 > 기업은행`을 `자산 > 입출금통장 > 기업은행`으로 바로잡는다.
- 계정 ID, 거래, 반복 규칙, 개시잔액, 잔액 이력은 그대로 유지된다.
- 이름·상위 그룹·마이너스통장 상태가 모두 성공하거나 모두 실패하므로 부분 저장이 없고, 다른 탭의 최신 변경을 오래된 설정 화면이 덮어쓰지 않는다.
- 이동하거나 새로 만든 계정은 대상 그룹의 마지막에 나타나 사용자가 결과를 즉시 찾을 수 있다.

## Constraints

- MoneyMap은 로컬 단일 사용자 FastAPI + SQLite + React 앱이다.
- 회계 코어와 계정 불변식은 사용자가 검증할 수 있는 Python에 둔다.
- 계정 화면은 계정 설정·계층·개시잔액만 담당한다. 거래 입력이나 대시보드 결과를 끌어오지 않는다.
- `Account.type`, `currency`, `archived`, `is_system`은 이 설정 계약으로 바꾸지 않는다.
- 물리 account delete는 지원하지 않는다. 보관이 유일한 제거 동작이며 account row와 position은 남는다.
- 계정 병합, 계정 유형 변경, 드래그앤드롭 대량 편집은 범위 밖이다.
- 외부 관행도 기존 계정의 편집 화면에서 부모를 바꾸고 동일 유형 계층을 유지한다. 참고: [QuickBooks](https://quickbooks.intuit.com/learn-support/en-us/help-article/chart-accounts/create-subaccounts-chart-accounts-quickbooks/L7NLrY7cd_US_en_US), [GnuCash](https://www.gnucash.org/docs/v5/C/gnucash-manual/chart-edit.html).

## Premises

1. 이동은 계정 구조 편집이다. `account_id`, postings, recurring rules, opening balances를 재작성하지 않는다.
2. 진입점은 거래 입력이 아니라 계정 화면의 `설정`이다.
3. 새 부모는 같은 계정 유형의 활성 그룹이거나 해당 유형의 최상위다.
4. 활성 일반 계정과 활성 마이너스통장 계정은 이동할 수 있다. 보관 계정은 먼저 복원해야 한다.
5. 그룹을 이동하면 하위 트리는 각 자식의 `parent_id`를 바꾸지 않고 함께 이동한다.
6. 원하는 이름과 새 부모의 조합이 기존 형제와 충돌하면 이동을 차단한다. 병합이나 자동 이름 변경은 하지 않는다.
7. 이동 후 기존 부모가 모든 자식을 잃으면 `is_placeholder=1`로 저장해 명시적 그룹으로 유지한다.

## Approaches Considered

- **Approach A, 전용 이동 API:** 가장 작지만 이름·마이너스통장·위치 저장이 계속 분리되고 영속 순서를 해결하지 못해 기각했다.
- **Approach B, 원자적 계정 설정 + 영속 순서:** 선택. 한 저장 계약과 `position`으로 부분 성공과 위치 불확실성을 함께 제거한다.
- **Approach C, 계층 편집 모드:** 드래그앤드롭·일괄 정렬은 한 계정의 위치 정정이라는 현재 문제보다 범위가 커서 기각했다.

## Recommended Approach

### User flow

계정 행의 `설정`에서 다음 세 필드를 함께 편집한다.

- `계정 이름`
- `상위 그룹`: 같은 유형의 활성 그룹과 `최상위`만 표시한다.
- `마이너스통장`: 현재 자산 leaf 조건을 그대로 적용한다.

상위 그룹 선택지는 `자산 > 입출금통장`처럼 전체 경로를 표시한다. 자기 자신, 자신의 모든 후손, 보관 계정, 시스템 계정, 마이너스통장 계정은 부모 후보에서 제외한다. 마이너스통장 계정 자체는 leaf인 채로 다른 자산 그룹이나 최상위로 이동할 수 있다.

저장은 한 번만 수행한다. 성공하면 계정 목록을 새로 읽고 이동한 계정에 포커스를 돌려주며, `기업은행을 입출금통장으로 이동했습니다`를 표시한다. 기존 부모가 빈 그룹으로 전환됐다면 `비어진 저축·적금은 그룹으로 유지했습니다`도 같은 결과 메시지에 포함한다. 실패하면 입력값을 유지하고 설정 영역 안에 오류를 표시한다.

### Data model and ordering

`accounts`에 서버 소유 필드 `position`과 낙관적 동시성 필드 `version`을 추가하고 `Account` 및 API 응답에 항상 포함한다.

```sql
position INTEGER NOT NULL DEFAULT 0 CHECK(position >= 0),
version  INTEGER NOT NULL DEFAULT 1 CHECK(version > 0)
```

기존 SQLite 테이블은 `_migrate_account_position_version(conn)` 한 곳에서 변환한다. helper는 명시적 `BEGIN IMMEDIATE` 뒤에 개별 `execute()`만 사용하며, 컬럼 추가, backfill, unique index, trigger 설치, 사후 검증을 모두 성공시킨 뒤 commit한다. 중간 실패는 schema 변경까지 전부 rollback하고 애플리케이션 시작을 중단한다. `executescript()`는 pending transaction을 먼저 commit할 수 있으므로 이 migration 내부에서는 사용하지 않는다.

backfill은 계정을 `(type, COALESCE(parent_id, -1), id)` 순으로 한 번 읽고 Python에서 형제 그룹별 `1..N`을 계산한 뒤 `executemany()`로 갱신한다. 계정마다 별도 `COUNT`나 `MAX`를 실행하지 않는다.

```sql
CREATE UNIQUE INDEX idx_accounts_sibling_position
ON accounts(type, COALESCE(parent_id, -1), position);

CREATE TRIGGER trg_account_position_insert
BEFORE INSERT ON accounts WHEN NEW.position <= 0
BEGIN SELECT RAISE(ABORT, 'account_position_invalid'); END;

CREATE TRIGGER trg_account_position_update
BEFORE UPDATE OF position ON accounts WHEN NEW.position <= 0
BEGIN SELECT RAISE(ABORT, 'account_position_invalid'); END;
```

SQLite는 nullable `parent_id`를 일반 unique key로 묶으면 최상위 중복을 허용하므로 expression index에서 `NULL`을 `-1`로 치환한다. 계정 ID는 양수이므로 sentinel과 충돌하지 않는다.

형제 범위는 `(type, parent_id)`다. 새 계정과 다른 부모로 이동한 계정은 공통 `_next_sibling_position(conn, type, parent_id)`에서 다음 쿼리로 빈 범위에서는 1, 그 외에는 마지막 position을 받는다. unique expression index와 같은 식을 사용하고 adapter test의 `EXPLAIN QUERY PLAN`은 전체 설명 문자열이 아니라 `idx_accounts_sibling_position` 사용 여부만 확인한다. 운영 요청에서는 `EXPLAIN`을 실행하지 않는다.

```sql
SELECT COALESCE(MAX(position), 0) + 1
FROM accounts
WHERE type = ?
  AND COALESCE(parent_id, -1) = COALESCE(?, -1)
```

보관 계정도 같은 범위의 순서 계산에 포함하므로 보관·복원으로 상대 순서가 바뀌지 않는다.

기존 DB에는 사용자가 의도한 수동 순서가 저장돼 있지 않고 프론트가 이름순으로 즉석 정렬한다. 마이그레이션은 복원할 수 없는 의도를 추측하지 않고 각 형제 범위에서 `id ASC` 순으로 `position=1..N`을 한 번 부여한다. 이는 **업그레이드 직후 기존 형제의 표시가 이름순에서 과거 생성순으로 한 번 바뀔 수 있는 가시적 마이그레이션**이다. 이 문서 승인은 그 정책의 승인도 포함하며 CHANGELOG에 기록한다. 마이그레이션 후 이름 변경, 재시작, 표준 시드 재실행, 보관·복원은 position을 바꾸지 않는다.

프론트 `accountTree()`는 이름 정렬을 제거하고 `(position, id)`로 정렬한다. `id`는 손상되거나 구버전 데이터에 position 동률이 있을 때만 결정적 tie-breaker로 사용한다.

모든 accounts writer를 inventory한다. 계정 생성, 표준 시드, settings 이동만 새 position을 할당한다. 이름 변경, 마이너스통장 변경, 보관, 복원, placeholder 변경은 기존 position을 보존한다. 물리 delete 경로는 없고 archive는 position을 남기므로 중간 position gap을 압축하지 않는다. repository의 일반 insert는 양수 position 없이는 실패하며 raw SQL 우회도 trigger와 unique expression index가 차단한다. `_next_sibling_position()`은 repository create, 표준 시드, settings 이동, `init_db`의 system-account bootstrap이 모두 사용한다. API에 남아 있는 표준 시드 SQL과 path lookup도 repository/application service로 옮긴다. 표준 시드는 빠진 path만 현재 형제 범위의 마지막에 추가하고 기존 계정의 position을 재작성하지 않는다.

`version`은 계정 행의 사용자 관찰 가능 필드가 바뀔 때마다 1 증가한다. settings, archive, restore, placeholder 전환, startup의 system-account 보정이 모두 대상이다. create와 seed insert는 version 1로 시작하고, position backfill은 앱 시작 전에 version을 함께 도입하므로 별도 증가가 필요 없다. system-account 보정은 `WHERE is_system=0`인 경우에만 update해 반복 `init_db()`가 version을 올리지 않게 한다. postings만 바꾸는 개시잔액·거래·미분류 재분류는 Account 표현을 바꾸지 않으므로 version을 올리지 않는다. 포괄적인 account update용 repository method는 제거하거나 private로 제한해 version 증가를 우회하지 못하게 한다.

### Canonical API contract

```http
PUT /api/accounts/{account_id}/settings
Content-Type: application/json

{
  "name": "기업은행",
  "parent_id": 3,
  "is_overdraft": false,
  "version": 7
}
```

요청은 부분 patch가 아니라 사용자가 본 최종 설정 상태다. `parent_id: null`은 같은 유형의 최상위로 이동한다는 명시적 값이다. `position`은 클라이언트가 보내지 않고 서버가 이동 여부에 따라 결정한다. `version`은 설정 화면을 열 때 읽은 값이며 현재 DB 값과 다르면 어떤 검증이나 쓰기도 하지 않고 `409 account_settings_stale`을 반환한다.

```json
{
  "account": {
    "id": 34,
    "name": "기업은행",
    "type": "asset",
    "parent_id": 3,
    "position": 4,
    "currency": "KRW",
    "archived": false,
    "is_placeholder": false,
    "is_system": false,
    "is_overdraft": false,
    "version": 8
  },
  "effects": {
    "moved": true,
    "previous_parent_id": 7,
    "source_parent_grouped": true
  }
}
```

`effects.previous_parent_id`는 항상 저장 직전 값이며 `null`일 수 있다. `effects.moved`는 이전 parent와 요청 parent가 다를 때만 true다. `effects.source_parent_grouped`는 이번 요청이 이전 부모를 `is_placeholder=0`에서 `1`로 실제 변경했을 때만 true다. rename-only, overdraft-only, same-parent 저장은 `moved=false`, `source_parent_grouped=false`다. root-to-group은 `previous_parent_id=null`, `source_parent_grouped=false`다. 이미 placeholder였던 이전 부모는 빈 상태여도 `source_parent_grouped=false`다.

repo search 기준 기존 update endpoint의 소비자는 bundled frontend와 tests뿐이다. 프론트 전환과 함께 `PATCH /api/accounts/{id}` 및 `PUT /api/accounts/{id}/overdraft`를 제거해 부분 업데이트 경로를 남기지 않는다. MoneyMap은 프론트와 백엔드를 같은 로컬 릴리스로 배포하므로 별도 호환 기간을 두지 않는다.

### Domain and port boundary

API에 있던 이름 정리·형제 중복 검사를 순수 도메인 함수로 옮긴다. `normalize_account_name()`은 leading/trailing whitespace만 제거하고 내부 whitespace는 보존한 표시 이름을 반환한다. `account_name_key()`는 그 결과에 `casefold()`를 적용한다. Unicode normalization은 이번 정책에 추가하지 않는다. 따라서 ` 기업은행 `은 `기업은행`과, `Toss`는 `toss`와 충돌하지만 `기업 은행`은 별도 이름이다. 이름 길이에는 별도 도메인 상한을 두지 않는다.

검증은 SQL이나 repository를 알지 않는 순수 함수로 구성한다. 공통 primitive는 `normalize_account_name()`, `account_name_key()`, `is_account_group()`, `validate_name_available()`, `validate_parent_target()`, `validate_overdraft_eligibility()`이며, 진입점별 orchestrator는 `validate_account_create()`와 `validate_account_settings_transition()` 두 개다. 고정된 오류 우선순위는 settings orchestrator가 소유한다. backend가 canonical 정책이고 frontend 후보 필터는 빠른 UX 피드백이다. canonical group predicate는 `is_group = is_placeholder OR EXISTS(any child, archived 포함)`로 정의한다.

검증 우선순위는 다음처럼 고정한다. 먼저 source 존재와 version을 확인하고, 이후 아래 순서를 적용해 하나의 요청이 여러 조건을 위반해도 항상 같은 code를 반환한다.

1. source 활성 상태와 non-system 여부
2. trim 후 비어 있지 않은 이름
3. `desired.parent_id != current.parent_id`일 때만 새 parent placement 검증 블록 실행
   - `parent_id is not null`이면 parent 존재, 활성 상태, non-system 여부
   - parent와 source의 type 일치
   - 자기 자신·후손을 부모로 선택하지 않는 acyclic 조건
   - overdraft parent 금지
   - canonical group predicate 충족
4. 원하는 `(type, parent_id, account_name_key)` 범위의 중복, 보관된 형제 포함, 자기 ID 제외
5. 원하는 source의 overdraft eligibility: `type=asset AND is_placeholder=false AND 자식 없음(archived 포함)`

Overdraft eligibility 안의 오류 우선순위도 고정한다. `type != asset`이면 먼저 `overdraft_invalid_account`, 그 다음 `is_placeholder=true`이면 `overdraft_cannot_be_group`, 마지막으로 archived를 포함한 자식이 있으면 `overdraft_requires_leaf`를 반환한다.

현재 parent가 바뀌지 않는 rename-only 또는 overdraft-only 저장은 과거 버그나 raw SQL로 생긴 illegal parent를 grandfather한다. 설정 select에는 현재 경로를 `현재 위치 · 이동 필요` option으로 유지해 form value가 사라지지 않게 하고, 다른 부모로 이동할 때는 새 parent 규칙을 전부 적용한다. 이 정책은 오래된 비정상 계정도 삭제 없이 유효한 그룹으로 옮겨 복구할 수 있게 한다. 새 계정 생성과 모든 새 이동은 archived/system/다른 type parent를 거부하므로 새로운 illegal placement는 만들 수 없다.

계층 책임은 명확히 나눈다.

```text
API -> app_services.update_account_settings(command, accounts)
    -> AccountRepository.update_settings(command)
       -> SQLite adapter: BEGIN IMMEDIATE, snapshot load, version check
       -> pure domain validator(current, desired, snapshot)
       -> SQL writes, effects construction, COMMIT
```

별도 `AccountSettingsWriter` port는 만들지 않는다. 하나의 `AccountRepository` port가 read method와 명시적 `create()`, `update_settings()`, `set_archived()`, `set_placeholder()`만 노출한다. 기존의 포괄적 `save()`와 `set_overdraft_enabled()`는 제거해 version 증가와 position 보존 규칙을 우회할 수 없게 한다. application service는 use-case 진입점과 repository 호출을 담당하고 SQL을 모른다. `SqliteAccountRepository`가 트랜잭션과 queries/writes를 묶되 정책 판단은 순수 domain validator 결과만 사용한다.

### Transactional flow

SQLite adapter는 account write 전용 private transaction context manager로 `BEGIN IMMEDIATE`, commit, rollback, integrity error 번역을 한 곳에 둔다. `SQLITE_BUSY`와 `SQLITE_LOCKED`만 retryable `503 database_busy`로 번역하고 다른 오류는 숨기지 않는다. unrelated transaction repository는 이번 범위에서 바꾸지 않는다. settings는 이 경계 안에서 다음 전 과정을 수행한다.

1. 현재 계정을 다시 읽는다. 없으면 404, version이 다르면 stale 409로 종료한다.
2. 요청된 부모와 전체 account snapshot을 같은 트랜잭션에서 읽는다.
3. 최종 `Account`를 만들고 고정된 우선순서로 순수 도메인 검증을 수행한다.
4. 부모가 실제로 바뀌면 대상 형제 범위에서 다음 position을 계산한다. 같은 부모면 position을 유지한다.
5. `UPDATE ... WHERE id=? AND version=?`로 `name`, `parent_id`, `is_overdraft`, `position`, `version=version+1`을 한 번 갱신한다. 영향 행이 0이면 stale 409로 rollback한다.
6. 이전 부모가 존재하고 이제 자식 행이 하나도 없으면 `UPDATE ... SET is_placeholder=1, version=version+1 WHERE id=? AND is_placeholder=0`을 실행한다. archived 자식도 자식으로 계산한다. 정상 사용자 계정뿐 아니라 archived source parent도 정리 대상이지만, system parent, overdraft parent, raw SQL로 이미 사라진 legacy parent는 정리를 건너뛴다. 이 경우에도 계정 이동은 성공하고 `source_parent_grouped=false`다. 직접 posting 존재 여부는 정리를 막지 않는다. 이전 부모는 이동 전 이미 자식을 가진 그룹이었기 때문이다.
7. 결과와 effects를 구성하고 commit한다.

어느 단계에서든 실패하면 이름, 마이너스통장, 부모, position, 이전 부모의 placeholder 변경을 모두 rollback한다. postings, transactions, recurring rules, opening balances에는 쓰기 SQL을 실행하지 않는다.

계정 생성도 같은 position 할당 규칙을 사용해 `COALESCE(MAX(position),0)+1` 계산과 insert를 한 트랜잭션에 둔다. 이로써 `신규 계정과목을 해당 그룹의 맨 마지막에 추가` TODO를 함께 완료한다.

SQLite connection은 `PRAGMA busy_timeout=5000`을 설정한다. 지원 배포 형태는 기존과 같은 단일 backend process다. process-level request lock과 `BEGIN IMMEDIATE` 아래의 동시 쓰기는 둘 다 순서대로 성공해야 한다. 별도 process가 5초 이상 lock을 점유하면 `503 database_busy`와 `retryable=true`를 반환하며 어떤 필드도 변경되지 않는다.

### Error contract

`DomainError`는 JSON-safe `context`를 지원하고 FastAPI handler는 `{ "detail": { "code": "...", "message": "...", ...context } }` 형식으로 반환한다. structured context는 충돌 계정 ID·보관 상태·대상 경로와 `retryable`을 전달하며 문자열 parsing에 사용하지 않는다. JSON 필드 누락이나 잘못된 타입은 FastAPI 기본 request validation `422`를 유지하며 이 envelope의 대상이 아니다.

| Status | Code | 의미 |
|---:|---|---|
| 404 | `account_not_found` | 이동하는 계정이 없음 |
| 404 | `account_parent_not_found` | 요청한 부모가 없음 |
| 400 | `account_name_required` | trim 후 이름이 비어 있음 |
| 409 | `account_settings_stale` | 요청 version이 최신 DB와 다름 |
| 409 | `archived_account_read_only` | 보관 계정은 복원 후 수정해야 함 |
| 409 | `system_account_read_only` | 시스템 계정은 수정할 수 없음 |
| 409 | `archived_account_parent_forbidden` | 보관 계정을 부모로 지정함 |
| 409 | `system_account_parent_forbidden` | 시스템 계정을 부모로 지정함 |
| 409 | `account_name_conflict` | 원하는 이름이 대상 위치의 활성 또는 보관 형제와 충돌 |
| 409 | `account_parent_type_mismatch` | 부모와 자식 type이 다름 |
| 409 | `account_parent_requires_group` | 부모 후보가 활성 그룹이 아님 |
| 409 | `account_cycle` | 자기 자신 또는 후손을 부모로 선택함 |
| 409 | `overdraft_parent_forbids_children` | 마이너스통장을 부모로 선택함 |
| 409 | `overdraft_requires_leaf` | 자식이 있는 계정을 마이너스통장으로 설정함 |
| 409 | `overdraft_cannot_be_group` | 명시적 그룹을 마이너스통장으로 설정함 |
| 409 | `overdraft_invalid_account` | 비자산 계정을 마이너스통장으로 설정함 |
| 500 | `account_position_invariant` | unique position 충돌, 서버 결함으로 기록하고 전체 rollback |
| 503 | `database_busy` | 5초 lock 대기 초과, `retryable=true` |

`account_name_conflict`에는 `conflicting_account_id`, `conflicting_account_archived`, `target_path`를 포함한다. 사용자 메시지는 예를 들어 `선택한 위치 '자산 > 입출금통장'에 이미 '기업은행' 계정이 있습니다`로 표시한다. 보관 계정과 충돌하면 그 사실도 명시한다. 병합 버튼이나 자동 이름 변경은 제공하지 않는다.

### UI states and accessibility

`Accounts.tsx`에서 `AccountSettingsPanel.tsx`를 분리한다. 이 panel은 draft, 전체 경로, 부모 후보, 단일 저장, duplicate/stale 오류, 취소를 소유한다. 계정·개시잔액 화면의 책임을 유지하기 위해 balance, opening balance, dashboard 결과는 panel에 전달하지 않는다. `Accounts.tsx`는 목록, 선택된 account ID, refresh, 성공 후 focus/scroll을 소유한다. 설정은 승인된 평면형 패널이며 별도의 장식 카드 안에 넣지 않는다.

- settings draft에 `parentId`, `originalParentId`, `version`을 추가하고 현재 XOR 저장 제한을 제거한다. 세 필드 중 하나 이상 바뀌고 이름이 유효하면 저장할 수 있다.
- 저장 중 세 필드를 모두 비활성화하고 버튼 문구를 `저장 중…`으로 고정한다.
- 전체 경로를 option label과 선택 아래 보조 행에 함께 표시해 같은 이름의 그룹을 구분한다.
- 후보가 `최상위`뿐이어도 select는 유지해 현재 위치를 분명히 한다.
- 기존 illegal parent는 선택된 `현재 위치 · 이동 필요` option으로만 표시하고 새 선택 후보로는 제공하지 않는다. parent를 그대로 둔 이름·마이너스통장 설정은 저장할 수 있지만, 다른 계정의 부모로 다시 선택할 수는 없다.
- 오류 후 draft와 포커스를 유지한다. stale 오류는 최신 계정을 다시 읽도록 안내하고 사용자 입력을 자동 병합하지 않는다.
- 현재 계정 트리는 접힘 상태가 없으므로 destination은 항상 렌더된다. 성공 시 `pendingFocusAccountId`를 저장하고 refresh된 accounts가 렌더된 뒤 해당 ID를 `scrollIntoView({block: "nearest"})`하고 설정 버튼에 포커스를 둔다. 향후 접기 기능이 생기면 먼저 destination ancestor path를 펼치는 것이 같은 계약의 전제다.
- 긴 경로는 한 줄 말줄임과 `title`을 함께 사용하고, 모바일에서는 경로를 두 줄까지 허용한다.
- 이동은 되돌릴 수 있는 메타데이터 변경이므로 확인 dialog를 띄우지 않는다. 다시 설정을 열어 원래 부모를 선택하면 되돌릴 수 있다.
- 성공 문구는 move-only, rename-only, overdraft-only, combined 변경을 구분한다. combined 변경은 `기업은행 설정 3개를 저장했습니다`처럼 변경 수를 말하고, 이동 경로와 source group 효과를 보조 문장으로 붙인다.
- 보관된 계정 행은 `복원`만 제공하고 설정 버튼이나 설정 panel을 렌더하지 않는다. 복원 후 활성 목록에서 다시 설정할 수 있다.

## Success Criteria

- 기존 계정을 같은 유형의 다른 활성 그룹 또는 최상위로 이동할 수 있다.
- 이동 전후 account ID, 거래 수, 반복 규칙 참조, 개시잔액, **계정별 raw balance**, 유형별 합계, 전역 trial balance가 동일하다. 이전·새 조상의 rollup subtotal은 계층 이동에 따라 바뀌는 것이 정상이다.
- 그룹 이동 시 모든 후손의 ID와 직접 parent_id가 그대로이며 화면 경로만 새 조상 아래로 바뀐다.
- 마지막 자식이 이동한 이전 부모는 같은 트랜잭션에서 명시적 그룹으로 남는다.
- 이름·부모·마이너스통장을 함께 바꾸다 하나가 실패하면 어떤 필드도 저장되지 않는다.
- 다른 탭의 오래된 version으로 저장하면 409를 받고 최신 변경을 덮어쓰지 않는다.
- 신규·이동 계정은 대상 형제 범위의 마지막에 나타나며 rename·재시작·보관·복원·재시드 후에도 순서가 유지된다.
- 중복 오류는 충돌한 위치와 보관 여부를 설명하고, 사용자는 잘못된 새 계정 생성과 기존 계정 이동을 구분할 수 있다.
- 키보드만으로 설정 열기, 부모 선택, 저장, 오류 수정, 취소가 가능하며 성공 후 포커스를 잃지 않는다.
- 기존 계정의 표시가 업그레이드 시 이름순에서 생성순으로 한 번 바뀔 수 있으며, 이후 모든 순서는 영속적으로 유지된다.

### Migration and write pipeline

`backend/moneymap/adapters/sqlite/database.py`에는 다음 파이프라인을 짧은 ASCII 주석으로 남긴다.

```text
legacy accounts
    -> BEGIN IMMEDIATE
    -> add position/version columns
    -> one ordered read -> Python sibling numbering -> executemany backfill
    -> unique expression index + positive-position triggers
    -> verify schema/invariants
    -> COMMIT
       any failure -> ROLLBACK -> startup abort
```

일반 account write 흐름은 다음과 같다.

```text
FastAPI request
    -> process request_lock
    -> application service
    -> AccountRepository explicit command
       -> account transaction context (BEGIN IMMEDIATE)
       -> reload current + account snapshot
       -> version guard
       -> pure create/settings validation
       -> allocate position only for create or cross-parent move
       -> one account update + optional legacy source-parent cleanup
       -> COMMIT
    -> structured response/effects

DomainError ---------------------------> typed 4xx + context
SQLITE_BUSY / SQLITE_LOCKED ------------> 503 + retryable=true
position/index invariant --------------> rollback + logged typed 500
```

### Failure modes

| Codepath | Realistic failure | Test | Handling | User-visible result |
|---|---|---|---|---|
| Legacy migration | duplicate or invalid position prevents index install | forced failure rollback | full rollback and startup abort | backend does not start with half-migrated DB |
| Position allocator | query shape misses expression index | `EXPLAIN QUERY PLAN` index-name assertion | exact matching expression | no visible delay at expected scale |
| Account transaction | another process holds SQLite write lock over 5s | busy timeout/retry test | rollback, typed 503 | retryable error message |
| Settings save | another tab already changed the account | stale-version API/E2E | no validation or write after mismatch | reload guidance, newer data preserved |
| Name/parent validation | archived duplicate or illegal target selected | domain/API/E2E | typed 409 with context | draft preserved with target-specific message |
| Tree mutation | self or descendant chosen as parent | domain/API | reject before SQL write | cycle error in settings panel |
| Position invariant | unexpected sibling collision | forced adapter/API collision | full rollback and logged typed 500 | save failure, no partial change |
| Source cleanup | legacy parent is missing/system/overdraft | cleanup skip tests | move commits, effect false | move succeeds without misleading cleanup claim |
| Frontend save | slow response and repeated click | delayed-route E2E | fields/buttons disabled | one request and stable draft |
| Archive lifecycle | user tries to edit archived account | API and E2E | settings absent until restore | restore is the only available row action |
| Accounting links | reparent accidentally rewrites linked rows | critical regression test | repository writes accounts only | balances and rules remain unchanged |
| E2E execution | multiple specs mutate shared DB | full E2E suite | Playwright `workers: 1` | deterministic suite |

Critical gaps: **0**. Every data-loss, silent-write, stale-write and partial-write failure has a planned test and explicit handling. Focus restoration failure is non-destructive; the implementation should no-op safely if the refreshed row is absent.
