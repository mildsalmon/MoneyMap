# 할부 구매와 납부 일정 — 아이디어 제안

작성: 2026-10-03 · gstack /office-hours · Builder mode
상태: 2026-10-18 사용자 요청으로 무이자 첫 버전 구현. 아래 2026-10-18 구현 계약이 초안의 미결 사항을 확정한다.

## 해결할 문제

할부 구매를 입력할 때 소비 총액, 아직 갚지 않은 부채, 매달 통장에서 나갈 돈을 함께 추적한다. 월 납부액만 지출로 입력하면 남은 약정이 드러나지 않고, 구매와 납부를 모두 지출로 입력하면 소비가 중복된다.

이번 제안은 원화 신용카드 무이자 할부를 첫 대상으로 가정한다. 대출·리볼빙·해외 할부까지 포함한다는 사용자 결정은 아직 없다. 앱 내부 기록 방식의 제안이며 카드사별 청구 규칙을 확정한 문서는 아니다.

## 현재 구조와 재사용 범위

- `backend/moneymap/domain/transaction.py`: 구매와 납부를 기존 복식 거래로 표현한다.
- `backend/moneymap/domain/recurring_rule.py`: 시작·종료일과 고정 금액은 있으나 구매별 회차·잔여 원금·납부 연결은 없다.
- `backend/moneymap/domain/projection.py`: 공통 이벤트로 순자산·현금 전망을 계산한다. 할부도 같은 이벤트 경로에 통합해야 한다.
- `backend/moneymap/domain/simulation.py`: 수동 비용을 변동지출 평균에 포함한다. 일회성 할부 구매가 미래의 반복 소비로 추정되는 문제를 별도로 해결해야 한다.
- 기존 입력은 차변·대변 직접 선택 방식이다. 예전 카드값 납부 탭을 전제로 설계하지 않는다.

## 대안 비교

| 대안 | 장점 | 한계·위험 | 규모 |
|---|---|---|---|
| A. 구매 총액 입력 + 종료일 있는 납부 반복 규칙 | 기존 거래·규칙 재사용, 가장 작은 변경 | 회차 추적·마지막 금액 보정·합산 카드 납부 연결이 수동이며 자동 생성분이 실제 납부로 오인될 수 있음 | S / 중간 |
| B. 구매 거래에 연결된 유한 할부 일정 | 총액·회차·잔여 원금 일치, 실제 납부와 예측을 구분할 수 있음 | 일정과 실제 납부 배분 모델, 중복 방지 설계 필요 | M~L / 중간 |
| C. 카드 명세서·결제주기 전체 관리 | 일시불과 여러 할부를 하나의 청구액으로 관리 | 명세서 수집·대사·카드사 규칙까지 범위가 커짐 | XL / 높음 |

**추천: B.** MoneyMap의 미래 현금 전망에 필요한 것은 유한한 지급 약정이다. 구매는 기존 거래로 유지하고, 할부 일정과 납부 연결만 추가한다. A는 수동 임시 운용안, C는 후속 확장 후보로 남긴다. 월별 납부액을 매번 새로운 소비로 처리하는 방식은 기존 순자산·소비 집계 의미와 맞지 않아 권하지 않는다.

## 추천 동작과 숫자 예시

생활용품 1,200,000원을 6개월 무이자 할부로 구매하고 매달 200,000원씩 납부한다고 가정한다.

| 시점 | 실제 원장 | 소비 | 현금 변화 | 순자산 변화 |
|---|---|---:|---:|---:|
| 구매일 | 차변 생활용품 비용 1,200,000 / 대변 카드부채 1,200,000 | 1,200,000 | 0 | -1,200,000 |
| 매월 실제 납부일 | 차변 카드부채 200,000 / 대변 통장 200,000 | 0 | -200,000 | 0 |

자산으로 관리하는 물건은 구매 차변을 해당 자산으로 둔다. 이 경우 구매 자체의 순자산 변화는 0이다. 모든 할부 구매를 비용으로 강제하지 않는다.

입력할 정보는 구매 거래, 할부 원금, 카드 계정, 납부 통장, 개월 수, 첫 납부 예정일이다. 저장 전에 회차별 날짜·원금 합계를 미리 보여준다. 예정일은 사용자가 확인하며 카드사 청구일을 구매일만으로 추정해 확정하지 않는다.

‘이번 달 소비’는 구매 기준을 유지한다. 별도로 ‘이번 달 할부 납부 예정’, ‘남은 원금’, ‘다음 납부일’, ‘완납 예정월’을 표시한다. 이를 전체 카드 청구액처럼 표시하지 않는다. 후속으로 시나리오에서 일시불과 할부의 최저 현금 잔액·현금 부족 시점을 비교하면 MoneyMap의 장점을 살릴 수 있다.

## 첫 버전의 안전한 경계

1. **유한 일정:** 구매 하나에 여러 회차를 연결한다. 예: 100,000원/3회는 33,333·33,333·33,334원. 최소 화폐 단위 정수로 계산하고 마지막 회차에 나머지를 반영한다. 원금 합계는 항상 구매의 할부 대상 금액과 같다.
2. **예정과 실제 분리:** 예정일이 지나도 실제 원장에 자동 납부 처리하지 않는다. 실제 거래를 입력하거나 기존 거래에 배분하여 확인한다. 지난 미확인 회차는 ‘확인 필요’로 남기며 향후 현금 전망이 완전하다고 표시하지 않는다.
3. **카드 합산 납부:** 하나의 실제 카드 납부 거래를 여러 할부 회차에 배분할 수 있다. 거래는 한 번만 저장하며 회차 연결은 추가 현금 출금을 만들지 않는다. 배분 총액은 실제 납부액을 넘을 수 없고, 일시불 등 나머지 금액도 허용한다. 같은 금액·날짜라는 이유만으로 자동 연결하지 않는다.
4. **중복 전망 방지:** 실제 납부 배분으로 완납한 회차만 예정 이벤트에서 제외한다. 부분 납부 회차는 미납 원금만 예정 금액으로 남긴다(20만 원 중 5만 원 납부 시 15만 원). 전체 카드값 반복 규칙에 같은 할부가 포함됐는지 사용자가 선택해야 하며, 같은 카드·기간에 중복 가능 규칙이 있으면 선택 전 할부의 현금 전망 반영을 보류한다. 전체 카드값에 포함된 할부를 별도로 다시 더하지 않는다. 구체적인 선택 UI와 배분 저장 계약은 구현 전 확정한다.
5. **추정 소비 분리:** 할부 구매 중 일회성으로 지정한 비용은 원장의 소비 통계에는 그대로 남기고 미래 변동지출 평균에서만 제외한다. 할부라는 이유만으로 모든 구매를 자동 제외하지 않는다. 예상 납부 원금은 미래 비용으로 더하지 않는다.
6. **변경·취소:** 납부 확정 회차와 실제 거래는 자동 재작성하지 않는다. 구매 수정·삭제나 연결 거래 수정·삭제는 관련 일정과 배분의 영향 확인 없이는 차단한다. 초기 버전의 중도상환·환불은 명시적 실제 거래와 잔여 일정 조정을 함께 검산하는 방식으로 처리하며, 부분 환불의 카드사 회차 재배분을 자동 추측하지 않는다.
7. **날짜:** 월 납부일 기준을 유지하고 없는 날짜는 말일로 당긴다. 1월 31일→2월 말일→3월 31일이며 카드사 휴일 이연은 자동 적용하지 않고 예정일 수정으로 대응한다.
8. **보존·원자성:** 구매·일정 생성은 함께 성공하거나 실패해야 한다. 저장 재시도, 납부 재연결, 전망 재계산이 중복 거래를 만들지 않아야 한다. 기존 CSV 거래의 ID·출처·금액은 보존한다.

유이자 할부는 첫 버전에서 지원한다고 표시하지 않는다. 후속 지원 시 원금 상환과 이자/수수료 비용을 분리하고, 카드 명세서 기준 회차 금액을 입력할 수 있게 한다. 임의의 이율 계산식으로 정확한 청구액을 단정하지 않는다. 기존 진행 중 할부의 중도 등록과 개시부채 연결도 별도 설계가 필요하다.

## 구현 전 확인할 사항

- 사용자의 실제 요구가 무이자 카드 할부인지, 유이자·이미 진행 중인 할부가 반드시 필요한지 확인한다.
- 실제 카드 납부를 한 건으로 입력하는 사례로 회차 배분과 반복 규칙 중복 방지 흐름을 확정한다.
- 미확인 과거 회차의 전망 경고·재일정 동작, 부분 환불·중도상환의 최소 조정 절차를 확정한다.
- 기존 시나리오가 actual의 할부 일정을 상속하는 방식과 실제 납부 이후 대체 규칙을 확정한다. 시나리오 전용 할부 생성은 후속 후보이며 실제 일정을 포함한 기존 전망의 정확성은 첫 버전 조건이다.

## 완료 조건과 다음 단계

- 120만 원/6회 예시에서 구매 후 부채 120만 원, 2회 납부 후 현금 누적 감소 40만 원·잔여 원금 80만 원, 전체 소비 120만 원을 검증한다.

- 실제 원장·반복 카드값·할부 일정·변동지출 추정 사이에서 현금 또는 비용이 중복되지 않는지 실제/기준/시나리오별로 검증한다.
- 구현 시 백엔드 pytest와 프런트 E2E를 모두 실행한다. 이번 변경은 아이디어 문서와 TODO 기록만 수행한다.

다음 착수 과제: 실제 무이자 할부 한 건의 총액·개월 수·첫 납부일·첫 두 회차 금액을 기준으로 위 예시와 대조하고, 카드 합산 납부 한 건에 연결하는 흐름을 설계한다. 계좌번호 등 식별 정보는 필요 없다.


## 2026-10-18 구현 계약

사용자는 할부 사용 빈도가 낮고 무이자면 충분하다고 확인했다. 이번 범위는 새 원화 무이자 구매이며, 진행 중인 기존 할부를 중도 등록하거나 기존 구매 거래를 다시 생성하는 이관 기능은 제공하지 않는다.

```
구매 거래 (총액, 기존 transactions/postings)
  └─ installment_plans (원금, 카드, 통장, 구매 계정)
       └─ installments (회차, 예정일, 원금)
            └─ installment_allocations ← 실제 납부/환불 거래
                  원장 거래 추가 없음; 연결 금액만 보관
```

- `/installments` 화면에서 구매일·계정·총액·2~60개월·첫 납부일을 입력하고 서버 계산 회차를 미리 본 뒤 저장한다. 구매와 일정 생성은 하나의 `BEGIN IMMEDIATE` 경계다. 원금은 정수이며 마지막 회차에서 나머지를 보정한다.
- 납부/환불 거래는 기존 거래 입력에서 기록한 뒤 내역 또는 번호로 찾아 연결한다. 배분 저장은 그 거래의 기존 배분 전체를 원자적으로 교체한다. 회차 잔여 원금, 거래의 카드 차변과 상대 계정 대변 모두를 검산하여 여러 구매에 나눈 합계도 한도를 넘지 못한다. 중도상환은 실제 납부를 여러 미래 회차에 배분하고, 부분/전체 환불은 구매 계정→카드 실제 환불을 원하는 회차에 배분한다. 날짜·금액 유사성으로 자동 연결하지 않는다.
- 연결된 거래는 저장소 트리거로 수정·삭제를 차단한다. 배분을 해제한 뒤 실제 거래를 정정하고 다시 연결한다. 구매 수정은 배분 해제→일정 삭제 후 기존 거래 수정으로 처리하며, 일정 삭제 자체는 구매 거래를 삭제하지 않는다. 납부 연결이 없는 회차는 예정일을 변경할 수 있다. 이미 배분된 회차의 날짜 변경은 먼저 배분 해제가 필요하다.
- 공유 계산 revision과 요청 UUID/내용 해시/결과 영수증으로 동시 변경과 재시도를 처리한다. 저장 응답 유실 시 브라우저 sessionStorage의 같은 요청을 재전송한다. 내용이 다른 UUID 재사용은 거부한다. 화면을 다시 열어도 미확인 저장 결과를 먼저 확인한다.
- 전망은 공통 `ProjectionEvent(kind=installment)` 경로를 쓴다. 납부 원금은 현금·카드부채를 동시에 감소시키므로 순자산 및 소비 비용을 중복 감소시키지 않는다. 시작 잔액에 들어간 구매만 사용하며, 배분은 해당 전망 기준일 이하의 실제 거래만 차감한다. 과거 기준 시나리오에서 나중 납부를 미리 차감하지 않는다. 활성/보관 live-additive 시나리오가 동일한 실제 일정을 따른다.
- 과거/당일 미확인 회차를 임의로 미래 날짜로 옮기거나 자동 기장하지 않는다. 회차·전망 화면에 누락 경고를 표시하고 납부 연결 또는 명시적 예정일 수정을 요구한다. 현금 계정 선택은 기존 계정 설정을 유지한다.
- 같은 카드의 기간 중첩 반복 규칙이 있으면 할부의 별도 전망을 보류한다. 사용자가 규칙에 미포함/포함을 선택한다. 포함은 같은 납부일·통장·카드의 반복 규칙 금액이 포함된 여러 구매의 원금을 모두 감당할 때만 허용한다. 규칙 내용/대상 변경 시 다시 확인하도록 하고 처리 watermark 이동은 판단을 무효화하지 않는다. 일정 조정도 중복 판단을 초기화한다.
- 현재 live-additive 전망은 등록한 가정만 사용한다. 기존 legacy 평균 소비 추정은 사용자가 일회성 구매로 명시한 경우에만 제외한다. 소비 통계와 실제 거래는 유지한다.
- 스키마 v7의 할부 테이블과 v8의 연결된 카드 납부 규칙 삭제 보정을 기존 순차·백업·원자적 마이그레이션 경로로 추가한다. 실제 사용자 DB를 개발 검증에 사용하지 않는다. 구버전 앱은 자신이 지원하는 버전보다 높은 DB를 거부하므로 되돌릴 때는 마이그레이션 전 백업과 맞는 앱 버전을 사용한다.

### 유이자 확장 경계

이번의 `principal`과 배분 `amount`는 모두 **원금**이다. 이자·수수료는 이 컬럼에 합산하지 않는다. 이후 회차에 별도 비용 구성요소(이자·수수료) 및 그 실제 비용 분개/배분을 추가하고, 지급 총액을 원금+이자+수수료로 검산한다. 원금 배분은 카드부채 감소액, 비용 배분은 해당 비용 분개 한도를 각각 확인해야 한다. 이번에는 미사용 이율·이자 컬럼이나 자동 계산기를 만들지 않는다. 명세서 기준 금액·부분 납부 배분 순서·중도상환 수수료 정책을 먼저 확정하며 [TODO](../../TODOS.md)에 후속 기능으로 기록했다.
