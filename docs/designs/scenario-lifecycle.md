## Problem Statement

MoneyMap의 시나리오는 현재 생성과 인라인 규칙 편집만 제공한다. 이름·설명 수정, 복제, 보관·복원, 영구 삭제가 없고, 생성한 시나리오의 결과도 전용 화면에서 충분히 설명하지 않는다. 사용자는 시나리오를 만든 직후 그 가정이 순자산과 현금 흐름에 주는 영향을 보고, 더 이상 필요하지 않은 시나리오는 실제 장부에 영향 없이 정리하고 싶다.

현재 구현의 `copy-on-fork`는 생성 시 실제 장부의 반복 규칙을 시나리오에 복사한다. 이 방식은 이후 실제 규칙 변경을 기존 시나리오에 반영하지 않아, 사용자가 원하는 “실제 장부는 독립적으로 움직이고 시나리오는 최신 실제 규칙을 따라가는” 모델과 맞지 않는다. 현재 기준 전망에 들어가는 최근 3개월 변동지출 평균도 사용자가 등록한 규칙만으로 계산한다는 원칙과 충돌한다.

이번 기능은 시나리오를 실제 장부에 덧붙이는 가상 계획으로 다시 정의하고, 생성부터 수정·복제·보관·복원·영구 삭제까지의 수명주기와 전용 전망 대시보드를 완성한다.

## What Makes This Cool

- 시나리오를 만들자마자 전용 `개요` 화면에서 “현재 패턴을 유지할 때”와 “이 가정을 적용할 때”의 3·6·12개월 결과를 바로 비교한다.
- 실제 장부 규칙은 최신 상태를 자동으로 따라가되, 시나리오가 만든 규칙과 예정 거래는 실제 장부를 절대 수정하지 않는다.
- 순자산이 충분해도 지급일에 현금이 부족한 경우, 최초 부족일과 최대 부족액을 별도로 보여준다.
- 일상적인 정리는 복원 가능한 보관으로 처리하고, 영구 삭제는 보관함에서 영향 범위를 확인한 뒤에만 실행한다.

## Constraints

- MoneyMap은 로컬 단일 사용자 FastAPI + SQLite + React 웹앱이다.
- 계산 규칙과 불변식은 도메인·애플리케이션 서비스에 두고, HTTP와 SQLite는 어댑터로 유지한다.
- `actual` 시나리오(`id=1`)는 실제 장부를 나타내는 시스템 행이다. 이름 수정, 복제, 보관, 복원, 영구 삭제의 대상이 아니다.
- 시나리오의 기준 장부는 실제 장부로 고정한다. 중첩 시나리오와 기준 장부 변경은 범위 밖이다.
- 시작 기준일은 생성 후 바꾸지 않는다. 날짜를 바꾸려면 복제해 새 시나리오를 만든다.
- 실제 장부 규칙의 대체·제외는 현재 제공하지 않는다. 시나리오는 자기 규칙과 일회성 예정 거래만 추가한다.
- 보관은 이력 스냅샷이 아니다. 보관된 시나리오도 조회할 때 최신 실제 장부와 규칙으로 다시 계산한다.
- 최근 지출 평균이나 모델 추정값은 자동 반영하지 않는다. 사용자가 등록한 규칙과 예정 거래만 미래 계산에 사용한다.
- 화면은 `DESIGN.md`의 “잉크와 원장” 원칙을 따른다. 숫자와 계산 근거가 장식보다 먼저 보여야 한다.

## Premises

1. 시나리오는 실제 장부의 복사본이 아니라 `실제 장부의 기준 상태 + 최신 실제 반복 규칙 + 시나리오 전용 가정`으로 계산한다.
2. 시작 잔액은 저장된 스냅샷이 아니다. 차트를 계산할 때마다 시작 기준일의 실제 장부 마감 잔액을 다시 구한다.
3. 시작 기준일 당일의 실제 거래는 시작 잔액에 포함하고, 전망 규칙과 시나리오 예정 거래는 다음 날부터 적용한다.
4. 새로 만들거나 legacy 변환을 마친 시나리오는 실제 장부의 반복 규칙을 복사하지 않는다. 활성·보관 상태와 무관하게 조회 시 최신 실제 규칙을 사용한다.
5. 실제 규칙은 시나리오 화면에서 출처를 표시한 읽기 전용 항목이다. 시나리오 전용 규칙과 예정 거래만 그 시나리오에서 편집한다.
6. 이름과 설명은 수정 가능하다. ID, 실제 장부라는 기준, 시작 기준일, 생성 시각은 불변이다.
7. 보관은 활성 목록과 메인 대시보드 비교에서 제외하는 읽기 전용 상태다. 복원하면 다시 편집할 수 있다.
8. 영구 삭제는 보관된 시나리오에서만 가능하며, 시나리오가 소유한 규칙·예정 거래·분개를 모두 제거한다.
9. 순자산과 현금성 잔액은 다른 지표다. 대표 차트는 순자산이고, 같은 차트에서 현금성 잔액으로 전환할 수 있다.
10. 현금성 여부는 시나리오 설정이 아니라 최하위 계정의 전역 설정이다. 상위 그룹은 자식의 포함 현황만 요약한다.

## Approaches Considered

### Approach A: 한 페이지 연속 작업대

- **Summary:** 시나리오 요약, 차트, 규칙, 예정 거래, 기본 정보를 한 페이지에 세로로 배치한다.
- **Effort:** M
- **Risk:** Low
- **Pros:** 기존 `Scenarios.tsx` 인라인 편집 구조를 가장 많이 재사용하며 가장 작은 변경으로 출시할 수 있다. 모든 내용을 한 번에 훑을 수 있다.
- **Cons:** 규칙과 거래가 늘면 페이지가 길어지고 결과 확인과 편집 작업의 정보 위계가 섞인다.
- **Reuses:** 현재 시나리오 목록, `ScenarioEditor`, 기존 projection API와 표 컴포넌트.

### Approach B: 전용 페이지와 역할별 탭 — 선택

- **Summary:** 시나리오별 전용 경로에서 `개요`, `가정`, `정보` 탭을 제공한다. 생성 직후 `개요`로 이동하고, 결과 확인과 가정 편집과 수명주기 관리를 분리한다.
- **Effort:** XL, 네 stacked PR
- **Risk:** Medium
- **Pros:** 차트가 첫 화면의 주인공이 되고, 실제 규칙 대체 같은 미래 기능도 `가정` 탭 안에서 확장할 수 있다. 경로가 고정돼 새로고침·직접 링크·보관함 복귀 동작을 명확히 만들 수 있다.
- **Cons:** 라우팅과 로딩·오류 상태를 화면 단위로 다시 정리해야 하고, 가정 편집에는 탭 이동 한 번이 추가된다.
- **Reuses:** `build_projection`, `ScenarioRepository`, 계정 보관·복원의 상태 전환 패턴, `DESIGN.md`의 대시보드 작업대.

### Approach C: 목록·상세 분할 화면

- **Summary:** 왼쪽 시나리오 목록과 오른쪽 상세·차트를 동시에 유지한다.
- **Effort:** L
- **Risk:** High
- **Pros:** 여러 시나리오를 빠르게 전환할 수 있고 목록 맥락이 유지된다.
- **Cons:** 168px 전역 사이드바와 다시 충돌해 차트 폭이 좁아진다. 모바일에서 별도 내비게이션 모델이 필요하며 전용 페이지라는 사용자의 기대와 덜 맞는다.
- **Reuses:** 현재 목록과 열기 상태를 재사용할 수 있으나 레이아웃 재작업이 크다.

## Recommended Approach

### Information architecture

`/scenarios`는 활성 시나리오 목록과 생성 진입점만 담당한다. 시나리오 생성 성공 후 `/scenarios/{id}`의 `개요` 탭으로 이동한다.

- **개요:** 시작값, 선택 기간 종료값, 현재 패턴 유지와의 차이, 전망 비교 차트, 월별 수입·지출, 계산 근거.
- **가정:** 실제 장부 반복 규칙을 읽기 전용으로 표시하고, 시나리오 전용 반복 규칙과 일회성 예정 거래를 생성·수정·삭제한다.
- **정보:** 이름과 설명 수정, 불변인 시작 기준일 표시, 복제, 보관.
- **보관함:** 읽기 전용 시나리오 목록과 상세, 복원, 영구 삭제.

승인된 거친 와이어프레임: [시나리오 개요와 영구 삭제 확인](assets/scenario-lifecycle-wireframe.png)

### Delivery slices and stacked PRs

전체 설계는 하나지만 네 개의 stacked PR로 나눈다. 브랜치 의존 관계는
`scenario-liquidity → scenario-assumptions → scenario-lifecycle → scenario-foundation → main`이며,
병합은 반대 순서인 PR 1 → 2 → 3 → 4로 진행한다.

1. **Foundation:** 기능별 FastAPI router·SQLite repository 분리, 요청별 연결과 WAL, migration runner와 검증 백업, 시나리오 aggregate UoW, 오류 envelope를 먼저 배포한다.
2. **Lifecycle + net-worth + legacy resolution:** live-additive 규칙 해석, legacy 변환 API·화면, 시작일 경계, 이름·설명 수정, 보관·복원·영구 삭제, React Router 전환, 전용 상세와 순자산·월별 수입/지출을 함께 배포한다. 새 계산 방식과 변환 수단을 같은 PR에 넣어 legacy 사용자가 중간 상태에서 막히지 않게 한다.
3. **Assumptions:** 시나리오 복제와 일회성 예정 거래 CRUD를 배포한다.
4. **Liquidity:** 계정의 현금성 설정, 현금성 잔액 곡선과 부족 구간 진단을 별도 마이그레이션과 성능 게이트로 배포한다.

PR 2 완료 시 `capabilities.scenario_liquidity=false`이고 응답에 `cash`가 없으며 UI도 현금성 전환을 렌더하지 않는다. PR 4에서 capability와 `cash`를 함께 활성화한다. 필드가 없거나 알 수 없는 capability는 프론트에서 `false`로 처리한다. PR 4까지 완료되어야 이 문서 전체를 완료로 본다.

### Lifecycle transition policy

범용 상태 머신 프레임워크는 도입하지 않는다. `Scenario` 도메인 객체가 이름 변경, 보관, 복원, version 증가, actual 변경 금지 같은 자기 불변식을 소유한다. 복제·영구 삭제·날짜 충돌처럼 여러 저장소가 필요한 흐름은 application service가 조율하고, repository는 저장·조회, router는 HTTP 변환만 담당한다.

| 현재 상태 | 허용 동작 | 다음 상태 | 규칙 |
|---|---|---|---|
| 실제 장부 | 실제 거래·실제 규칙 관리 | 실제 장부 | 시나리오 수명주기 동작은 모두 거부 |
| 활성 시나리오 | 조회, 이름·설명 수정, 가정 편집, 복제, 보관 | 활성 또는 보관 | 영구 삭제 버튼을 노출하지 않음 |
| 보관 시나리오 | 읽기 전용 조회, 복원, 영구 삭제 | 활성 또는 삭제됨 | 수정 API도 서버에서 거부 |
| 삭제됨 | 없음 | 없음 | 물리 삭제되어 복원 불가 |

보관 성공 시 활성 목록, 메인 대시보드의 비교 선택, 브라우저에 저장된 `chartToggles`에서 제거하고 보관함 상세로 이동한다. 복원 성공 시 최신 실제 장부와 규칙으로 다시 계산해 활성 상세의 `개요`로 이동한다.

### Scenario identity and effective assumptions

시나리오 엔티티의 불변 필드는 `id`, `base_scenario_id`, `fork_date`, `created_at`이다. `base_scenario_id`는 모든 사용자 시나리오에서 `ACTUAL_SCENARIO_ID`여야 한다. 수정 가능한 필드는 `name`, `description`뿐이며 `status`, `archived_at`, `version`은 서버가 상태 전환 과정에서 관리한다.

전망 계산에 사용할 최종 규칙 목록은 작은 순수 도메인 서비스 `EffectiveRuleResolver` 한 곳에서 조립한다. 이 서비스만 `rule_mode`를 이해하며 projection 계산은 이미 해석된 규칙만 받는다.

1. `live_additive`는 실제 장부의 현재 반복 규칙과 시나리오 전용 규칙을 읽는다.
2. `legacy_snapshot`은 변환 전 기존 시나리오 규칙만 읽어 이중 계산을 막는다.
3. 각 규칙에 `origin=actual|scenario`, `editable=true|false` 메타데이터를 붙인다.
4. 기준 전망은 실제 규칙만 사용한다.
5. 시나리오 전망은 resolver가 반환한 유효 규칙을 사용한다.

새 시나리오는 실제 규칙을 복사하지 않는 `create_scenario()`로 생성하며 기존 `fork_scenario()` 호환 wrapper는 남기지 않는다. 모든 legacy 변환이 끝나면 resolver의 `legacy_snapshot` 분기만 제거할 수 있어야 한다.

시나리오 화면은 실제 규칙에 수정·삭제 동작을 렌더하지 않는다. 쓰기 API도 요청한 규칙의 `scenario_id`와 경로의 시나리오 ID가 일치하는지 검사해 다른 시나리오나 실제 규칙의 변경을 거부한다. 미래에 대체·제외가 필요해지면 이 조립 단계 사이에 별도 override 계층을 추가하되 현재는 테이블이나 API를 만들지 않는다.

### Projection contract

모든 전망은 같은 기준에서 갈라진다.

- `start_balance`: 선택 metric에 맞춰 `fork_date` 종료 시점의 게시 완료된 실제 장부 거래로 다시 계산한다. 순자산은 자산·부채 합, 현금성 잔액은 선택한 현금성 자산 계정 합이다.
- `projection_start`: `fork_date + 1 day`.
- `projection_end`: `fork_date`에 선택한 3·6·12 calendar months를 더한 날짜이며 양 끝을 포함한다. 존재하지 않는 말일은 `add_months()`가 그 달의 마지막 날로 당긴다. 예를 들어 1월 31일 + 3개월은 4월 30일이다.
- 기준 전망: `start_balance + 실제 반복 규칙`.
- 시나리오 전망: `start_balance + 실제 반복 규칙 + 시나리오 전용 규칙 + 시나리오 일회성 예정 거래`.
- 실제 장부의 `fork_date` 이후 거래는 두 전망에 섞지 않는다.
- 최근 3개월 변동지출 평균은 계산하지 않는다.

모든 날짜는 서버의 `Asia/Seoul` local date이며 timestamp로 경계를 나누지 않는다. `fork_date`는 오늘 또는 과거만 허용한다. 미래 날짜의 실제 마감 잔액은 확정할 수 없으므로 미래 fork는 `422`로 거부한다. 실제 장부의 `fork_date` 이전 또는 당일 거래를 나중에 정정하면 시작값과 두 전망이 함께 바뀐다. 실제 반복 규칙을 수정·추가·삭제하면 활성·보관 시나리오의 다음 조회부터 두 전망에 반영된다.

규칙 발생일은 `[projection_start, projection_end]`와 규칙의 `[start_date, end_date]`가 겹치는 구간에서만 전개한다. 새 fork보다 일찍 시작한 반복 규칙은 projection start부터 이어지고, 새 fork 이전에 끝난 규칙은 0회로 계산한다. 시나리오 전용 예정 거래는 반드시 `date > fork_date`여야 하며 선택한 화면 기간 밖의 거래도 보존하되 현재 차트에는 나타나지 않는다.

전망은 규칙을 메모리에서 발생일로 전개하는 순수 계산만 사용한다. `materialize`가 만든 실제 거래는 fork 마감 잔액에만 들어가고, 미래 projection 입력에는 들어가지 않는다. 시나리오 규칙은 거래로 materialize하지 않는다. 과거 copy-on-fork가 만든 규칙 발생 거래가 있으면 마이그레이션 단계에서 legacy 규칙과 함께 분류하며, 규칙 전개와 저장 거래를 동시에 더하지 않는다.

시나리오에 전용 규칙이나 예정 거래가 하나도 없으면 두 전망은 동일하다. 빈 화면 대신 `아직 시나리오 전용 가정이 없습니다`와 `가정 추가` 진입점을 보여주며, 동일한 두 선을 겹쳐 그리지 않는다.

### Monthly income and expense contract

월별 수입·지출은 projection과 동일한 발생 항목을 calendar month별로 묶는다. 첫 달과 마지막 달은 projection 범위에 포함된 날짜만 집계한다.

- `income`: income 계정 posting 합계에 `-1`을 곱해 자연 양수로 표시한다.
- `expense`: expense 계정 posting 합계를 그대로 자연 양수로 표시한다.
- 자산↔자산, 자산↔부채처럼 수익·비용 계정이 없는 이체는 두 값에서 제외한다.
- 환불이나 취소로 월 순수입·순지출이 음수가 될 수 있으며 0으로 잘라내지 않는다.
- 기준 막대는 실제 규칙만, 시나리오 막대는 실제 규칙·시나리오 규칙·일회성 예정 거래를 사용한다.
- 같은 발생 항목을 순자산, 현금성 잔액, 월별 수입·지출 계산에서 한 번 전개한 뒤 공유해 서로 다른 숫자가 나오지 않게 한다.

projection 응답의 `monthly_income_expense`는 다음 모양이다. 이는 현금 계정의 입출금이 아니라 수익·비용 계정 기준이므로 `cashflow`라고 부르지 않는다.

```json
{
  "month": "2026-10",
  "baseline": {"income": 3200000, "expense": 1450000},
  "scenario": {"income": 3700000, "expense": 1450000}
}
```

### Net-worth and liquidity views

`순자산`이 기본 지표다. 같은 차트의 분할 제어로 `현금성 잔액`으로 전환하며, 기간 선택은 `3개월`, `6개월`, `12개월`이고 기본값은 6개월이다.

현금성 잔액은 `include_in_cash=true`인 활성 최하위 자산 계정의 표시 잔액 합계다. 그룹·수익·비용·자본·시스템 계정에는 이 설정을 허용하지 않는다. 계정 간 이동에서 양쪽 모두 현금성 계정이면 총액 변화는 0이고, 한쪽만 현금성이면 해당 posting만 현금 곡선에 반영한다.

`include_in_cash=true`로 바꾸는 요청은 active, non-system, non-placeholder asset이고 활성·보관 자식이 하나도 없는 계정에만 허용한다. leaf 판정에는 보관된 자식도 포함한다. 선택된 계정에 새 자식을 만들거나 다른 계정을 reparent하거나 보관된 자식을 복원하는 요청은 `409 cash_account_parent_forbidden`으로 거부한다. 선택된 계정 자체를 placeholder로 바꾸면 `409 cash_account_must_be_leaf`, 보관하면 `409 cash_account_selected`로 거부하고 먼저 설정을 끄게 한다. 같은 자산 유형 안에서 leaf 상태를 유지하는 선택 계정의 reparent는 값을 보존한다. 서버는 create, seed, reparent, placeholder, archive, restore, cash-setting writer 모두에서 이 불변식을 검사하며 설정을 조용히 해제하지 않는다.

선택된 현금성 계정이 없으면 0원 차트를 그리지 않는다. `현금 부족 계산에 포함할 계정을 먼저 선택하세요`와 계정과목 설정 링크를 보여준다. 앱은 근거 없는 `안전/위험` 등급을 부여하지 않는다.

현금 부족은 일 마감 잔액으로 판정한다. 같은 날의 모든 발생 항목을 합산한 뒤 0원 미만이면 부족일이다. 첫 부족 구간의 시작일, 0원 이상으로 회복한 전날, 일수, 전체 전망에서 가장 낮은 잔액과 날짜를 반환한다. 전망 종료일까지 회복하지 못하면 `through_horizon=true`와 `end=null`을 반환한다. 같은 날 여러 항목이 처음 부족을 만들면 임의의 원인 하나를 고르지 않고 날짜·규칙 ID·예정 거래 ID 순으로 정렬한 그날의 모든 항목을 `triggering_items`로 반환한다.

```json
{
  "first_shortage": {
    "start": "2026-11-25",
    "end": "2026-11-29",
    "days": 5,
    "through_horizon": false,
    "triggering_items": [{"kind": "planned_transaction", "id": 42, "label": "이사 보증금"}]
  },
  "maximum_shortage": {"date": "2026-11-28", "balance": -620000}
}
```

계정과목의 최하위 자산 계정 설정에 다음 항목을 추가한다.

> 현금 부족 계산에 포함 — 이 계정의 잔액을 즉시 사용할 수 있는 자금으로 계산합니다.

상위 그룹은 `하위 3개 중 2개 포함`처럼 집계만 표시한다. 이름이나 계정 종류로 현금성을 추측하지 않으며, 기존 계정은 마이그레이션 후 모두 미선택으로 시작해 사용자가 명시적으로 결정한다. 표준 계정과목을 새로 시드할 때도 사용자 확인 없이 자동 선택하지 않는다.

### Create, update, and duplicate

생성 입력은 이름, 선택형 설명, 시작 기준일이다. 시작일 기본값은 오늘이며 생성 후 바꿀 수 없다. 생성 과정에서 실제 규칙을 복사하지 않는다. 응답은 scenario DTO와 현재 적용되는 실제 규칙 개수를 반환한다.

이름·설명 저장은 현재 계정 설정에서 쓰는 `version` 기반 낙관적 동시성 패턴을 재사용한다. 오래된 탭은 최신 값을 덮어쓰지 않고 `409 scenario_version_conflict`를 받으며, 입력값을 유지한 채 다시 불러오기를 안내한다.

복제는 새 ID의 활성 시나리오를 만든다. 사용자는 새 이름과 시작 기준일을 확정하고, 설명·전용 반복 규칙·일회성 예정 거래를 한 트랜잭션에서 복사한다. 실제 규칙은 복제하지 않는다. 트랜잭션을 연 뒤 source scenario가 활성이고 제출한 source version과 정확히 같은지 먼저 확인하고, 일치할 때 읽은 자식만 복사한다. 새 시작일보다 이르거나 같은 예정 거래가 있으면 자동 누락하지 않고 `409 scenario_duplicate_date_conflict`와 해당 거래 목록을 반환해 사용자가 날짜를 다시 선택하게 한다. version 또는 날짜 검증 실패 시 새 scenario row도 남기지 않는다.

### Scenario-owned assumptions

시나리오 전용 반복 규칙은 기존 `recurring_rules`에 `scenario_id=<scenario>`로 저장한다. 일회성 예정 거래는 기존 `transactions`와 `postings`를 재사용한다.

- `scenario_id`는 URL의 시나리오 ID와 같아야 하고 actual일 수 없다.
- 일회성 예정 거래는 `source_rule_id=NULL`, `posted=1`인 균형 거래다. `scenario_id != 1`이므로 실제 장부 materialization이나 잔액에는 절대 들어가지 않는다.
- projection은 이 저장 거래를 일회성 입력으로 한 번 사용한다. 반복 규칙에서 미래 거래를 별도로 저장하지 않는다.
- 생성·수정은 transaction과 postings 전체를 원자적으로 저장하고, 수정 시 기존 posted 거래를 같은 DB 트랜잭션 안에서 잠시 unpost한 뒤 postings를 교체하고 다시 검산한다.
- 규칙·예정 거래를 생성·수정·삭제할 때 소유 시나리오가 활성이고 제출 version과 일치하는지 확인한다. application service는 같은 트랜잭션에서 scenario version을 조건부로 정확히 1회 증가시키며 child row의 내부 unpost·repost 횟수는 version에 추가로 반영하지 않는다.
- 삭제는 URL 소유권을 검사하고 실제 규칙, 실제 거래, 다른 시나리오의 항목을 거부한다.

CRUD는 `/api/scenarios/{scenario_id}/rules`와 `/api/scenarios/{scenario_id}/planned-transactions` 아래로 노출한다. list는 실제 규칙을 섞지 않은 소유 데이터만 반환하며, 화면이 함께 보여줄 실제 읽기 전용 규칙은 `effective-rules`에서 가져온다.

### Transaction ownership

현재 SQLite repository의 `save()`가 자체 commit하므로 복제, child mutation + scenario version, legacy 변환, 영구 삭제를 원자적으로 묶을 수 없다. PR 1에서 시나리오 aggregate 경로에 명시적 `SqliteUnitOfWork`를 추가하고 transaction 경계를 application service가 소유하게 한다. 시나리오 내부 writer primitive는 commit하지 않으며 UoW가 최종 commit한다. 기존 계정 설정·materialize 경계는 현재 동작을 유지하고 `commit=True/False` flag는 추가하지 않는다. 두 번째 실제 cross-repository 유스케이스나 중복 경계가 관측되기 전에는 전 repository를 UoW로 전환하지 않는다.

런타임은 앱 전체 `asyncio.Lock`과 단일 연결을 제거하고 FastAPI dependency가 요청별 SQLite 연결을 제공한다. 파일 DB는 migration과 검증 백업을 마친 뒤 WAL을 사용한다. projection은 명시적 read transaction, 쓰기는 `BEGIN IMMEDIATE`를 사용하며 `busy_timeout`과 구조화된 busy 오류를 유지한다. FastAPI handler는 raw SQL 순서나 commit을 직접 조립하지 않는다.

### Archive, restore, and permanent delete

보관과 복원은 `version`을 요구하는 명시적 상태 전환이다. 활성 시나리오만 보관할 수 있고 보관 시나리오만 복원할 수 있다. 서버는 actual 보호와 존재 여부를 먼저 검사하고, 이미 요청한 목표 상태라면 제출한 version이 오래됐어도 현재 DTO를 `200`으로 반환한다. 아직 상태 전환이 필요할 때만 version의 정확한 일치를 요구한다. 보관 중에는 이름·설명·규칙·예정 거래 쓰기를 모두 `409 scenario_archived_read_only`로 거부한다.

영구 삭제는 두 단계다.

1. 삭제 영향 조회가 시나리오 이름, 전용 반복 규칙 수, 일회성 예정 거래 수, legacy generated 거래 수, 연결된 postings 수, 현재 aggregate `version`을 반환한다. `live_additive`에서는 generated 수가 항상 0이다.
2. 확인 창은 이름과 개수를 보여주고 `영구 삭제`를 한 번 누르게 한다. 이름 재입력은 요구하지 않는다.

aggregate `version`은 이름·설명·상태뿐 아니라 시나리오 소유 규칙과 예정 거래의 생성·수정·삭제 때도 같은 트랜잭션에서 증가한다. 삭제 영향 조회는 body의 version과 함께 리소스별 strong ETag(예: `"scenario-7-v6"`)를 반환한다. DELETE는 받은 ETag를 `If-Match`로 그대로 보내며, 현재 representation과 다르면 `412 scenario_version_conflict`와 최신 영향 정보를 반환한다. 다른 시나리오의 ETag도 일치하지 않는다. 프론트는 자동 재삭제하지 않고 변경된 영향을 보여준 뒤 사용자의 두 번째 명시적 확인을 요구한다.

DELETE는 보관 상태와 version을 다시 확인한 뒤 SQLite `BEGIN IMMEDIATE` 안에서 모두 처리한다.

1. 시나리오 거래를 `posted=0`으로 바꿔 posting 삭제 방지 트리거와 충돌하지 않게 한다.
2. 시나리오 거래의 postings를 삭제한다.
3. 시나리오 거래를 삭제한다.
4. 시나리오 전용 반복 규칙을 삭제한다.
5. 시나리오 행을 삭제하고 commit한다.

어느 단계든 실패하면 전체 rollback한다. 스키마를 재구축해야 하는 광범위한 `ON DELETE CASCADE` 도입은 하지 않는다. 실제 장부나 다른 시나리오 ID를 가진 행은 삭제 쿼리의 대상이 될 수 없다.

삭제 성공 후 확인 창을 닫고 보관함 목록으로 이동하며 `반복 규칙 2개와 예정 거래 1개를 포함해 시나리오를 영구 삭제했습니다`처럼 결과를 표시한다. legacy generated 거래가 있으면 그 개수도 별도 줄로 보여준다. 실패하면 확인 창과 목록을 그대로 유지한다. legacy 변환 여부와 무관하게 보관 후 영구 삭제할 수 있다.

### API contract

모든 endpoint를 `account`, `transaction`, `rule`, `scenario`, `reporting` feature router로 분리하고 `api.py`는 app factory·middleware·조립만 담당한다. 구조 이동은 동작 변경과 분리해 기존 method/path 회귀 테스트를 먼저 통과시킨다. 기존 `/api/transactions`와 `/api/rules`는 actual 전용으로 고정하고 시나리오 소유 데이터는 아래 nested endpoint만 사용한다. URL이 소유권의 유일한 출처이며 body의 `scenario_id`는 받지 않는다.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/scenarios?status=active|archived` | 상태별 목록. actual은 별도 시스템 항목으로 취급 |
| `POST` | `/api/scenarios` | 이름·설명·시작일로 생성, 규칙 복사 없음 |
| `GET` | `/api/scenarios/{id}` | 상세와 불변·상태 메타데이터 |
| `PATCH` | `/api/scenarios/{id}` | 이름·설명만 version과 함께 수정 |
| `POST` | `/api/scenarios/{id}/duplicate` | 새 이름·시작일로 전용 가정 복제 |
| `POST` | `/api/scenarios/{id}/archive` | 활성 → 보관 |
| `POST` | `/api/scenarios/{id}/restore` | 보관 → 활성 |
| `GET/POST` | `/api/scenarios/{id}/legacy-rule-resolution` | 기존 복사 규칙 분류 조회·원자적 확정 |
| `GET` | `/api/scenarios/{id}/deletion-impact` | 영구 삭제 영향과 version 조회 |

목록은 로컬 단일 사용자 앱이므로 현재 범위에서는 pagination 없이 전부 반환한다. 활성 목록은 `created_at DESC, id DESC`, 보관함은 `archived_at DESC, id DESC`로 정렬한다. 100개 시나리오 fixture를 목록 성능 테스트에 포함하고, 실제 사용에서 이를 넘겨 문제가 확인될 때 cursor pagination을 추가한다.

legacy 분류 조회는 `legacy_rule_id`, 규칙 내용, 구조가 비슷한 actual 참고 후보, 날짜 충돌이 있는 legacy transaction을 반환하되 자동 선택하지 않는다. 확정 body는 모든 legacy rule과 충돌 거래를 빠짐없이 한 번씩 분류하고 scenario version을 포함한다.


실제 후보는 설명용일 뿐 변환 전제나 저장 참조가 아니므로 후보 actual rule의 변경은 stale 조건이 아니다. legacy rule·transaction 또는 scenario version이 조회 뒤 바뀌면 `409 legacy_rule_resolution_stale`로 전체를 거부한다. 성공 시점의 최신 actual 규칙 전체가 live base가 된다. 성공 응답은 변환된 `ScenarioDto`, 제거·보존한 규칙, 제거·이동한 transaction 개수를 반환한다.

삭제 영향과 DELETE 계약:

```json
{
  "scenario_id": 7,
  "name": "이직 후 월급 400만 원",
  "rules": 2,
  "planned_transactions": 1,
  "generated_transactions": 0,
  "postings": 2,

```

영향 조회는 body와 함께 `ETag: "scenario-7-v6"`을 반환하고, 클라이언트는 `DELETE /api/scenarios/7`에 `If-Match: "scenario-7-v6"`을 그대로 보낸다. 성공은 `{"deleted":7,"rules":2,"planned_transactions":1,"generated_transactions":0,"postings":2}`다. 헤더 누락은 `428 scenario_version_required`, 따옴표 없는 값·weak ETag·wildcard·복수 ETag는 `400 invalid_scenario_version`, 문법은 맞지만 다른 시나리오 또는 오래된 ETag는 `412 scenario_version_conflict`다.

projection은 `GET /api/projection?scenario_id=7&months=6` 형식을 사용한다. `scenario_id`는 정확히 하나이며 활성·보관 모두 조회할 수 있다. 서버는 한 SQLite read transaction에서 scenario version과 calculation revision을 먼저 읽고, 시작 잔액·규칙·예정 거래·계정 설정을 같은 snapshot으로 조립한다.

curve는 fork 마감 시작점, 잔액이 변한 각 날짜의 일 마감, projection end terminal point를 포함한다. 한 날짜의 개별 항목에는 장중 순서가 없으므로 차트 점을 항목마다 만들지 않고 날짜별로 합산한다. 개별 `ProjectionEvent`는 툴팁·부족 원인·월별 집계를 위해 보존한다. UI는 점 사이를 직선 보간하지 않고 계단선으로 그린다. 각 point는 `{"date":"2026-10-31","balance":43180000}` 형식이며 12개월 payload는 최대 약 367개 날짜로 제한된다.

애플리케이션 오류는 모두 `{"detail":{"code":"...","message":"...",...context}}` envelope를 사용하며 프론트 `ApiError`는 context 전체를 보존한다. ### Data model and migration

PR 1에서 `PRAGMA user_version` 기반의 순서 있는 migration runner를 도입한다. pending migration이 있을 때만 기존 DB를 migration 전용 이름의 `.partial` 파일로 온라인 백업하고, `PRAGMA integrity_check`, SHA-256 기록, 파일 동기화와 close를 마친 뒤 최종 이름으로 원자적으로 rename한다. migration backup은 daily backup과 prefix·보존 정책을 분리해 daily rotation이 삭제하지 못하게 한다. 백업 실패는 스키마 변경 전에 앱 기동을 중단한다.

각 migration과 `user_version` 증가는 같은 transaction에서 실행한다. 중간 실패는 해당 migration을 전부 rollback하고 앱 기동을 중단한다. 같은 날 daily backup이 있어도 pending migration backup을 생략하지 않으며, pending migration이 없는 일반 기동은 migration backup을 새로 만들지 않는다. WAL 전환은 검증 백업과 migration 완료 뒤에 수행한다.

`scenarios`에 다음 필드를 추가한다.

```sql
description TEXT NOT NULL DEFAULT '',
status      TEXT NOT NULL DEFAULT 'active' CHECK(status IN ('active','archived')),
archived_at TEXT,
version     INTEGER NOT NULL DEFAULT 1 CHECK(version > 0),
rule_mode   TEXT NOT NULL DEFAULT 'live_additive' CHECK(rule_mode IN ('live_additive','legacy_snapshot'))
```

`accounts`에는 최하위 자산 계정의 현금성 포함 여부를 저장한다.

```sql
include_in_cash INTEGER NOT NULL DEFAULT 0 CHECK(include_in_cash IN (0,1))
```

projection이 어떤 실제 장부 상태를 읽었는지 식별하도록 singleton revision row를 추가한다.

```sql
CREATE TABLE calculation_revisions (
  id                     INTEGER PRIMARY KEY CHECK(id = 1),
  actual_ledger_revision INTEGER NOT NULL DEFAULT 1,
  actual_rule_revision   INTEGER NOT NULL DEFAULT 1,
  cash_config_revision   INTEGER NOT NULL DEFAULT 1
);
```

actual transaction의 insert/update/delete는 ledger revision, actual recurring rule의 insert/update/delete는 rule revision, `include_in_cash` 변경은 cash config revision을 증가시킨다. 이 세 global revision에는 SQLite trigger를 누락 방지 백스톱으로 두며 한 사용자 동작에서 값이 두 번 이상 증가해도 허용한다. 이 값은 변경 순서를 식별하는 단조 증가 token이지 사용자에게 보여주는 편집 횟수가 아니다.

반면 scenario aggregate version에는 child trigger를 두지 않는다. 이름·설명·상태·시나리오 규칙·예정 거래를 바꾸는 application service가 `UPDATE scenarios SET version=version+1 WHERE id=? AND version=?`를 한 번 실행하고 rowcount가 1일 때만 같은 transaction의 child 쓰기를 진행한다. validation 또는 child 쓰기가 실패하면 bump도 rollback한다. 따라서 planned transaction 수정 과정의 내부 unpost·post와 postings 교체가 있더라도 외부에서 관찰되는 version은 명령당 정확히 1 증가한다.

보관 스냅샷 테이블과 실제 규칙 연결 테이블은 만들지 않는다. `recurring_rules.scenario_id=1`은 실제 규칙이고, `live_additive` 시나리오의 그 외 ID는 해당 시나리오가 소유한 추가 규칙이라는 기존 소유 관계를 사용한다. actual 행에는 `rule_mode=live_additive`를 쓰되 이 값은 계산에서 무시한다.

기존 copy-on-fork 규칙에는 원본 actual rule ID가 저장돼 있지 않아 복사본과 사용자가 추가한 규칙을 일반적으로 구분할 수 없다. 이름·금액·일정이 같다는 이유로 추측해 삭제하면 안 된다. 마이그레이션은 다음 순서로 데이터 손실과 이중 계산을 막는다.

1. 검증된 migration backup을 만든 뒤 actual·시나리오별 규칙 및 `source_rule_id`가 있는 시나리오 거래 개수를 진단 로그에 남긴다.
2. 기존 non-actual 시나리오는 우선 `rule_mode=legacy_snapshot`으로 표시해 기존처럼 자기 규칙만 계산한다. 이 상태에서는 새 실제 규칙을 더하지 않아 이중 계산이 없다.
3. actual 규칙과 시나리오 규칙 중 한쪽이 0개인 시나리오는 의미가 모호한 clone 충돌이 없으므로 기존 시나리오 규칙을 local addition으로 보존하고 `live_additive`로 자동 전환한다. 현재 로컬 DB의 actual 규칙 0개와 시나리오 `id=2` 규칙 1개가 이 경로다.
4. 양쪽에 규칙이 모두 있으면 자동 추론하지 않는다. 한 번만 표시되는 변환 화면에서 각 legacy rule을 `snapshot 폐기` 또는 `시나리오 추가로 유지`로 사용자가 분류한다. 화면은 구조가 비슷한 현재 actual rule을 참고 후보로 보여줄 수 있지만 저장하거나 요구하지 않는다. `snapshot 폐기`는 원본 actual rule이 수정·삭제됐더라도 해당 legacy row를 명시적으로 제거한다. 규칙 간 one-to-one mapping은 만들지 않는다.
5. legacy scenario transaction 중 `source_rule_id IS NOT NULL`인 행은 과거 규칙 발생분이므로 분류 완료 트랜잭션에서 unpost·삭제한다. `source_rule_id IS NULL`이면서 `date > fork_date`인 균형 거래는 일회성 예정 거래로 보존한다. `date <= fork_date`인 행은 각 거래마다 새 날짜로 이동하거나 삭제하도록 선택하게 하며 하나라도 미결정이면 변환을 차단한다.
6. 모든 규칙·거래 선택과 삭제·날짜 변경, `rule_mode=live_additive`, version 증가는 한 트랜잭션으로 commit한다. 취소·실패하면 `legacy_snapshot` 상태와 기존 계산을 그대로 유지한다.

`legacy_snapshot`은 호환 전용 상태다. 이름·설명·보관·삭제는 가능하지만 새 가정 편집과 새 전용 대시보드는 변환 완료 전까지 잠근다. 변환 API와 화면은 live-additive 계산을 여는 PR 2에 함께 포함하고, 모든 시나리오가 변환되면 후속 정리 PR에서 mode와 호환 분기를 제거할 수 있다.

`fork_scenario()`의 actual 규칙 복사 루프를 제거하고, 기존 projection의 `variable_monthly_spend()` 적용을 새 계약에서 제외한다. 현재 `SqliteLedgerQueries`의 fork 당일 예외 조건도 “actual 마감은 fork 당일까지 전부 포함, projection은 다음 날 시작”으로 단순화한다.

### Performance envelope

전용 상세 API는 한 요청에 시나리오 하나만 계산한다. projection 전용 read model은 같은 read transaction에서 scenario·revision, `date <= fork_date`의 계정별 시작 잔액 집계, actual/scenario 규칙 batch, 예정 거래와 postings join을 고정된 수의 SQL로 읽어 불변 `ProjectionInputs`를 만든다. 거래마다 postings를 다시 읽는 범용 `TransactionRepository.find_by_scenario()` N+1 경로는 projection에서 사용하지 않는다.

불변 `ProjectionEvent`는 날짜, 출처 kind/id/label, 균형 postings를 가진다. 기준·시나리오 규칙과 예정 거래를 한 번만 발생 항목으로 전개하고 한 번 정렬한 뒤 순자산, 현금성 잔액, 월별 집계, 부족 설명이 공유한다. 같은 날짜는 일 마감으로 합산한다. 초기에는 결과 cache를 두지 않아 실제 장부 변경이 즉시 보이게 한다.

대표 benchmark fixture는 계정 250개, actual 게시 거래 50,000개, actual 규칙 200개, 시나리오 규칙 100개, 예정 거래 500개, 12개월 기간이다. 기준 환경은 Apple M2 Pro arm64, macOS 26.5.1, Python 3.14.6, SQLite 3.51.0, APFS의 임시 file DB, 단일 프로세스다.

`cd backend && uv run python tests/benchmark_projection.py --warmups 5 --samples 30 --months 12`를 표준 명령으로 둔다. fixture 생성은 측정에서 제외하고 같은 warm connection으로 5회 예열 뒤 30회 측정해 nearest-rank p95를 출력한다. sqlite trace callback으로 request별 SQL statement 수도 기록한다. PR 2는 net-worth + monthly-income-expense service p95 300ms, 상세 API p95 500ms, 15 SQL statements 이하가 gate다. PR 4는 같은 요청에 cash curve와 두 shortage 결과를 추가한 전체 payload로 동일한 시간 기준과 18 statements 이하를 만족해야 한다.

저장소에 일반 test/build CI와 projection 관련 경로가 바뀔 때만 실행되는 performance job을 추가한다. 같은 runner에서 base와 head benchmark를 연속 실행해 head p95가 base보다 25% 넘게 느려지면 실패시키고 결과 JSON을 artifact로 보존한다. SQL statement 제한은 CI의 절대 gate이며, M2 Pro의 300ms·500ms는 기준 장비의 절대 gate이자 CI의 참고값이다.

기존 `idx_txn_scenario_date`, `idx_postings_txn`, `idx_postings_account`를 재사용하고 `recurring_rules(scenario_id)`, `scenarios(status, archived_at)` 인덱스를 추가한다. benchmark가 기준을 넘기기 전에는 cache나 materialized projection 테이블을 도입하지 않는다. 나중에 cache가 필요하면 actual ledger revision, actual rule revision, cash config revision, scenario aggregate version, months를 모두 key에 포함해야 한다.

### UI states and accessibility

- React Router의 중앙 route table로 대시보드, 계정, 거래, 규칙, 시나리오 목록·상세·보관함·404를 모두 관리한다. 로컬 `view` 상태와 URL router를 섞지 않는다.
- 프론트 API는 `api/core`의 공통 request·구조화 `ApiError`와 `accounts`, `transactions`, `rules`, `scenarios`, `reporting` feature 모듈로 나눈다. 범용 SDK 계층은 만들지 않는다.
- 공통 request는 `AbortSignal`을 받고 화면의 query effect는 이전 요청과 unmount 요청을 취소한다. 취소는 오류 알림으로 보이지 않으며 화면은 `loading/error/empty/ready`를 명시적으로 구분한다.
- 로딩 중에는 이전 숫자를 새 결과처럼 유지하지 않고 차트와 요약에 계산 중 상태를 표시한다.
- projection 실패 시 이름·가정 편집 영역은 유지하고, 개요 안에서 다시 계산할 수 있게 한다.
- 긴 이름은 상세 제목에서 두 줄까지 허용하고 목록에서는 말줄임과 전체 이름 tooltip을 제공한다.
- 탭은 키보드 방향키와 Tab으로 이동할 수 있고 현재 탭, 보관 상태, 읽기 전용 이유를 스크린리더에 전달한다.
- 영구 삭제 확인 창은 제목에 초기 포커스를 두고 `Escape`, 취소, backdrop으로 닫을 수 있다. 삭제 중 버튼을 비활성화하고 성공 후 보관함 제목으로 포커스를 돌린다.
- 위험색은 영구 삭제와 실제 현금 부족에만 사용한다. 기준 전망과 시나리오는 색과 선 스타일을 함께 사용한다.
- 720px 이하에서는 요약값을 한 열로 쌓고, 차트 제어는 두 줄로 감싸며, 탭은 가로 스크롤 대신 세 항목이 모두 보이게 유지한다.

```text
          └─ application service / deterministic guards
              ├─ Scenario domain invariants
              ├─ EffectiveRuleResolver
              ├─ SqliteUnitOfWork (scenario aggregate writes)
              └─ ProjectionInputReader (single read snapshot)
                    └─ ProjectionInputs
                        └─ ProjectionEvent[] (expand and sort once)
                            ├─ net-worth daily close
                            ├─ cash daily close
                            ├─ monthly income / expense
                            └─ shortage explanation
```

SQLite runtime flow:

```text
startup: pending user_version?
  ├─ no  → open runtime connections
  └─ yes → .partial backup → integrity/checksum/fsync → atomic rename
           → one migration transaction + user_version → WAL

read request  → request-scoped connection → BEGIN read snapshot → close
write request → request-scoped connection → BEGIN IMMEDIATE UoW → commit/rollback → close
```

### Failure modes and required behavior

| Failure | Required behavior |
|---|---|
| migration backup permission·disk·integrity failure | schema를 만지기 전에 startup 중단, `.partial`은 복구본으로 취급하지 않음 |
| migration statement failure | 해당 migration과 `user_version` rollback, 검증된 backup 유지, startup 중단 |
| SQLite busy | timeout 뒤 구조화 오류, 부분 commit 없음 |
| duplicate·child mutation·legacy conversion·delete 중간 실패 | aggregate version과 모든 child row rollback, actual·타 시나리오 불변 |
| stale body version | `409 scenario_version_conflict`, 사용자 입력 보존 |
| stale 또는 다른 resource ETag | `412 scenario_version_conflict`, 최신 impact 표시 후 재확인 |
| archived write | version 비교보다 먼저 `409 scenario_archived_read_only` |
| 빠른 기간 전환의 늦은 응답 | 이전 request abort, 최신 선택만 렌더 |
| projection 중 actual writer | 응답은 변경 전 또는 변경 후 하나의 snapshot, revision과 숫자 일치 |
| liquidity capability 없음·unknown | 현금 toggle과 `cash` 소비를 모두 비활성화 |
| 현금성 계정 없음 | 0원 curve 대신 `cash_accounts_not_configured` 안내 |
