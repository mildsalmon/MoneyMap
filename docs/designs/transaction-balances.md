# 거래 후 잔고 저장과 조회

2026-11-15 · feature/account-history-filter · 사용자 요청에 따라 일상 구현 판단은 위임된 범위에서 진행한다.

- 목적: 선택 계정의 각 거래 직후 잔고를 보여주고, 대시보드가 같은 과거 거래를 반복 합산하는 비용을 줄인다.
- 비교안 A: 조회마다 누적 SQL. 가장 작은 변경이지만 잔고를 저장·재사용하려는 요구와 반복 계산 비용은 해결하지 않는다.
- 비교안 B(선택): 실제 거래별 계정·통화 단위 누적 잔고를 별도 파생 테이블에 저장한다. 거래 원본은 유지하며 SQLite 트리거가 같은 쓰기 트랜잭션에서 뒤쪽 잔고에 증감분을 반영한다. 최신순 조회도 거래일·ID 오름차순의 거래 직후 값이다.
- 비교안 C: 일별 체크포인트와 조회시 재생. 대량 소급 입력에 유리하지만 거래별 잔고를 바로 읽을 수 없고 경계·복구 규칙이 늘어난다.
- 같은 날짜는 거래 ID로 순서를 고정한다. 날짜/태그/페이지 조건과 무관한 전체 실제 장부 누적값이다. 과거 삽입·수정·삭제·계정 변경은 기존/새 계정의 이후 값을 원자적으로 보정한다. 반복 생성·개시잔액·할부·이관도 같은 posted 경계를 통과한다.
- 저장 범위는 actual의 posted 거래다. 통화는 분리하고 내부 raw 부호를 보존한다. 잔고 표시는 계정 유형의 자연 부호(부채·수익·자본 반전)를 적용한다. 흐름의 빨강/파랑 증감 표시는 기존 기준을 유지한다.
- 계정으로 필터한 거래내역에 `거래 후 잔고` 열을 추가한다. 그룹은 현재 하위 범위의 거래 직후 잔고를 통화별로 합산하며 보관 후손·과거 그룹 직접 기록을 포함한다. 전체 계정 목록에는 하나의 계정 잔고가 없으므로 필터 시 노출한다.
- 대시보드/계정 `/balances`는 실제 잔고 인덱스에서 지정일까지의 최신 값을 일괄 조회한다. 시나리오는 기존 fork 의미론을 유지하는 집계 SQL로 처리한다. 순자산과 표시 분류는 같은 raw 잔고 집합에서 계산한다.
- 대시보드의 전체 거래 조회에는 거래별 posting/tag 별도 조회가 있으므로 일괄 읽기로 바꿔 API 계약을 보존한다. 차트 계산과 전체 거래 응답 크기는 별도 비용이며 이번 개선으로 화면 전체가 특정 시간 안에 뜬다고 보장하지 않는다.
- 새 스키마 마이그레이션은 기존 백업·버전별 원자적 runner를 재사용한다. 최초 누적 잔고는 GROUP BY 및 window SUM으로 한 번 채운다. 읽기는 쓰지 않는다. 실패·롤백·동시 요청에서 원장과 파생 잔고가 같이 보이거나 같이 취소된다.
- 검증: 원본 분개 합계와 캐시 대조, 같은 날 순서/소급 삽입/날짜·계정 변경/삭제/rollback/다중 통화/보관·그룹·필터·페이지, 마이그레이션 보존·실패·재실행, SQL 수 상한·합성 10,000건 성능 전후, 실제 API 수정 후 화면 잔고 갱신, 모바일·접근성. 전체 backend/E2E/build.
- 출시: 로컬 기능 단계. VERSION/CHANGELOG/ship/기존 PR18/main은 별도 요청 때 처리한다.
- 실제 사용 확인: 통장 계정에서 개시잔액과 임의 거래 2건의 거래 후 잔고를 은행 기록과 비교한다.

## 정수 정확성·쓰기 경계

- 계정별 변동액은 분개의 원통화 최소 단위를 BigInt로 합산한다. 안전 정수 범위를 벗어나는 분개에는 원래 숫자 필드와 함께 십진 문자열 `exact_minor`를 보낸다. 이 필드는 계정별 거래내역과 대시보드가 요청한 거래 목록에서만 사용한다.

- 각 계정·통화의 저장 누적값은 SQLite signed int64 범위다. `typeof(delta/balance)='integer'` CHECK로 REAL 승격·반올림을 차단한다. 범위를 넘는 추가·소급 변경·삭제는 원장과 캐시를 함께 롤백하고 `balance_history_integer` 오류를 반환한다. 기존 데이터가 이 범위를 넘으면 마이그레이션도 원자적으로 중지한다.
- 그룹 합계는 개별 계정 범위를 넘을 수 있으므로 Python 정수로 합산한다. 새 `balance_after.amount`는 10진 문자열이며 UI에서 BigInt로 통화 minor unit까지 정확히 표시한다. 기존 `/balances`의 숫자 계약은 유지한다.
- 메모·내역·태그만 바꾸는 수정은 금융 분개와 날짜가 같으면 unpost/repost하지 않는다. 유효성·버전·요청 영수증 검증은 그대로 실행한다. 실제 금융 변경은 기존 원자적 경계와 정수 제한을 따른다.
- [SQLite 트리거 문법](https://www.sqlite.org/lang_createtrigger.html), [window SUM](https://www.sqlite.org/windowfunctions.html) 문서를 확인했다. 마이그레이션 초기 채움은 window SUM, 이후 쓰기는 영향을 받는 계정의 suffix 증감 보정이다.
