# MoneyMap 미완료 TODO 12건의 제품 설계

2026-11-19 · office-hours 빌더 모드 · 미션 2 설계 노드 · 기준 브랜치 `feature/violet-dashboard`

장부를 쓰는 사람이 명세서의 금액을 설명하고, 분류나 가설을 바꾸어도 원래 거래를 추적할 수 있게 하는 것이 목표다. 아래 제목은 [미완료 TODO](../../TODOS.md)의 순서를 따른다. 각 절의 ‘선택’은 사용자가 위임한 설계 판단이다. 숫자와 날짜는 검산용 합성 예시다. 사용 빈도, 명세서 관행, 조작 선호는 이번 설계에서 관찰한 사실이 아니다.

먼저 계정 하나를 대사해 **기준일 잔액 → 차이의 원인 → 장부에 실제 남은 거래**를 확인한다. 이후 생활 분류와 통계가 같은 거래를 다르게 묶어도 원장 합계가 보존되는지 확인한다. 시나리오·외화·할부는 원금, 비용, 가정의 출처를 각각 추적해야 같은 금액을 두 번 세는 오류를 찾을 수 있다. 계정 화면은 키보드·터치 조작을 먼저 고정한 뒤 이동 효과와 병렬 저장을 검증한다.

## 1. 시나리오 중첩 (v2)

- **사용 사례와 기존 설계.** 월세 인상을 가정한 장부에 이사 비용만 더해 두 전망을 비교한다. 지금은 실제 장부에서 분기하거나 전용 규칙·예정 거래를 복제할 수 있다. 복제 후 원본 변경을 다시 맞추는 일이 생긴다. [시나리오 생명주기](scenario-lifecycle.md)
- **대안과 선택.** 독립 복제는 결과를 고정하기 쉽다. 부모를 참조하는 live-additive 분기를 선택해 부모 가정의 변경을 자식 전망에도 반영한다. 실제 장부에서 부모 분기일 마감까지 읽고, 이후에는 부모 전망을 자식 분기일 마감까지 이어받는다. 부모의 과거 가정을 포함한 이 잔액에 실제 장부를 다시 더하지 않는다. 다음 날부터 실제 규칙과 각 조상의 추가 항목, 자식 추가 항목을 원천 ID·발생일별로 한 번씩 적용한다. 단계마다 규칙 유효기간과 해당 단계의 분기 경계를 함께 적용한다.
- **수락 조건.** 5월 1일 부모 분기, 5월 10일 자식 분기에서 부모의 10일 지출 100원은 자식 시작잔액에 한 번 들어간다. 11일 부모 지출 20원과 자식 지출 30원은 자식에서 50원, 부모에서 20원이다. 실제 거래와 기존 단일 분기의 합계도 대조한다. 자식 분기일이 부모보다 이르거나 순환·부모 영구 삭제로 연결이 끊기는 변경은 거절한다. legacy snapshot은 명시적 변환 후 중첩한다.
- **미확인 가정과 검증.** 부모 수정이 자식에게 전파되는 동작을 원하는지는 미확인이다. 같은 예시를 독립 복제와 중첩으로 만들고 부모 월세를 바꿔, 어느 결과가 의도에 맞는지 확인한다.

## 2. 유이자 카드 할부 지원

- **사용 사례와 기존 설계.** 구매자는 카드 명세서에서 이번 달의 원금·이자·수수료를 옮기고, 일부만 납부한 뒤 잔여 원금을 확인한다. 기존 할부 일정과 실제 납부·환불 배분은 원금 단위다. [할부 구매와 납부 일정](installment-payments.md)
- **대안과 선택.** 이율로 일정을 자동 산출하면 입력량은 줄지만 실제 청구액과 어긋날 수 있다. 명세서 확정액을 회차별로 입력하고 부분 납부는 구성요소별 금액을 확인해 배분한다. 원금은 카드부채 상환, 이자·수수료는 각각 비용으로 한 번 기장한다. 비용을 먼저 기장한 경우에는 해당 분개를 참조해 납부와 연결한다.
- **수락 조건.** 회차 원금 10,000원, 이자 600원, 수수료 100원 중 5,700원을 원금 5,000원과 비용 700원으로 납부하면 남은 원금과 미지급 총액은 모두 5,000원이다. 명세서상 원금 환불 1,000원은 잔여 원금만 줄이고, 별도 이자 환급은 해당 비용을 반대로 기장한다. 중도상환 때 확정 수수료와 취소된 미래 이자를 따로 확인한다. 거래·회차 한도 초과 배분을 거절한다. 실제·기준·시나리오 전망에서는 기준일 현재 미지급분과 카드값 규칙 충당액을 대조해 한 번만 반영한다. 기존 무이자 일정 이관 전후 원금·배분·전망은 일치한다.
- **미확인 가정과 검증.** 명세서로 비용 종류와 환급을 구분할 수 있는지 확인이 필요하다. 익명화해 제공된 부분납·중도상환 명세서 한 건씩으로 배분하고, 자료에 없는 비용은 미확인으로 둔다.

## 3. 통계 기간 비교와 분류 확장

- **사용 사례와 기존 설계.** 이번 달 10일까지의 지출을 지난달 같은 기간과 비교하고, 차이가 큰 태그에서 거래로 내려간다. 기존 통계는 서울 날짜 기준의 실제 KRW 장부와 계정별 순액을 사용한다. [통계 개요](statistics-overview.md) · [계정 필터와 복귀](account-history-filter.md)
- **대안과 선택.** 모든 기간을 단순 일수로 이동하면 월별 비교의 월초가 어긋난다. 월 프리셋은 직전 달의 대응 날짜까지 비교하고 말일을 넘으면 그 말일로 자른다. 완료된 달 전체는 이전 달 전체와 비교한다. 직접 입력 기간은 바로 앞의 같은 일수로 잡는다. 양쪽 날짜와 실제 일수를 표시한다. 태그 행에는 해당 거래의 적격 분개 순액을 한 번씩 표시하고, 전체는 거래·분개를 한 번만 센다. 생활비·투자 구분은 명시적으로 지정한 비용·수익 분개 분류를 사용하며 미분류도 표시한다.
- **수락 조건.** 3월 1~10일은 2월 1~10일, 평년 3월 전체는 2월 1~28일과 대응한다. 전기 0원은 증감액만 표시하고 증감률은 산출 불가로 표시한다. 두 태그가 붙은 단일 비용 12,000원은 양쪽 태그에 각각 12,000원, 전체에 12,000원이다. 환불도 부호를 유지한다. 거래 상세와 돌아온 통계의 기간·태그·분류가 일치하고, 생활비·투자·미분류 합은 동일한 장부 총액과 맞는다.
- **미확인 가정과 검증.** 달력상 같은 날짜가 사용자의 비교 질문에 맞는지, 태그 중복 설명을 이해하는지 확인한다. 합성 부분 월과 복수 태그 거래에서 전체와 상세 거래의 합을 각각 찾아보게 한다.

## 4. 계정 행위·상태의 시간 이력과 시점별 사용 가능 여부

- **사용 사례와 기존 설계.** 이미 보관한 통장의 보관 전 거래를 입력하고, 보관 기간에 선택할 수 없던 이유를 확인한다. 기존 거래 수정 설계는 과거 계정 연결을 보존한다. 상위 계정의 그룹 여부는 자식 유무에도 영향을 받는다. [거래 수정](transaction-editing.md) · [계정 이동과 그룹 판정](account-reparenting.md)
- **대안과 선택.** 모든 상태를 처음부터 이벤트로 관리하기에는 과거 자료가 부족하다. 수집 개시 상태를 기준 스냅샷으로 저장하고, 상태 변경과 행위 로그를 같은 트랜잭션에 쓴다. 계정 ID, 행위, 전후 값, 기록·적용 시각, 동시각 순번과 부모 영향을 기록한다. 시점별 입력은 기준점 이후 로그로 판정한다. 읽기 비용이나 소급 정정이 요구되면 로그에서 겹치지 않는 SCD Type 2 유효 구간을 도출한다.
- **수락 조건.** 서울 기준 6월 1일 보관·6월 5일 복원(각 일자 시작 적용)이면 5월 31일·6월 5일 입력은 가능하고 6월 1~4일 신규 선택은 차단된다(스냅샷은 5월 31일 이전). 보관일과 실제 사용 종료일은 구분한다. 같은 적용 시각은 순번으로 판정하고 소급 정정은 새 로그를 남긴 뒤 최초 영향 시점부터 재계산한다. 이동으로 부모의 마지막 자식이 빠지는 경우까지 재구성한다. 로그 실패 시 상태도 롤백하고, 기준점 이전은 ‘이력 미상’으로 표시하며 기존 거래 참조를 보존한다.
- **미확인 가정과 검증.** 상태가 하루 중 바뀌어도 날짜만 있는 거래를 판정할 규칙이 필요하다. 거래일 마감 상태를 적용하고, 이력 미상인 날짜에는 기존 거래의 참조는 허용하되 새 계정 선택에는 현재 기장 가능 조건을 적용한다. 당일 보관·복원과 사후 정정 예시를 확인한다. 과거 보고서의 계정 경로 재현은 별도 수요로 확인한다.

## 5. 잔액 대사(reconciliation) 기능

- **사용 사례와 기존 설계.** 명세서 마감일의 통장 잔액과 장부를 비교해 누락 거래를 찾거나 차이를 조정한다. 거래 후 잔고와 계정별 거래 조회로 원인을 살펴볼 수 있다. [거래 후 잔고](transaction-balances.md) · [계정별 내역](account-history-filter.md)
- **대안과 선택.** 차액을 즉시 기장하면 날짜 착오까지 조정으로 굳어진다. 사용자가 계정·통화·마감일·명세서 잔액을 지정하면 같은 기준의 장부 잔액과 차이를 먼저 보여준다. 원인 거래를 정정한 뒤 다시 계산하거나, 조정 사유와 상대 계정을 확인해 균형 분개 한 건을 확정한다. 자산은 보유액, 카드는 미상환액을 양수로 입력하고 카드의 원장 부호로 변환한다.
- **수락 조건.** 통장 장부 95,000원, 명세서 100,000원이면 +5,000원을 제시한다. 카드 장부 미상환액 95,000원, 명세서 100,000원이면 부채를 5,000원 늘리는 분개를 제시한다. 미리보기·취소는 기장하지 않는다. 확정 후 차이는 0원이고 같은 요청을 재전송해도 조정 거래는 한 건이다. 미리보기 이후 과거 거래가 바뀌면 재계산을 요구한다. 기준일 뒤 거래는 비교에서 제외한다.
- **미확인 가정과 검증.** 31일 사용 중 차이가 얼마나 자주 생기고 원인 탐색이 오래 걸리는지는 미확인이다. 다음 월 마감에서 차이 발생 여부, 원인 거래를 찾았는지, 실제 조정이 필요했는지를 기록한다.

## 6. 다중 통화 원장과 기준통화 환산 (v2 검토)

- **사용 사례와 기존 설계.** 원화를 지급해 매수한 USD 수량과 원화 출금액을 각각 확인하고, 평가일에 환율이 없는 잔액을 알아본다. 기존 금액은 통화별 최소 단위 정수이고 거래 안에서는 같은 통화끼리 검산한다. TODO에는 과거 USD 구매 8건이 KRW 비용으로 남아 있다. [금액 모델](../../backend/moneymap/domain/money.py) · [이관 설계](legacy-transaction-migration-and-tags.md)
- **대안과 선택.** 통화별로 독립 장부를 두면 하나의 환전 거래를 양쪽에서 맞춰야 한다. KRW 기준 장부 하나에 환전 ID로 연결된 통화별 균형 분개를 한 번에 저장한다. 실제 지급액·취득 수량·거래 환율의 기준일과 출처·수수료를 구분한다. 첫 범위는 현금성 외화와 수동 확정 환율이다. 평가일별 환율로 미실현 차이를 표시하고, 매도 때는 이동평균 취득원가 기준으로 실현 차이를 구분한다. 환차손익 정책은 제품 내 관리 보고 기준으로 기록한다.
- **수락 조건.** USD 10.25를 1달러당 1,400원에 사고 수수료 100원을 내면 외화 1,025센트, 원화 출금 14,450원, 비용 100원이다. 1,410원으로 평가하면 환산액 14,453원(원 단위 반올림), 수수료 제외 미실현 차이는 103원이다. 평가환율이 없으면 원통화 수량과 미평가 표시, 평가 가능한 소계만 제공한다. USD 센트와 JPY 엔을 수정·재조회해 최소 단위 정수가 일치해야 한다. 기초 잔액이 없는 위 사례에서 전량을 14,555원에 매도하면 수수료 제외 실현차익은 205원, 남은 미실현 손익은 0원이다. 옛 8건의 분개는 그대로 남고, 선택 이관은 백업·영향 미리보기·행 계보·통화별 대사를 통과해야 적용한다.
- **미확인 가정과 검증.** 사용자가 원금·실제 지급액·별도 수수료를 구분해 입력할 수 있는지와 평균원가를 원하는지는 미확인이다. 익명화한 환전 내역 한 쌍으로 매수→평가→매도를 대조한다. 외화 카드·부채와 자동 환율 조회는 별도 수요를 확인한다.

## 7. 생활 분류를 태그·카테고리 레이어로 분리

- **사용 사례와 기존 설계.** 식비와 교통비에 걸친 출장 지출을 모으고, 식비 안에서 배달 지출만 다시 본다. 기존 거래 태그는 복수 선택을 지원하며 계정 트리는 잔액과 거래 조회에 쓰인다. [거래 태그](transaction-tags.md) · [계정 필터](account-history-filter.md)
- **대안과 선택.** 세부 취향마다 계정을 나누면 잔액 구조와 보고 취향이 함께 바뀐다. 교차 관심사는 기존 거래 태그(예: 출장)로 두고, 합계가 맞아야 하는 생활 분류는 비용·수익 분개마다 선택하는 단일 분류(예: 생활비 / 배달)로 둔다. 분할 영수증도 각 행의 용도에 맞게 분류한다. 가맹점명에서의 자동 추론과 기존 계정의 일괄 재분류는 보류한다.
- **수락 조건.** 한 거래의 식비 8,000원과 교통비 4,000원에 같은 출장 태그를 붙여도 분류 합은 12,000원이다. 배달 분류를 외식으로 바꿔도 거래·분개 ID, 금액, 자산 잔액과 장부 총비용은 같다. 미지정 분개는 미분류에 남고, 분류명 변경 뒤에도 기존 분개에서 찾을 수 있다.
- **미확인 가정과 검증.** 거래 태그 외에 분개 단위 분류를 직접 관리할 의사가 있는지 확인한다. 한 영수증에 생활비·투자비가 섞인 예시에서 각각의 금액을 찾는 과제를 비교한다.

## 8. 계정 행 작업을 오버플로 메뉴로 정리

- **사용 사례와 기존 설계.** 작은 화면에서 잔액을 읽은 뒤 원하는 계정의 설정을 열거나 계정을 보관한다. 기존 작업은 소분류 생성, 그룹 전환, 설정, 보관·복원이며 순서 이동에도 별도 키보드 경로가 있다. [계정 설정](account-reparenting.md) · [계정 순서](account-ordering.md)
- **대안과 선택.** 작업을 모두 펼치면 좁은 화면에서 잔액 열을 압박하고, 모두 감추면 반복 작업도 한 단계 늘어난다. 활성 행의 ‘설정’을 직접 노출하고 나머지를 계정명으로 구별되는 ‘더보기’에 둔다. 보관 행은 ‘복원’을 직접 노출한다. 순서 이동 버튼은 기존 이동 흐름에서 계속 접근할 수 있어야 한다.
- **수락 조건.** 마우스 hover 없이 터치와 키보드로 설정을 열고 닫으며, 더보기에서 보관할 계정명을 확인한다. Enter·Space로 열고 방향키로 이동하며 Esc는 원래 버튼에 포커스를 돌린다. 보관·복원 이후에는 메뉴의 허용 작업이 새 상태를 따른다. 작업 후 행이 사라지면 다음 행 또는 목록 제목으로 포커스를 옮긴다. 화면 읽기 도구가 계정명·펼침 상태를 읽고, 마지막 보관 행에서도 복원할 수 있다.
- **미확인 가정과 검증.** 활성 행에서 설정이 가장 유용한 직접 작업이라는 가정이다. 작은 화면에서 설정·소분류·보관을 각각 찾아보게 하고 탐색 횟수와 잘못 연 행을 기록한다.

## 9. 계정 mutation 범위별 병렬 처리

- **사용 사례와 기존 설계.** 한 그룹의 순서 저장이 지연되는 동안 다른 독립 그룹의 계정을 추가한다. 기존 설계는 전역에서 쓰기 한 번만 허용하며, 최신 작업 실행 취소와 불명확한 저장 결과의 재조회를 제공한다. [계정 순서와 복구](account-ordering.md)
- **대안과 선택.** 전역 직렬화는 단순하지만 무관한 그룹까지 기다린다. 계정 유형·부모 ID로 형제 범위를 구분하고 겹치지 않는 쓰기만 허용한다. 이동은 출발·도착 범위와 영향받는 계정·부모 상태를 함께 점유한다. 요청 세대 번호와 범위별 임시 화면 상태로 늦은 응답을 걸러낸다. 범위를 확정하기 어려운 트리 변경은 직렬화한다.
- **수락 조건.** A 순서 저장을 지연시키고 B에 계정을 추가한 뒤 전체 새로고침과 역순 응답을 발생시켜도 양쪽 결과가 남는다. 같은 부모 수정과 조상 이동 충돌은 차단하거나 최신 버전으로 재확인한다. 다중 탭 충돌·응답 유실은 서버 상태를 재조회한 뒤 미적용 요청만 재시도하며 중복 생성되지 않는다. 실행 취소는 성공으로 확인된 작업 중 사용자 조작 순서가 가장 최근인 건에만 노출한다.
- **미확인 가정과 검증.** 실제 지연에서 독립 편집을 필요로 하는 빈도는 모른다. 두 그룹 편집 중 대기로 막힌 작업을 관찰하고, 지연·역순 응답을 주입한 합성 원장에서 최종 서버·화면 순서를 비교한다.

## 10. 계정 subtree 드래그 시각 보강

- **사용 사례와 기존 설계.** 여러 단계의 계정 그룹을 끌 때 함께 이동할 자손과 도착 위치를 놓기 전에 확인한다. 기존 오버레이에는 이름·경로가 있고 삽입선과 이동 버튼이 있다. [계정 순서 변경](account-ordering.md)
- **대안과 선택.** 모든 행을 따라 움직이게 하면 긴 표에서 목적지를 읽기 어렵다. 화면에 펼쳐진 하위 행을 정적으로 함께 강조하고 오버레이에 숨은 자손을 포함한 수를 표시한다. 목적지는 기존 삽입선을 사용하고 놓은 뒤 100~150ms 정렬 효과만 준다.
- **수락 조건.** 부모·자식·손자의 세 단계에서 형제는 강조 대상에서 빠지고 접힌 후손은 개수에 포함된다. 이동 후 자손 간 순서와 부모 관계가 유지된다. 취소·실패는 원래 순서로 복구한다. 모션 축소 설정에서는 애니메이션 없이 같은 결과를 보이며, 이동 버튼과 드래그 결과가 일치한다. Chromium·WebKit 표에서 삽입선 위치와 가로 스크롤을 확인한다.
- **미확인 가정과 검증.** 색·행 강조가 깊은 계층에서 범위 판단을 개선하는지 미확인이다. 접힌 그룹과 펼친 그룹에서 놓기 전에 함께 이동할 행을 지목해 보게 한다.

## 11. 컴팩트 클릭 영역 점검

- **사용 사례와 기존 설계.** 휴대전화에서 원장 표를 가로로 밀어 체크박스나 작은 행 버튼을 누를 때 이웃 거래가 선택되는지 확인한다. 현재 디자인은 720px 이하 주요 조작에 44px를 사용한다. [공통 디자인](../../DESIGN.md) · [모바일 화면 검증](../verification/violet-workspace.md)
- **대안과 선택.** 모든 화면의 행 높이를 늘리면 큰 화면에서 한눈에 보는 거래가 줄어든다. 계정·거래·설정 등 표를 순회해 버튼·체크박스·라벨의 실제 클릭 사각형을 측정하고, 모바일·거친 포인터에서는 최소 44×44 CSS px 공간을 확보한다. 필요한 행만 키우거나 메뉴로 이동해 활성 영역이 겹치지 않게 한다.
- **수락 조건.** 390px 너비의 터치 브라우저에서 표 왼쪽·오른쪽 끝까지 스크롤한 뒤 대상 중앙과 가장자리 안쪽을 눌러 모두 해당 행만 작동한다. 보이는 아이콘보다 넓은 라벨도 실제 이벤트 대상인지 확인한다. 가로 밀기만 하면 행이 선택되지 않는다. 키보드 탭 순서와 포커스 표시를 확인하고, 데스크톱에서 행 밀도와 가로 넘침을 비교한다.
- **미확인 가정과 검증.** 어느 표에서 오조작이 생기는지는 미확인이다. 마이너스통장 행을 포함해 화면·대상·스크롤 위치·측정 크기·누른 결과를 기록하고 대표 크기마다 재확인한다.

## 12. 전 repository UoW 전환 재평가

- **사용 사례와 기존 설계.** 대사 조정 기록과 그에 연결되는 분개 중 한쪽 저장이 실패해도 사용자가 반쪽짜리 결과를 보지 않아야 한다. 시나리오 생성·수정은 UoW가 트랜잭션을 소유하고 내부 writer가 함께 참여한다. 계정 설정과 반복 거래 생성도 각자의 원자적 쓰기 경계가 있다. [시나리오 설계](scenario-lifecycle.md) · [현행 UoW](../../backend/moneymap/adapters/sqlite/uow.py)
- **대안과 선택.** 전 저장소를 공통 UoW로 바꾸는 안과, 유스케이스별 실제 원자성 필요에 따라 경계를 공유하는 안을 비교했다. 후자를 채택한다. 대사 확정·계정 상태와 로그·할부 배분은 두 번째 독립 사례의 **후보**다. 구현된 경로에서 같은 트랜잭션으로 묶어야 할 쓰기와 커밋 소유자를 추적한 뒤 필요한 경계만 확장한다. 이미 하나의 경계 안에서 충분하면 현 구조를 유지하고 이유를 기록한다.
- **수락 조건.** 시나리오와 다른 실제 쓰기 경로 하나씩에서 호출 진입점·저장 대상·커밋 소유자·중간 실패 결과를 비교표에 남긴다. 두 번째 쓰기 직전에 실패를 주입해 모두 롤백되는지 별도 연결로 읽고, 재시도 시 한 세트만 생기는지 확인한다. 확장 시 내부 writer의 독자 커밋과 호출자별 commit 플래그 없이 같은 검증을 통과한다. 유지 시에도 실패 결과와 재검토 조건을 남긴다.
- **미확인 가정과 검증.** 새 유스케이스들이 실제로 커밋 조립을 중복하는지는 구현 후에 판정할 수 있다. 후보 개수만으로 전환을 결정하지 않는다. 대사와 계정 이력의 저장 경로가 생겼을 때 위 비교를 수행한다.

## 구현·검증 인계

미션 노드명은 위 절과 다음처럼 대응한다. 대사(5)와 메뉴(8)는 기존 대시보드 통합 뒤 독립적으로 진행할 수 있다.

| 작업 흐름 | 노드와 설계 절 |
|---|---|
| 장부와 보고 | reconcile ⑤ → history ④ → category ⑦ → analytics ③ → installments ② → fx ⑥ → scenario ① |
| 계정 조작 | menu ⑧ → touch ⑪ → drag ⑩ → parallel ⑨. parallel은 history의 변경 범위도 확인한다. |
| 원자성 재평가 | uow ⑫는 scenario와 parallel 결과를 함께 읽고, verify는 병합본을 격리 장부에서 검산한다. |

첫 검증은 테스트 통장에 95,000원을 기장하고 100,000원 명세서로 대사를 두 번 확정하는 것이다. 차액이 0원이고 조정 거래가 한 건이면 첫 사례를 통과한다. 각 절의 수락 조건은 후속 구현의 판정 기준이다. 합성 자료로 계산·복구를 확인한 결과와 실제 사용으로 확인한 가정은 검증 기록에서 따로 표시한다.
