## 구현 기록 (2026-09-12)

사용자의 “다음 진행해줘” 승인 후 T1–T6를 완료했다. 단건 조회·원자적 수정·요청 결과 확정 API, 공통 폼과 수정 화면, 기존 선택 유지, 원본 출처 보존, 목록 복귀 및 충돌·이탈 보호를 포함한다. 백엔드 434개·E2E 133개·프론트 빌드가 통과했다. 테스트와 실행 환경은 [검증 기록](../verification/transaction-editing.md)을 따른다.

기존 writer마다 코드를 흩어 넣는 대신 DB 트리거로 거래·분개·태그 변경의 수정 버전을 무효화한다. 계정 재분류와 규칙 삭제도 같은 계약을 충족하며 별도 전체 UoW 전환은 하지 않았다. 수정 명령은 도메인 검증과 SQLite 어댑터의 짧은 쓰기 경계로 나눴다.

아래의 “구현 전/아직 변경하지 않았다”와 마지막 GSTACK REVIEW REPORT는 제품·기술 설계 검토 당시의 기록이다. 현재 구현·검증 상태와 혼동하지 않는다. 기존 개발서버의 자동 재시작으로 실제 로컬 DB에 v6 스키마가 적용되었다. 마이그레이션 직전 백업과 원본 열을 양방향 대조해 거래 7,797건·분개 15,594건·태그·출처·계정·규칙 값이 모두 같음을 확인했다. 실제 거래 수정 요청, 커밋·푸시·릴리스 배포는 수행하지 않았다.

## 문제와 목표

현재 거래 내역은 조회·삭제만 제공한다. 잘못 입력된 기록을 고치려면 삭제하고 다시 입력해야 한다. 사용자는 “db에 유저가 입력한 모든 항목”을 수정하길 원하며 “종류 상관없이 모든 거래는 수정되어야” 한다고 명시했다. 거래 하나를 익숙한 입력 폼으로 열어 바로잡되, 그 거래의 정체성과 출처는 잃지 않는 것이 목표다.

## 확정 결정

- 날짜·내역·금액·계정·메모·태그 및 분할 입력의 모든 사용자 작성 행을 편집한다. 실수 정정에 필요한 입력 범위를 일부 필드로 줄이지 않는다.
- 직접 입력, CSV 이관, 반복 규칙으로 이미 생성된 거래, 개시잔액 모두 포함한다. 개시잔액을 드물게 수정한다는 이유로 제외하지 않는다.
- 반복 생성 거래는 해당 거래 한 건만 변경한다. 규칙·다음 실행·다른 거래·생성 완료 시점은 변경하지 않으며 출처 참조도 끊지 않는다.
- 거래 ID, 원본 CSV 출처·원본 값, 시스템 출처는 편집 항목이 아니다. 수정된 현재 값과 원본 계보를 구분한다.
- 수정 이력 조회·복원·실행 취소는 제외한다. 저장 전 취소, 실패 시 초안 보존, 충돌 방지·결과 확인은 필수다.
- 여러 거래의 일괄 수정, 자동 재분류, 거래 간 관계 추론, 다중 통화 확장은 포함하지 않는다.
- 별도 수정 폼 복제안 대신 **공통 거래 폼**을 선택했다. 입력·수정은 계정 선택·분할·검산을 공유하고 초기화·저장 수명주기를 분리한다.
- 거래내역의 수정 버튼 → 값이 채워진 전용 수정 화면 → 저장 또는 취소 → 원래 목록으로 복귀한다. 필터·스크롤을 복원한다.
- 태그 셀렉트/드롭다운 개선은 TODOS.md에 후속으로 기록했다. 이번에는 현재의 여러 태그 선택·새 태그 추가 UI를 그대로 재사용한다.
- **신규 입력 계정 유지 (추가 승인):** 내역 변경 시 계정 자동 초기화 자체를 없앤다. 신규 입력의 자동 추천은 비어 있는 계정만 채우며 이미 선택된 계정은 선택 출처와 무관하게 덮거나 지우지 않는다. 수정 화면에서는 자동 추천을 실행하지 않고 기존 계정을 유지한다. 신규 입력의 저장 후 금액·메모 비우기는 그대로 둔다. 이는 거래 입력 설계의 ‘내역 변경 시 auto/retained 초기화’ 결정을 대체하며 이번 공통 폼 작업 범위에 포함한다.

## 화면과 조작

- DESIGN.md의 기존 거래 입력 배치를 따른다. 날짜·내역·메모·태그·금액, 차변/대변 계정 트리, 검산, 취소와 변경사항 저장을 배치한다. 모바일은 한 열로 쌓는다.
- 새 입력과 구분되는 “거래 수정” 제목과 기존 값으로 초기화한다. 마지막 계정 조합 자동 회상, 최근 입력 클릭으로 값 대체, 저장 후 금액·메모 비우기는 수정 화면에서 실행하지 않는다.
- 기본 거래는 기본 모드, 여러 분개 행은 분할 모드로 손실 없이 연다. 계정명 대신 ID를 기준으로 유지하고 현재 경로를 표시한다.
- 반복 생성 거래에는 “이 거래 한 건만 변경되며 반복 규칙과 다음 거래는 바뀌지 않습니다”를 안내한다.
- 개시잔액에는 “계정의 시작 잔액이 바뀌며 이후 잔액과 전망에도 반영됩니다”를 안내한다. 문구 접두사가 아니라 서버의 거래 구조·출처로 판별한다.
- 변경 전 취소는 저장하지 않는다. 편집 중 뒤로가기·다른 화면 이동은 저장하지 않은 변경을 버리는지 확인한다. 저장 중에는 중복 저장과 추가 편집을 막으며, 화면 이탈 후 늦은 결과가 다른 화면을 이동시키거나 덮지 않게 한다.
- 필드 오류와 차변·대변 불일치는 입력을 유지하고 수정 위치를 안내한다. 서버 실패에서도 초안을 비우지 않는다.
- 저장 성공 시 거래내역을 다시 읽고 관련 잔액·전망을 갱신한다. 순서 변경과 달리 금액·날짜·계정 수정은 재무 계산에 영향을 준다. 날짜/태그 변경으로 기존 필터에서 사라지면 저장 성공과 그 이유를 알리고 필터는 유지한다.
- 직접 URL 진입 등 돌아갈 목록 상태가 없으면 기본 거래내역으로 복귀한다. 해당 행이 보이지 않으면 목록 제목으로 포커스를 복원한다.

## 재사용과 데이터 경계

기술 설계 Step 0 승인: 기능 종류·필드는 줄이지 않고, 한 거래 저장 기능·공통 폼·수정 화면의 세 경계로 한정한다. 테스트·DB 업그레이드까지 포함한 8개 초과 파일 변경은 허용하지만 범용 폼 엔진·앱 전체 구조 개편은 하지 않는다. (2026-09-12)

- `frontend/src/views/TxnInput.tsx`, `transactionInputState.ts`, `TransactionAccountPicker.tsx`에서 폼·순수 변환·검산을 좁게 추출한다. 생성 전용 자동 회상과 완료 동작까지 공통화하지 않는다.
- `History.tsx`의 조회/태그 필터에 수정 진입을 추가한다. 새로운 수정 컨테이너가 조회·원본 버전·저장·충돌·복귀 상태를 소유한다. 기존 생성 초안과 수정 초안은 섞이지 않는다.
- **한 건 조회 (성능 검토 승인):** 수정 화면의 초기 조회·저장 결과 확인은 거래 ID로 해당 actual 거래와 분개·태그만 읽는 전용 API를 사용한다. 전체 목록을 가져온 뒤 브라우저나 서버에서 한 건을 찾지 않는다. `transactions.id`, `postings.txn_id`, `transaction_tags.txn_id`의 기존 키·인덱스를 활용하며 거래가 누적되어도 조회 횟수가 전체 거래 수에 비례하지 않도록 검증한다. 목록 조회·페이지네이션 개선은 기존 TODO에 남기고 이번에는 확장하지 않는다.
- **화면 이탈 방지 구조 (승인):** 최상위 `BrowserRouter` 구성을 `createBrowserRouter`/`RouterProvider`로 좁게 전환해 수정 화면에서 `useBlocker`를 사용한다. 기존 화면·주소·조회 수명주기는 유지하며 loader/action 기반 조회로 전면 전환하지 않는다. 앱 내부 이동은 수정 초안의 변경 여부에 따라 확인하고, 새로고침·탭 닫기는 별도 `beforeunload` 경고를 사용한다. 브라우저 경고는 강제 종료까지 보장하는 영구 초안 저장 기능이 아니다. 최상위 설정 변경에 따른 기존 메뉴·뒤로/앞으로·직접 URL 진입 회귀를 검사한다.
- 실제 거래 수정 API는 기존 한 거래를 원자적으로 갱신한다. 거래 삭제 후 재생성으로 구현하지 않는다. 현재 `save()`의 `id != None` 금지와 별도의 명시적 수정 경로를 둔다.
- 현재 SQLite는 확정된 분개 변경을 트리거로 막는다. 하나의 write transaction 안에서 임시 미확정 → 필드·분개·태그 갱신 → 검산 후 재확정을 수행하고 실패 시 전체 롤백한다. 분개 변경 중간 상태가 다른 읽기에 노출되면 안 된다.
- 서버가 수정 버전을 비교해 오래된 저장을 거절한다. 버전은 이력 기능이 아니라 충돌 방지용이다. 새 버전 도입 시 기존 DB 업그레이드·백업·검증을 포함한다.
- **다른 쓰기 경로의 충돌 감지 (승인):** 계정 재분류처럼 기존 거래의 분개를 바꾸는 경로와 반복 규칙 삭제 시 기존 거래의 출처 참조를 해제하는 경로도 해당 거래 버전을 같은 쓰기 트랜잭션에서 갱신한다. 새 수정 API에만 버전 갱신을 넣지 않는다. 구현 전 전체 기존 거래 변경 경로를 감사하며 실제 값이 바뀐 거래만 대상이다. 수정 화면이 오래된 원본으로 재분류 결과나 변경된 출처 상태를 덮지 않는지 교차 기능 회귀 테스트를 추가한다. 현재 장부에 재분류를 실행하는 요청은 아니다.
- **기존 분개 행 식별 (승인):** DB의 posting ID를 수정 조회·초안·저장까지 유지한다. 화면용 행 key와 서버 posting ID는 구분하며, 새 행에는 기존 ID를 부여하지 않는다. 서버는 같은 거래에 속한 원래 행인지 확인하고 중복 ID·다른 거래의 ID를 거부한다. 보관·그룹 계정 예외는 원래 행의 계정을 그대로 유지할 때에만, 0원 예외는 원래 0원 행을 유지할 때에만 적용한다. 계정 교체나 새 행에는 현재 계정 사용 가능 여부를 검증한다. 기본/분할 모드 전환에서도 원래 행 ID를 잃거나 임의로 다른 행에 붙이지 않는다. ID는 사용자 입력 항목으로 노출하지 않는다.
- **동시 수정 충돌 처리 (승인):** 다른 창에서 먼저 수정된 거래는 오래된 버전으로 저장하지 못한다. 작성 중인 내용은 보존하고 최신 거래를 확인한 뒤 다시 수정하도록 한다. 금액·계정의 자동 병합이나 강제 덮어쓰기는 제공하지 않는다. 최신 값 조회만으로 원래 초안을 새 버전 위에 자동 재제출하지 않는다. 거래가 삭제된 경우에도 초안을 유지하되 같은 ID로 재생성하지 않는다.
- **저장 응답 유실 처리 (승인):** 연결 끊김·시간 초과는 저장 실패로 단정하지 않는다. 제출 시점의 초안·원본 버전·저장 요청 ID를 보존한다. 사용자 추가 승인에 따라 최소 처리 결과를 기록하고 요청 ID로 결과를 확정하며, 현재 거래 값·버전 조회만으로 성공/실패를 추정하지 않는다. 결과 확인 전에는 자동·수동 재저장을 막는다. 확인할 수 없으면 초안을 유지하고 ‘저장 결과 확인 필요’와 결과 재확인 동작을 제공한다. 후속 동시 수정·삭제는 충돌 처리로 연결한다. 요청 번호는 거래 ID를 대체하지 않으며 수정 이력 기능도 아니다. 세부 계약은 아래 ‘저장 요청 결과 확인’을 따른다.
- 이관 중복 판정은 코드상 `source_hash + source_row`를 사용한다. 이 키와 원본 필드는 수정하지 않으며, 현재 값 변경 후 동일 원본 재이관도 중복 생성하지 않는지 테스트한다.
- 반복 생성의 `last_materialized`와 `source_rule_id`는 수정 payload로 받지 않는다. 생성 거래 날짜를 옮겨도 이미 실행한 회차를 재생성하지 않고 향후 일정은 기존 규칙대로 유지한다.

## 확정된 특수 거래 검증

아래는 승인된 특수 거래 조건이다. 사용자의 “모든 항목 수정”을 기존 신규 입력 제한으로 조용히 축소하지 않는다. 통화 지원은 사용자가 명시적으로 후속 분리했다.

1. **보관·그룹화된 계정 (승인):** 해당 거래가 원래 참조한 일반 계정은 유지하면서 날짜·금액·메모 등을 수정할 수 있다. 계정 교체·새 분개 행은 현재 사용 가능한 계정만 선택하며, 수정 때문에 계정을 복원하거나 그룹 상태를 바꾸지 않는다. 시스템 상대계정은 아래 별도 검증을 따른다. 행 단위 기존 참조 보존 계약은 posting ID로 확인한다. 계정 행위별 시간·SCD Type 2 후보는 별도 TODO로 분리했으며 이번에는 날짜별 계정 유효성 모델을 추가하지 않는다.
2. **개시잔액 (승인):** 대상 계정·날짜·금액·내역·메모·태그는 수정한다. 대상 계정과 기존 개시잔액 시스템 상대계정의 정확히 두 행 구조를 유지하며 시스템 계정은 변경하지 않는다. 상대 금액은 서버에서 균형에 맞춰 계산한다. 분할 행 추가·삭제는 제공하지 않는다. 대상 계정 변경 시 자기 거래를 제외한 개시잔액 중복을 같은 쓰기 트랜잭션 안에서 검사한다. 일반 거래에는 시스템 계정 사용 권한을 열지 않는다.
3. **0원 이관 기록 (승인):** 기존 0원 분개는 그대로 유지하면서 내역·메모 등 다른 항목을 수정하거나 유효한 0원이 아닌 금액으로 정정할 수 있다. 기존 0원이 아닌 분개를 0원으로 변경하거나 새 0원 분개를 추가하는 것은 제한한다. 과거 0원 예외 여부는 클라이언트 플래그를 신뢰하지 않고 서버가 원래 행으로 확인한다. 개시잔액 인식과의 관계는 별도로 검증하며, 메모만 수정했다는 이유로 과거 기록을 거부하거나 일반 0원 기록을 개시잔액으로 재분류하지 않는다.
4. **통화 (후속 TODO로 분리, 사용자 승인):** 이번 수정 기능은 KRW 기준으로 진행한다. 비원화 거래의 통화별 표시·소수 단위 입력·수정 지원은 TODOS.md의 ‘다중 통화 원장과 기준통화 환산’으로 이관하며 이번 구현의 선행 조건으로 삼지 않는다. 기존 비원화 데이터가 발견되어도 KRW로 암묵 변환하거나 덮어쓰지 않는 보호 검증은 유지한다. 미지원 거래를 원화 편집기로 저장하지 않으며 지원 범위를 안내한다. 기존에 원화 비용으로 정리한 USD 구매 내역은 그대로 유지한다. 통화 변경·환전·기준통화 환산·다중 통화 계산도 후속 범위다.

## 독립 검토와 공개 참고

- 사용자 동의로 새 문맥의 Codex CLI 검토를 실행했다. 동일 모델 계열의 독립 검토이며 다른 모델 합의로 표현하지 않는다. 검토자는 소스를 직접 읽지 않았고 전달받은 사실과 추론을 구분했다.
- 공통 폼과 별도 생성/수정 수명주기를 추천했다. 과거 계정·0원·개시잔액 검증, 원본 중복 방지, 오래된 버전·응답 유실을 강조했다. 기능 범위의 기존 전제를 뒤집지는 않았다.
- [Actual Budget split transactions](https://actualbudget.org/docs/transactions/split-transactions/): 분할 행 편집과 합계 검산을 참고했다. 모델을 그대로 복제하지 않는다.
- [YNAB transaction editing](https://support.ynab.com/en_us/how-to-edit-and-delete-transactions-BJG4oS1s): 기존 거래에서 편집을 시작하는 흐름을 참고했다. 검색에는 일반 용어만 쓰고 실제 거래 데이터는 보내지 않았다.

## 시안과 검증 과제

- 사용자 승인: `/tmp/moneymap-transaction-edit-sketch-20260912.html` (이미지: 같은 이름 `.png`). 실제 저장·검색·분할 편집은 없는 예시다. 상단 예시 전환 버튼은 제품 UI가 아니다.

- 다음 확인 과제: 구현 후 테스트용 거래 하나에서 금액·메모를 바꾸고 목록 복귀 위치를 확인한다. 자동 생성 거래 수정 후 다음 회차 금액이 원래 규칙을 따르는지도 테스트 데이터로 확인한다. 실제 장부 변경을 개발 검증에 사용하지 않는다.

## 완료 기준과 다음 단계

코드 품질 검토 확인: `transactionInputState.ts:47–50`의 내역 변경에 따른 초기화뿐 아니라 `applyPair()`의 빈 추천·실패 응답에 의한 초기화와 자동 추천 덮어쓰기도 함께 제거한다. 내역 키/요청 세대/계정별 변경 번호를 통한 오래된 응답 무효화는 유지한다. 신규 입력 또는 수정의 계정 교체/새 행에서 선택한 계정이 보관 등으로 사용 불가능해진 경우에는 값을 조용히 지우지 않고 유효성 오류로 저장을 막는다. 수정의 원래 참조 보존 예외는 별도로 유지한다. 테스트에서 기존 초기화 기대값을 새 승인 정책으로 바꾸고, 신규 입력의 빈 쪽 추천·선택된 쪽 보존·조회 실패·응답 역전·저장 후 유지 및 수정에서 자동 추천 미호출을 각각 검증한다. 현재 코드나 테스트는 아직 변경하지 않았다.

1. 특수 거래 네 조건, 수정 API·동시성·복귀 계약을 엔지니어링 설계에서 확정한다.
2. 동일 거래 ID 갱신, 출처·규칙 불변, 차대변 검산, 실패 롤백·충돌·응답 유실 테스트를 먼저 갖춘다.
3. 공통 폼과 전용 수정 화면을 연결하고 기존 생성 기능의 회귀를 검증한다.
4. 직접 입력·CSV·반복 생성·개시잔액과 과거 특수 거래의 편집, 모바일·키보드·오류 초안 유지, 변경 날짜/계정의 잔액·전망 반영, 필터·스크롤 복귀를 검증한다.
5. `cd backend && uv run pytest`, `cd frontend && npm run e2e`, 프론트 빌드를 통과한다. 배포는 기존 앱 경로를 사용하며 별도 서비스나 배포 채널은 추가하지 않는다.

테스트 검토: `docs/designs/transaction-editing-test-plan.md`에 API·UI·출처·동시성·오류·회귀 경로와 실행 흐름도를 작성했다. 현재는 모두 구현 예정이며 실행 결과가 아니다. 기존 다른 쓰기 경로의 버전 갱신과 요청별 처리 결과 기록까지 사용자 승인으로 확정했다. 기술 검토 결과·작업 순서는 아래에 기록한다.

## 대화에서 드러난 기준

문서 검토: office-hours 독립 리뷰 1회, 당시 제품 설계 기준 PASS 9/10. 이후 통화는 사용자 요청으로 후속 분리했고 특수 거래와 안전한 저장 계약을 엔지니어링 검토에서 확정했다. 제품·기술 설계 확정은 구현이나 테스트 통과를 뜻하지 않는다.

- “종류 상관없이 모든 거래”가 편집 가능해야 한다는 요구를 기준으로, 드문 거래를 제외하는 최소 구현은 선택하지 않았다.
- 수정 이력과 태그 UI 개선은 지금 필요하지 않다고 명시했다. 데이터 수정의 안전성과 부가 편의 기능은 구분한다.

## 기술 구현 계약

아래 계약은 승인된 동작을 구현 단계로 구체화한다. 기능 코드·DB·실제 장부는 아직 변경하지 않았다.

### 조회·요청·응답

- `GET /api/transactions/{id}`: actual의 확정 거래 한 건만 조회한다. 거래 필드·현재 수정 버전·posting ID·일반/개시잔액 구분·기존 참조 보존 정보를 반환한다. 별도 시나리오의 예정 거래 API는 대체하지 않는다.
- `PUT /api/transactions/{id}`: 사용자 입력 필드와 `expected_version`, `request_id`, 기존 행의 `posting_id`를 받는다. 새 행은 posting ID 없음. 원본 출처·시나리오·통화·시스템 권한·서버 예외 플래그는 수정 payload에서 거부한다.
- 개시잔액 명령은 대상 계정·날짜·금액/방향·내역·메모·태그를 받고 서버가 기존 시스템 상대 행을 계산한다. 일반 분개 배열로 시스템 행을 조작하는 우회 경로를 만들지 않는다.
- 성공 응답은 같은 거래 ID, 새 수정 버전, 확정된 현재 필드·행 ID를 반환한다. UI는 제출 객체를 성공 결과로 추정하지 않는다.
- 잘못된 입력은 기존 400/422 체계, 없는 거래는 404, 오래된 버전·요청 번호 재사용 불일치는 409, 확인된 DB 잠금/쓰기 거절은 기존 503 오류 체계를 재사용한다. 사용자에게 보여줄 메시지와 안정적인 오류 코드를 분리한다.
- 기존 목록·생성 응답 형식은 불필요하게 바꾸지 않는다. 수정용 DTO를 명시적으로 두고 생성 모델을 느슨하게 만들어 0원/시스템 예외를 전역에 열지 않는다.

### 버전·출처·원자성

- 수정 버전은 수정용 DTO에서 다루는 불투명 토큰이다. 클라이언트는 동등성만 비교하고 정수 +1이나 시각으로 해석하지 않는다. DB에는 거래별 새 토큰을 채우는 마이그레이션과 새 거래 생성 시 초기 토큰을 만드는 DB 측 삽입 처리를 둔다. 생성 경로가 직접 SQL인 이관도 빠지지 않아야 한다.
- 토큰은 새 거래 및 해당 거래의 데이터 변경마다 새로 발급한다. 숫자 거래 ID가 삭제 후 재사용돼도 이전 거래의 토큰으로 새 거래를 수정하지 못한다. 거래 ID·posting ID를 UUID로 전면 교체하거나 원장을 재구성하지 않는다.
- 계정 재분류, 규칙 삭제의 출처 참조 해제 등 실제 거래를 바꾸는 기존 경로도 같은 토큰 갱신 계약을 사용한다. 계정 이름/표시순서 변경처럼 거래 자체가 바뀌지 않는 작업으로 모든 거래 버전을 무효화하지 않는다. 저장 시 현재 계정 사용 가능 여부는 별도로 검사한다.
- 한 번의 `BEGIN IMMEDIATE` 안에서 원본/버전/요청 확인 → 행 소속·계정·금액 검증 → `posted=0` → 필드·기존 행 UPDATE/추가 INSERT/제거 DELETE·태그 갱신 → `posted=1` 검산 → 새 버전과 처리 결과 기록 → COMMIT. 중간 예외는 버전과 처리 결과까지 전체 ROLLBACK.
- 기존 행 ID를 보존하므로 기존 시나리오용 `replace()`의 모든 분개 삭제·재삽입을 그대로 호출하지 않는다. 미확정→검산→재확정 패턴, 태그 정규화/교체, 내역 검색 키 정규화는 재사용한다.
- `entry_origin`, 이관 원본/중복 방지 키, 반복 출처는 수정 과정에서 재계산하지 않는다. 내역 변경에 필요한 `item_key`만 정규화해 갱신한다. 규칙 watermark나 전망의 계산 정책을 수정 기능에서 바꾸지 않는다.
- 계정·개시잔액 중복 검증도 쓰기 잠금을 얻은 뒤 같은 트랜잭션에서 수행한다. 네트워크 요청·대기·UI 처리·전체 전망 계산을 DB 쓰기 잠금 안에 넣지 않는다.
- 거래 날짜/계정/금액 수정 후 기존 잔액·actual/시나리오 전망 조회가 새 데이터를 반영하도록 기존 refresh 경로를 사용한다. 과거 기준으로 고정된 스냅샷을 수정 기능에서 임의로 다시 쓰지 않는다.

### 저장 요청 결과 확인 (사용자 승인)

- 거래 ID는 대상, 버전은 읽었던 상태, 요청 ID는 이번 저장 시도를 식별한다. 사용자 화면에 새 입력 항목은 추가하지 않는다.
- 최소 결과 테이블 `transaction_edit_requests`를 추가한다. 요청 ID(고유), 대상 거래 ID, 원본 버전, 서버가 정규화한 요청의 SHA-256, 결과 상태(`applied`/`not_applied`), 적용 후 버전만 저장한다. 거래의 수정 전후 내역·메모·금액 사본은 저장하지 않는다.
- 같은 요청 ID와 같은 내용은 한 번만 적용된다. 다른 내용으로 같은 번호를 사용하면 거부한다. 해시는 인증 수단이 아니라 요청 내용 일치 검사다.
- 성공 결과 행과 실제 거래 변경은 같은 COMMIT에 포함된다. 결과 확인에 필요한 작은 메타데이터는 거래 삭제와 함께 지워지거나 임의 TTL로 사라지지 않게 유지한다. 해당 거래가 이후 변경/삭제됐다면 ‘요청은 적용됐지만 현재 상태는 달라짐’으로 구분하며 과거 값을 복원하지 않는다.
- 응답 유실 시 `POST /api/transactions/{id}/edit-result`로 원래 요청 ID·원본 버전·동일 제출 내용을 보내 결과를 확정한다. 이 API는 원래 수정을 실행하는 재저장 API가 아니다. 결과 확정을 위해 메타데이터를 쓸 수 있으므로 GET으로 구현하지 않는다.
- 결과 확정은 저장과 같은 SQLite 쓰기 잠금 아래 직렬화한다. 이미 성공한 기록이면 `applied`; 기록이 없다면 해당 요청을 `not_applied`로 종료 기록한다. 뒤늦게 도착한 원래 저장은 이 기록을 보고 적용하지 않는다. ‘기록 없음’을 읽기만 하고 실패를 단정하는 경쟁 조건을 피한다.
- 결과 확인 응답도 유실되면 같은 결과 확인을 반복할 수 있다. 확인이 불가능한 동안 초안과 제출 스냅샷을 유지하고 재저장을 막는다.
- `applied`이고 현재 버전이 적용 결과와 같으면 성공 흐름으로 복귀한다. 후속 변경/삭제/다른 토큰이면 초안+최신 상태를 보여주는 충돌 흐름이다. `not_applied`가 확인되고 현재 원본도 여전히 같을 때만 사용자가 새 요청 번호로 다시 저장할 수 있다. 자동 재저장은 없다.

```
편집 원본(id, version) + 초안
  -> 저장(request_id)
       -> DB 짧은 쓰기 잠금
            -> 원본·버전·기존 요청 검증
            -> 거래 + 분개 + 태그 + 새 버전 + applied 결과 COMMIT
       -> 성공 응답: 목록/잔액 갱신
       -> 응답 불명: edit-result (동일 요청, 재저장 아님)
            -> applied: 성공 또는 후속 변경 안내
            -> 기록 없음: not_applied 확정 -> 늦은 저장 차단
            -> 확인 실패: 초안 유지, 결과 재확인만 허용
```

### 공통 폼·복귀 상태

- 표시/필드 조작/계정 선택/분할/검산은 좁은 공통 폼, 신규 입력의 회상·최근 입력·완료 정리는 생성 컨테이너, 조회·기존 버전·요청 결과·복귀는 수정 컨테이너가 맡는다. 범용 폼 엔진이나 여러 불리언 조합으로 한 컴포넌트에 전부 몰지 않는다.
- 신규 입력의 내역 변경은 선택된 계정을 유지한다. 자동 추천의 키·세대·계정별 변경 번호 검사는 유지하면서 빈 계정만 채운다. 이미 양쪽이 채워졌으면 추천 로딩 때문에 저장을 불필요하게 막지 않는다. 불가능한 계정 선택은 지우지 않고 검증 오류를 표시한다.
- 수정 기본/분할 전환은 원래 posting ID와 화면 행 key를 분리해 유지한다. 0원에는 금액 부호만으로 유실되는 행/차대변 방향을 추정해 합치지 않는다. 손실 없는 기본 표현이 안 되면 분할 모드로 연다.
- 원본 조회 성공 때만 초기화하고, 계정/태그 목록 재조회나 전역 refresh가 작성 중인 초안을 초기화하지 않는다. 미지원 비원화는 분개를 KRW로 생성하지 않고 저장을 막아 안내한다.
- 내비게이션은 최상위 data router의 wildcard App 경로로 최소 전환하고 기존 하위 Routes를 유지할 수 있다. 이번 작업에서 기존 API 조회를 loader/action으로 이동하지 않는다.
- History에서 현재 필터·목록 위치·대상 거래 ID를 검증 가능한 내부 복귀 상태로 넘긴다. 저장/취소 후 이전 목록을 복원하되 임의 외부 URL을 복귀 대상으로 사용하지 않는다. 새로고침/직접 진입에 복귀 상태가 없으면 기본 목록이다.
- 저장 후 목록 재조회가 실패해도 이미 확인된 저장 성공을 실패라고 표시하지 않는다. 필터에서 사라진 행은 성공과 사라진 이유를 안내한다. 현재 제품에 없는 날짜 필터를 새로 만들지는 않는다.
- 저장 중·결과 확인 필요 상태는 중복 제출을 차단한다. 화면 이탈 시 경고, 늦은 응답의 visit/request guard를 적용한다. 저장 초안의 영구 보관·브라우저 강제 종료 복구는 별도 기능으로 만들지 않는다.
