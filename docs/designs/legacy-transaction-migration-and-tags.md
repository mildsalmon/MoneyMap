## Problem Statement

- 과거 가계부 CSV의 7,677개 유효 거래를 MoneyMap에 옮겨야 한다.
- CSV와 앱의 계정 체계가 다르고, 과거의 `메모`와 데이트·엄마·지인 같은 맥락을 잃지 않아야 한다.
- 현재 앱은 `내역`과 별도의 `메모`를 이미 저장·조회하지만, 재사용 가능한 다중 태그와 CSV 이관 경로가 없다.

## What Makes This Cool

- 과거 기록을 통계를 위해 억지로 합치지 않고 사실 그대로 보존하면서, 새 계정 계층과 태그로 더 유용하게 조회할 수 있다.
- 같은 원본과 분류 자료로 언제든 시험 이관을 재현하고, 이미 이관한 원본은 중복 저장하지 않는다.

## Constraints

- 원본 SHA-256은 `b2849c42fd1b20f7ab65cb0f2189dbe859028a16f78e8d081ad8f1d415ec9814`이며 달라지면 중단한다.
- 숫자 거래 행 하나를 MoneyMap 거래 하나로 저장한다. 환불·회수·즉시결제·정산도 삭제하거나 병합하지 않는다.
- 날짜, 내역, 금액, 원본 메모, 원본 양쪽 유형·계정, 원본 행 번호를 추적할 수 있어야 한다.
- 실제 DB 쓰기 전에 SQLite 온라인 백업을 만들고, 전체 이관은 하나의 원자적 트랜잭션으로 수행한다.
- 통계상의 상계나 거래 관계 추론은 이관 범위가 아니다.

## Premises

- 계정은 거래의 회계적 성격(`무엇`)을, 태그는 `누구와/왜`를 나타낸다.
- 분류 자료에서 확정된 행별 경로를 우선하고, 나머지 원본 식비는 `식비/외식`으로 보낸다.
- 분류 근거가 없는 비비용 계정은 이름을 버리지 않고 적절한 자산·부채·수익·순자산 그룹 아래에 같은 이름으로 만든다.
- `롯데카드(모바일엔디지로카)`와 `롯데카드(디지로카London)`은 별도 부채 계정이다.
- CSV의 독립된 `멘토링` 두 줄은 바로 앞 거래의 메모 연속 줄로 복원하되 거래 수에는 포함하지 않는다.

## Approaches Considered

### Approach A: 손실 없는 1:1 이관

원본 행마다 균형 잡힌 두 개의 posting을 만들고, 확정된 계정 재분류와 태그만 적용한다. 원본 필드와 배치 지문을 별도 provenance 테이블에 둔다.

### Approach B: 관계를 추론해 거래 병합·상계

환불과 결제, 계좌 이동으로 보이는 행을 연결하거나 합친다. 사용자가 지적한 대로 이 작업의 요지가 아니고 원본 사실을 바꿀 위험이 있어 제외한다.

## Recommended Approach

Approach A를 사용한다. 이관기는 dry-run과 apply 모드를 공유하고, 원본 해시와 `(배치, 원본 행)` 고유키로 멱등성을 보장한다. 확정 분류 CSV는 행별 override로 사용하고, 충돌하는 후보는 더 구체적인 결정 자료가 우선한다. 태그는 정규화된 이름 테이블과 거래 연결 테이블로 저장한다.

## Open Questions

- 없음. 향후 통계 화면에서 태그별 집계를 어떻게 시각화할지는 거래 저장과 별도 작업으로 다룬다.

## Success Criteria

- 7,677개 거래와 15,354개 posting이 actual 시나리오에 추가된다.
- 모든 이관 거래가 차변·대변 합계 0이고 KRW 단일 통화다.
- 원본 메모와 두 개의 `멘토링` 연속 줄, `강남역지하상가점` 오타 수정이 반영된다.
- 원본 식비 1,237건은 승인된 279개 예외와 외식 기본값 958개로 정확히 나뉜다.
- 환불을 포함한 모든 숫자 거래 행이 provenance에서 정확히 한 번 확인된다.
- 같은 파일을 다시 실행하면 새 거래가 0개 생긴다.
- 롯데카드 두 종류가 별도 계정으로 확인된다.
- 백엔드 전체 테스트와 프런트엔드 E2E가 통과한다.

## Distribution Plan

- 앱 스키마/태그 UI와 재현 가능한 backend CLI 이관기로 저장한다.
- 기존 배포 파이프라인을 사용하며, 개인 DB 이관 결과와 백업은 저장소에 커밋하지 않는다.

## Next Steps

1. 태그와 import provenance 스키마를 추가하고 저장·조회 경로를 테스트한다.
2. 승인된 계정 계층과 롯데카드 계정을 표준 계정에 반영한다.
3. CSV 파서·분류 자료 로더·계정 매퍼·dry-run 검증을 구현한다.
4. 라이브 DB를 백업하고 실제 이관한 뒤 건수·금액·멱등성을 검산한다.
5. 전체 백엔드 및 프런트엔드 테스트를 실행한다.

## What I noticed about how you think

- “그냥 저장하면 안되나?”라는 지적은 데이터 이관과 통계 해석을 분리해야 한다는 핵심 경계를 분명하게 했다.
- “환불 거래도 실제로 있는 거니까 제외하면 안되지 않나?”라는 기준 덕분에 이관의 성공 조건이 분류 정확도보다 원본 완전성에 먼저 놓였다.
- “별도 통계로 보고 싶다”는 요구는 중복 카테고리 대신 다중 태그가 필요한 이유를 명확히 했다.
