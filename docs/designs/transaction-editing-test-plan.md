## Affected Pages/Routes

- /transactions — 수정 진입, 필터·스크롤·포커스 복귀, 저장 후 최신 값.
- /transactions/:id/edit — 제안된 수정 URL. 기존 값 로드, 편집·취소·저장·오류·충돌.
- /transactions/new — 공통 폼 추출과 계정 초기화 제거의 회귀.
- /accounts 및 / — 수정 후 계정 잔액·개시잔액·전망 반영.
- 기존 시나리오 URL — 최상위 라우터 변경 회귀, 실제 거래 변경에 따른 기존 전망 계약.

## Test Environment

pytest와 기존 Playwright 테스트 구성을 재사용한다. backend/tests/test_api.py는 임시 앱 fixture를, frontend/playwright.config.ts는 포트별 임시 DB를 사용한다. 동시성은 별도 임시 파일 DB에 여러 연결을 열어 검증한다. 원본 CSV·실제 장부는 테스트에 사용하지 않는다. CSV 테스트는 가상 원본과 출처 키를 가진 fixture로 수행한다. E2E 실행 전 외부 API 환경변수가 실제 앱을 가리키지 않는지 확인한다.

## Key Interactions to Verify

- B01: 날짜·내역·금액·계정·여러 줄 메모·태그·분할 행을 저장 후 재조회. 거래 ID 유지, 차대변 합계 0, 미변경 값 보존.
- B02: 기존 행 ID 유지, 새 행 추가·삭제. 중복/다른 거래의 ID 제출은 거절하고 원래 데이터 불변.
- B03: 보관·그룹 계정의 원래 행 유지 허용. 계정 교체·새 행에는 현재 사용 가능 여부 적용. 다른 행에 과거 계정 예외를 옮길 수 없음.
- B04: 기존 0원 유지 또는 비영 금액 정정 허용. 새 0원/비영→0 거절. 메모만 변경해도 기존 값·종류 보존.
- B05: 개시잔액의 두 행·시스템 상대계정 유지, 대상 계정 변경, 중복 방지. 일반 거래에서 시스템 계정 권한을 얻을 수 없음.
- B06: 이관 거래 수정 후 원본 출처 키·원본 필드 불변. 같은 가상 CSV 재이관이 중복 거래를 만들지 않음.
- B07: 생성된 반복 거래의 날짜·금액 수정 후 규칙·watermark·source_rule_id·다른 거래 불변. 재실행 시 이미 생성된 회차 중복 없음, 다음 회차는 규칙의 원래 값.
- B08: 기본/분할 전환에서 행 ID·금액·계정·메모·태그 보존. 손실 없이 전환 불가능하면 현재 초안을 유지하고 이유 안내.
- F01: 내역 수정만으로 선택된 계정이 비워지거나 바뀌지 않음. 자동 추천 API는 수정 화면에서 호출되지 않음.
- F02: 신규 입력의 추천은 빈 계정만 채움. 수동/자동/이전 저장에서 유지된 모든 선택 보존. 느린 응답·추천 없음·조회 실패도 기존 선택을 지우지 않음.
- F03: 신규 입력의 저장 후 금액·메모 초기화, 후속 초안 보호, 분할·태그·키보드 입력은 기존 동작 유지.
- F04: 저장 또는 취소 후 원래 태그 필터·스크롤 복원. 행이 남으면 해당 수정 버튼에, 없으면 목록 제목에 포커스. 직접 URL 진입은 기본 목록으로 복귀.
- F05: 변경 있음/없음 각각에서 메뉴 이동·뒤로/앞으로·취소. 버리기 확인 취소는 초안 유지. 새로고침·탭 닫기는 브라우저 경고가 가능한 조건에서 확인.
- F06: 모바일 폭·키보드·IME 입력·메모 Enter·행 추가/삭제·선택기 초점·오류 접근성 확인.

## Edge Cases

- E01: 차대변 불일치, 미완성 분개, 동일 계정 기본 입력, 잘못된 날짜·문자 금액·안전 정수 초과·필드 길이·태그/행 개수 제한. 서버와 UI 모두 유효성 오류, 전체 데이터 불변.
- E02: 두 창의 같은 버전 제출에서 하나만 성공. 늦은 저장은 충돌, 초안 유지, 자동 병합/강제 덮어쓰기 없음.
- E02a: 수정 화면을 연 뒤 계정 재분류 또는 규칙 삭제로 해당 거래가 변경됨. 원래 버전의 수정은 충돌하며 재분류 결과·출처 해제 상태를 되돌리지 않음. 다른 거래 버전은 불필요하게 바뀌지 않음. 변경 도중 실패하면 버전도 전체 롤백.
- E03: 열어둔 거래 삭제, 다른 actual 외 시나리오의 ID, 존재하지 않는 ID. 명확한 오류이며 재생성 없음.
- E04: 분개/태그 갱신 도중 의도적 실패 및 DB 잠금. 부분 저장·버전만 증가·posted=0 잔존 없음. 사용자에게 실패와 초안 제공.
- E05: 서버 저장 후 응답 유실. 결과 재확인 전 중복 재저장 없음. 제출 내용·서버 값·버전으로 확인하며 후속 수정/삭제는 충돌로 안내.
- E06: 원래 저장 요청보다 재조회가 먼저 도착함. 이전 값 관찰만으로 ‘저장 실패’라 단정하거나 재저장을 허용하지 않음.
- E07: 저장 중 빠른 Enter/더블클릭은 단일 제출. 이탈 후 늦게 도착한 조회·저장 응답이 다른 화면을 이동하거나 초안을 덮지 않음.
- E08: 비원화 거래는 KRW 편집기로 저장되지 않으며 원본 통화/최소 단위 정수 불변. 기존 USD 구매의 원화 비용 거래는 일반 KRW 편집 가능.
- E09: 조회 오류·계정/태그 목록 로드 실패·저장 후 목록 갱신 실패. 입력 유실 없음, 확인된 저장 성공을 저장 실패로 오표시하지 않음.
- E10: 구 DB 업그레이드와 재시작 재실행. 거래 수·금액·출처 보존, 버전 초기화, 실패 시 원본 보존 및 백업 복구 경로 확인.
- E11: 금액·날짜·계정 변경 후 잔액/검산/actual 및 시나리오 전망이 기존 계산 정책대로 바뀜. 원래 계정과 새 계정 양쪽 확인.
- E12: 최상위 라우터 변경 후 기존 모든 메뉴·직접 URL·404·뒤로/앞으로 정상. 새 데이터 조회 체계로 바뀌지 않음.
- E13: 가상 거래 수를 늘려도 수정용 한 건 조회는 거래 수에 비례한 반복 쿼리를 실행하지 않음. 기존 기본키·분개/태그 인덱스를 사용하는지 실행 계획을 확인하며 전체 목록·페이지네이션 구현은 포함하지 않음.
- E14: 동일 요청 번호/동일 내용은 한 번만 적용, 같은 번호/다른 내용은 거절. applied 결과는 거래와 함께 커밋/롤백. 결과 확정이 먼저 잠금을 얻으면 not_applied를 기록하고 늦은 원래 저장은 차단한다. 결과 확정 응답 유실도 동일 요청으로 반복 확인 가능. 적용 뒤 다른 수정/삭제가 있어도 이전 성공을 현재값으로 오해하거나 복원하지 않는다. 결과 메타데이터에 사용자 필드의 전후 사본이 저장되지 않음.
- E15: 열어둔 거래를 삭제하고 같은 숫자 ID로 새 가상 거래가 생성된 경우, 원래 수정 버전으로 새 거래를 수정하지 못함. 직접/이관/규칙/개시잔액 생성 모두 수정 버전이 채워지며 클라이언트는 버전의 숫자 증가를 가정하지 않음.

## Critical Paths

1. [→E2E] 거래 목록 → 기존/이관/반복/개시잔액 각각 수정 → 저장 → 목록 복귀 → 실제 재조회로 값·ID·출처 확인.
2. [→E2E] 다른 창 수정/삭제 → 오래된 저장 → 초안 유지와 최신 거래 안내.
3. [→E2E] 응답 유실·느린 응답·목록 로드 실패 → 저장 결과 확인 → 중복 제출과 초안 유실 없음.
4. [→E2E] 신규 입력 → 계정 추천 → 내역 변경 → 계정 유지 → 저장 → 다음 입력.
5. [→integration] DB 중간 실패·동시 저장·개시잔액 중복 경쟁 → 전체 롤백 또는 단 한 건 성공.

## Planned Test Files

- backend/tests/test_transaction_edit_migration.py (신규): E10.
- backend/tests/test_legacy_import.py, test_materialize.py, test_live_projection.py: B06–B07/E11 교차 기능 회귀. 실제 개인정보 대신 가상 fixture.
- frontend/e2e/transaction-edit-state.spec.ts (신규): 초안/행 ID/모드 전환·응답 경쟁 순수 상태 검증.
- frontend/e2e/transaction-edit.spec.ts (신규): F01/F04–F06, E02–E09/E12의 화면 흐름. 핵심 성공 경로는 실제 API·임시 DB.

공통 폼·라우터 수정은 기존 기능에 영향을 주므로 F02/F03/E12는 CRITICAL 회귀 요건이다. 현재 회귀가 발생했다고 주장하는 것은 아니다. 실제 구현에서 추가한 모든 분기와 오류 경로에 집중 테스트를 붙인다.
